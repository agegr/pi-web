# Built-in subagents

## Built-in subagents
- Profiles accept `codemode: inherit | on | off` (missing means `off`). Inherit follows whether `codemode` is active in the parent session at spawn (so Always on, a project override, or the MCP extension switching it on under Automatic), not the parent's `codemode.mode` or `inlineBudget`, which the child reads from its own settings. The child loads only the codemode factory (`createSubagentCodemodeExtension()`, an inline extension because `noExtensions` drops `builtin:` ones; it reads `-builtin:codemode` itself on every load), never the normal session's MCP host or tool-search, and scripts call only the tools the child admits (see the allowlist below). The resolved choice is saved in `resourceSnapshot` (`codemode: true`, `codemode` in `tools`) for reload, resume and RPC reopen; old snapshots without the field keep their previous resource policy. Changing a profile applies to new children, not existing sessions. A Chat-only profile (no tools, skills or extensions) stays Chat only under inheritance and rejects an explicit `on`. A snapshot that cannot restore the child's resource policy is refused instead of being reopened as a normal session.
- Profiles accept `mcp: on | off` (missing means `off`; `true` reads as `on`; no `inherit`). A child with `mcp: on` loads `builtin:tool-search` and `builtin:mcp` with an `McpHost` of its own (`createSubagentMcpExtensions()`), so it connects the servers in `mcp.json` (project ones under the same trust rules) and nothing else of the normal session. They are named in `additionalExtensionPaths` (`SUBAGENT_MCP_EXTENSION_PATHS`), which loads a built-in under `noExtensions` as well and keeps the `builtin:mcp` path the host and the policies recognise; that also bypasses `-builtin:` settings, so each factory reads its switch on every load, as the child's Code mode does, and `scopeSubagentExtensions()` never drops them. Without Code mode the host registers `codemode` servers as `deferred` (`codemodeAvailable` is the child's Code mode, not the sandbox), and the allowlist adds `tool_search`. An allowlist admits MCP tools by name (`mcp__*` and the resource tools), since servers connect long after it is fixed. `createSubagentMcpPolicyExtension()` then blocks an MCP-named tool another extension registers unless the profile selected it, and, while the child's built-in tools are read-only (Explore, Plan), every MCP tool without `readOnlyHint: true`, codemode scripts included; a profile of extension tools alone is not read-only. A chat-only profile rejects `mcp: on`. The snapshot keeps `mcp: true`, so reload, resume and RPC reopen load the same; an older snapshot loads no MCP. A run prompts the SDK session directly, so `prepareChildMcp()` calls the wrapper's `prepareMcpForRun()` first: it waits for servers with `direct` tools as a sent prompt does, and abortSubagent, the parent's Stop and Stop in the child's chat all end the wait and abort the run before it starts (the wrapper's `isRunning()` is false meanwhile, so `steer_subagent` is refused). Each child connects its own servers (stdio servers start again); the wrapper disposes its host when it closes, and idle release applies. The Agents panel switches it under Resources, disabled for a chat-only draft unless it is already on (the switch can still turn it off), with a line saying why; a save that names no value keeps the file's, and a profile that never had it gets no key. `lib/subagent-mcp.integration.test.mjs` pins this against a real stdio server.
- The global `builtInEnabled` in `~/.pi/agent/agents/settings.json` is off when the file or field is absent and when the file is malformed (fail closed); writes are atomic and keep unknown fields. The inline extension factory is always present, so a reload can apply the switch, but registers no tools while off; after changing it the user must reload the session explicitly, and `Agent` dispatch re-checks the setting so a stale call cannot start a subagent. When on, only a recognized legacy `pi-subagents` extension registering a reserved tool (`Agent`, `get_subagent_result`, `steer_subagent`) is removed, along with the conflict errors it caused; unrelated extensions stay. ADR 0003.
- The three tools register with `exposure: "model-only"`, so `ctx.executeTool()` (a codemode script) cannot start, collect or steer a subagent: a script-started run would record the nested call id (`<codemode call>/<n>`) as its `parentToolCallId`, which no transcript entry carries, and the chat would lose its link to the child session. `lib/subagent-extension.integration.test.mjs` pins this against a real `AgentSession`.
- A run stays in `getSubagentRuns()` from dispatch until its result entry is written, so `get()` reports a persisted `running` / `queued` status with no result and no running wrapper as `interrupted`: its process stopped and nothing will finish it (otherwise `get_subagent_result({ wait: true })` polls forever after a restart). `start()` writes the child's session file at dispatch (`persistChildSession()`): pi creates one only once a user or assistant message exists, so a run stopped while queued or connecting MCP servers, or refused for missing credentials, kept its entries in memory only and was gone (from `get()`, `resume` and the sidebar) once its idle wrapper was released. `setSessionFile()` reloads the written file, so pi appends every later entry; a queued run a restart cuts off reads as `interrupted` like a running one. The file is the only record of a settled run: one kept in memory as well would outlive a deleted child, and `resume` would reopen its missing file as a new, unrestricted session in the server's cwd.
- Built-in profiles (`general-purpose`, `explore`, `plan`) are switched off by name in that file's `disabledBuiltIns`, never by copying them to a `.md` file (ADR 0005). `builtInProfiles()` stamps `enabled` onto them so the panel, the `Agent` tool description and `resolveSubagentProfile` agree. Writes are minimal edits that keep names they did not touch, including ones no built-in claims; reading fails *open* (the feature switch has already failed closed). `PATCH /api/subagents/profiles` with `scope: "builtin"` writes it; `PUT`/`DELETE` refuse that scope. A same-name file replaces the built-in outright and is switched off through its own frontmatter. Only the switch is live for a built-in; the rest of the form is read-only.
- A positive `max_turns` allows one wrap-up turn only when the SDK would otherwise continue. The limiter chains the SDK's awaited `finishTurn` hook and ends unfinished work without cancelling a completed answer. The wrap-up turn sets `steeringMode` to `all` so a steer queued earlier cannot hold the instruction back. An `end` decision alone does not stop the run: AgentSession starts another run for anything still queued, so the limiter clears the queues, lists those messages in the turn-limit error, and refuses `steer_subagent` from then on. Exhaustion is a failed run with that error and any partial output. A request that ends with `stopReason: "aborted"` is `aborted` even when the controller did not ask for it (Stop in the child's own chat); a provider error is `failed`.
- `notifyParent` skips a background run's completion notification when the parent already collected that result with `get_subagent_result`, which marks it consumed. The mark names the run (`sessionId` + `completedAt`), never just the session, since `resume` reuses the session id; `resume` keeps the mark. While the parent `isRunning()` (often still inside that poll) the notification is held and the mark re-checked; an idle parent is notified at once.
- The notification is a `custom` message, which pi's `convertToLlm` replays as a plain `user` turn, so `subagentNotificationText()` prefixes `SUBAGENT_NOTIFICATION_PREFIX`; otherwise compaction files the report under the user's Goal / Constraints. Keep the prefix in code, never in a profile prompt, so the model cannot drop it. A `resume`d run's notification adds a line saying it supersedes the earlier report, which it would otherwise repeat word for word. Foreground `Agent` and `get_subagent_result` results are `toolResult`s and keep the bare `subagentFinalText()`.
- Profile files (`~/.pi/agent/agents/*.md`, project `.pi/agents/*.md`) are shared with other runtimes: a save round-trips every frontmatter key outside `MANAGED_FRONTMATTER_KEYS` (`lib/subagents.ts`; e.g. `name`, `allowed_subagents`, `exclude_extensions`, `disallowed_tools`) and carries foreign `ext:` tool selectors through. The pi-subagents aliases `skills` / `extensions` are seeded on first save and kept in step with `load_skills` / `load_extensions` while they hold a boolean (or `none` / `all`); a whitelist such as `extensions: pi-advisor-flow` is never rewritten, and the flags fall back to the aliases when `load_skills` / `load_extensions` are absent.
- A `skills:` list (`[review, testing]` or `review, testing`) preloads those skills' bodies (frontmatter stripped) into the child's prompt in both prompt modes and hides the catalog, as pi-subagents does; `lib/subagent-skills.ts`. Names are looked up among the skills the SDK discovered (so trust, packages and collisions apply), never used as paths, and `disable-model-invocation` skills may be named. A missing or unreadable name becomes one line in the prompt; the rest still load. Parsing is lenient: empty and non-string items are dropped and an empty value means no list, because a profile that fails to parse disappears from the list and from `Agent`. `true` / `all` / `none` / `false` stay switch spellings, `[]` names nothing, and `load_skills: false` wins over a list. Off is pi's `noSkills`, which keeps skills an extension provides. Without a list, replace mode appends pi's catalog while `read` or `bash` is active, as pi's `--system-prompt` does. The snapshot keeps the names, never bodies or paths, so resume and reopen reread current bodies; a malformed snapshot list narrows to what it names and never widens to the catalog. The Agents panel has no editor for the list: it shows it read-only under the skills switch, and a save keeps the authored spelling.
- An `extensions:` list (`[codegraph, "@team/adapter"]` or `codegraph, @team/adapter`) limits which extensions a child keeps, as pi-subagents does: `scopeSubagentExtensions()` (`lib/subagents.ts`) is an `extensionsOverride` that drops the rest after the SDK loaded them, together with the providers and models their factories queued. A dropped extension binds no handlers, tools or commands, but its factory has already run once, so this scopes the child; it is not a sandbox. Selecting paths before import would mean reaching into SDK internals on every reload (#1035). Names resolve like `ext:` selectors (directory, file or package name, case-insensitive), and a name two sources claim keeps neither. Path entries load nothing: a project profile must not load code that project trust gates. pi-web's own `<inline:…>` extensions always stay. `*` keeps every extension, `none` / `false` switch extensions off, and `load_extensions: false` wins over a list; the list parses as leniently as `skills:`. The SDK reapplies the override on every reload, and the snapshot keeps the names, so resume and RPC reopen get the same scope through `subagentExtensionLoaderOptions()`. `tools: ext:` still picks tools among the extensions that remain. The Agents panel shows the list read-only under the extensions switch, and a save keeps it as authored. `lib/subagent-extension-scope.integration.test.mjs` pins spawn, reload, resume and reopen against a real `AgentSession`.
- A child that loads extensions without `ext:` selectors (the Agents panel's extensions switch) gets no `tools` allowlist: the SDK fixes one when the session is created, so a tool an extension registers at `session_start` or later (pi's `dynamic-tools` example) would never be callable (#883). `subagentToolOptions()` (`lib/subagents.ts`) passes `noTools: "builtin"` with the profile's built-ins as `+name` entries and excludes the reserved tools and the SDK's other built-ins (`SDK_BUILTIN_TOOLS` mirrors pi's unexported list), so no extension can switch on one the profile leaves out. The snapshot's `allExtensionTools` makes reopen do the same; an older snapshot keeps its allowlist. `ext:` selectors still pass the names resolved at spawn: the SDK admits tools by name, with no source-aware hook, so a selected extension's late tools stay out. Such an allowlist also excludes every MCP tool it does not name (`mcp__*` and the resource tools): pi keeps those registered for codemode and `tool_search` unless the list names one, so a script could otherwise call an unselected extension's MCP tool; `ext:` selectors that `disallowed_tools` cancels out admit no extension tool. `lib/subagent-codemode-scope.integration.test.mjs` pins this. `lib/subagent-late-tools.integration.test.mjs` pins spawn, reload and reopen.

## What the model may choose when spawning a subagent
- `Agent` offers `subagent_type`, `prompt`, `description`, `run_in_background`, `resume`, `input_files`, `model`, and `isolation`. Thinking level, turn limit, and parent-context inheritance belong to the profile (`thinking`, `max_turns`, `inherit_context` in its frontmatter, editable in the Agents panel); the one exception is a level a call writes into its own `model` (below). A per-call value for any of them used to win over the profile while never appearing in the tool description, so a model guessing `max_turns: 8` or `thinking: "high"` silently discarded what the profile had decided. The runtime reads `thinking` (falling back to the parent's level), `max_turns`, and `inherit_context` from the profile, never from a parameter of that name. pi's validator allows keys the schema does not name, so a call that still sends one is accepted and the key ignored; transcripts holding such calls render and resume as before.
- `model` resolves as `request ?? profile`: the profile decides by default, and one run may go to a different model, which the tool description informs by listing each profile's own model and thinking level. A model reference, from the call or the profile, reads as pi's `--model` does: `provider/modelId` or a bare id, optionally ending in `:<thinking level>` (#1188). The whole reference is tried first, so an id that contains a colon (`qwen3:8b`) still matches, and a suffix that is no level is refused, never dropped. The level travels with its model: a call's `model: "x:high"` sets that run's thinking over the profile's, which is how one call picks a model and its level together without a separate `thinking` parameter for a model to guess; a call naming a model without a level keeps the profile's `thinking`. Within a profile, `thinking:` wins over a level on its own `model:`, as pi's `--thinking` does over `--model x:level`. pi clamps the level to what the model supports. The Agents panel shows such a profile model as its base model (not unavailable) with the reference as written; choosing another model there drops the level, which the Thinking field sets. `input_files` stays a per-call parameter: the host inlines those UTF-8 files from the session cwd into the delegated task (`lib/subagent-input.ts`, bounded count and size), which is input preparation, not a profile setting. The size bound is the child model's: about a tenth of its context window by pi's chars/4, counted in bytes, never more than 512 KiB, and 512 KiB when the window is unknown (0). A copy at the flat limit (about 131k tokens) arrives in the child's first message and is over half of what a 272k-token model holds before pi compacts, so a child could compact before its first tool call (#1199). A larger set is refused before any worktree or child session exists, with an error telling the model to pass fewer or smaller files, or name the paths in `prompt` if the subagent can read them. That early check only looks the model up (the call's, else the profile's, else the parent's) and never fails on it: the child's model is still resolved, and a bad reference refused, after the child's `createAgentSessionServices()`, which reloads models.json into the shared runtime and registers the child's own extension providers. A model added in Settings › Models since the parent opened, or one only the child's extensions provide, therefore still runs, with the flat limit. `isolation` stays a string, not a `"worktree"` literal, so a model that fills every optional field with `""` can still start a subagent; only `"worktree"` takes effect.
- `Agent` resume retains the child's profile, model, thinking level, and context. Its continuation prompt, description, and background mode can change. Nonempty creation options (`model`, `input_files`, `isolation`) are rejected before dispatch; empty defaults remain compatible with tool startup. Start a new subagent to change those options. Resume refuses a child whose cwd no longer exists (an isolated child's worktree is removed when its run ends), as the wrapper's `send()` does, since a run prompts the SDK session directly, and its error tells the model to start a new subagent instead (#1202).
- An isolated run's `subagentFinalText()` says where its worktree is, since the model reads only `content` (#1202). It goes by whether the worktree path still exists when the run's result entry is written (`recordResult()`), and the entry keeps that as `worktreeExists`, so the child read back from its file says the same. Gone: removed, its branch keeping any commits, also when the checkout was removed during the run and git's removal then failed. Still there after this run's removal was refused for uncommitted or untracked files: kept at its path and branch, for that reason. Still there otherwise: still at its path and branch, with no reason, as after any resumed run (resume removes nothing, and an interrupted run never got to). Never in git's words, which end in `use --force to delete it`. An entry written without the field gets no sentence.

## Agent switcher usage
- Each row of the agent switcher (main agent and every subagent) shows its active time, total tokens and cost, with the stats popover's breakdown in its tooltip; the header shows their sum. `POST /api/sessions/stats` reads each id as `GET /api/sessions/[id]` does (a live wrapper's entries, else the cached file) and counts like the popover (`computeSessionStats()`, `computeSessionTotalActiveMs()`), never touching an `/api/agent/` route. A summary is kept per SessionManager until its entry count or last entry changes, since the switcher polls every 3 s on a visible page while any agent in the family runs, and reads once more when a run starts or ends. The toolbar's numbers are the main session's alone; the switcher's sum is the only place subagent spend adds up.
- The top bar's Agents badge counts the family's subagents, and while any of them runs it counts only those, accent-tinted and ringed by a spinner (`getAgentsBadge()`, `lib/session-family.ts`); the button's title and label say how many run. Running means listed by the sidebar's running poll, as in the switcher's header, so the badge adds no request of its own.

## Viewer tab
- The `Agent` card's button opens the child as a read-only tab in the right panel (`components/SubagentViewer.tsx`, tab id `agent:<sessionId>`), beside file and terminal tabs. The agent switcher above the chat opens a child as the main chat from its row; the row's side-panel button toggles this tab (accent-coloured and filled while the open panel has it, active or not; a click then closes the tab, and the panel with its last tab) and leaves the switcher open, except on phones, where the panel covers the chat. The tab reads only `GET /api/sessions/[id]` and `GET /api/sessions/[id]/context` (a running wrapper's in-memory entries, else the file), never an `/api/agent/` route, so viewing cannot start, reopen or keep alive an `AgentSession`. While the sidebar's running poll lists the child, it polls the newest page every 2 s on a visible page, one request at a time; only the active tab is mounted, so a hidden or closed tab polls nothing. It shows finished entries only, not the streaming message.
- A poll is folded into the pages already loaded (`mergeTailPage()`, `components/subagent-viewer-state.ts`): if the newest page overlaps them, the older pages stay and shown messages keep their objects; otherwise it replaces them. "Load more" asks `before` the oldest entry and prepends only while that is still the oldest (`prependOlderPage()`), so a page is never prepended twice or over a gap. Session info is refetched when the run starts or ends, so the persisted status replaces the live one. Subagent tabs are not persisted and are dropped on every project switch (`changeFileWorkspace()`), while the file tabs are parked; an active subagent tab hands the panel to the restored project's file tabs.
