# Settings › MCP: adding servers

## Settings › MCP add (`lib/mcp-add.ts`, `components/McpAddServer.tsx`)
- **The browser sends the paste, never a config** (ADR 0006). `POST /api/mcp { action: "add", text, scope, values?, secretReferences?, server?, name?, rawPi?, trustFolder?, confirmHostEnv? }`: `prepareMcpAdd()` parses `text` again with the importer the pane previewed it with, so only the importer's fresh object, escaping included, is written. `values` maps field ids to text (escaped as any literal) or `{ reference: NAME }` (stored as `${NAME}`, only where every target is a value pi resolves). `secretReferences`, the way into a project, maps the paste's **own** literal secrets in resolved values no field fills (`referenceableLiteralSecrets()` labels: `headers.Authorization`, `env.API_KEY`, `oauth.clientSecret`; never the URL, command or arguments, where pi reads no variable) to a variable name, stored after a header's `Bearer` / `Basic` / `Token` scheme; a bad name or place is a `field-reference-invalid` note.
- **Checks, in order, each a typed refusal:** the guards of every write (origin, JSON, cwd, `mcp-off`); the shape (`invalid-request`, text at most 256 KiB); where it may go (a project server's folder, below; first, so nothing is asked about a server the folder refuses); the parse (`import-failed` with `notes`); the name (`name-invalid`; `name-taken` with a free `suggestedName`, checked again under the file's lock by `insertMcpServer()`); the fill (`fields-incomplete` with `notes`, secret references included); the SDK's `validateMcpServerConfig()` (`server-invalid`); `PI_WEB_PASSWORD` in a resolved value (`web-password`); a literal secret in a project server (`secret-global-only` with `fields`, from `fillMcpImportFields()`'s `secretPaths`); then the host-variable confirmation.
- **Host variables sent elsewhere need a yes.** A non-pi paste (`pi mcp add` and the "Enable pi mcp syntax" toggle are the user's own syntax) whose headers or `oauth.clientSecret` read variables set in Pi Web's `process.env` gets `host-env-confirm` with their `names` (`mcpHostEnvNames()`: names, never values). A stdio entry's `env` (it stays in the process it starts) and a variable the user named do not count. `confirmHostEnv` covers only the names it lists, so a paste changed in between is asked about again.
- **A project server goes where a decision trusts the folder** (`writeTarget()`, as every project write), except a **fresh folder** (no trust-requiring resources, no decision for it or an ancestor), which `trustFreshFolderAndWrite()` (`lib/project-trust.ts`) trusts and writes in one step when the request says `trustFolder` (ADR 0006, "Fresh folders"); a plain add there is 403 `project-untrusted`. GET reports the step as `project.trustFolder` — `{ allowed: true }`, `{ allowed: false, reason: "trust-too-broad", breadth }`, or `{ allowed: false, reason: "folder-not-fresh" }` (the SDK sees nothing that needs trust but `hasTrustRelevantEntries()` finds a link to nothing) — from the step's own checks in its order, so the pane never offers a step the route refuses. The step:
  - **Breadth guard** (`freshFolderTrustBreadth()`, by real path): never the home folder, a filesystem root, or a folder holding the home folder, Pi's agent folder, another folder Pi Web knows (the allowed file roots), or a project with no decision that would inherit this one (`findInheritingTrustProject()`: `.pi/<entry>`, a dangling `.pi` link or `.agents/skills`, no decision of its own or between; `contains-project`). The scan is breadth first, 4 levels deep, never through a link, `node_modules` or `.git`, and refuses (`too-many-folders`) past 2,000 folders read. It runs in GET, in the route before the paste is parsed, and in the step, the nested scan again inside the chain after `getEntry()` (a `git clone` can land in between). 409 `trust-too-broad` with `breadth`.
  - **One step per folder at a time** (a globalThis chain, `Symbol.for("pi-web:fresh-folder-trust-locks")`, keyed by real path), and inside it the folder is checked again: `hasTrustRequiringProjectResources()`, then `hasTrustRelevantEntries()` (an `lstat` of the same places, since `existsSync` skips a dangling link that counts once its target appears), then `getEntry()` must be null. A folder that changed since the pane offered the step is 409 `folder-not-fresh` with its new `trust`, unwritten and untrusted. `TRUST_REQUIRING_PROJECT_ENTRIES` copies the SDK's module-private list; `lib/project-trust.test.mjs` compares it with the SDK's source, so an upgrade that adds an entry fails there.
  - **Trust first, then write.** `ProjectTrustStore.set(cwd, true)` (a locked or unparsable `trust.json` fails here, before any write: 409 `trust-unreadable`), then the insert; a failed insert takes the decision back with `set(cwd, null)`. When that fails too, the answer keeps the write's `reason` and adds `trustKept: true` with the folder's `trust`, which the pane says (`mcp.add.trustKept`). The pi CLI is not serialized against.
  - **Nothing is rebuilt and no session needs to be idle**, unlike `POST /api/project-trust`: the MCP host reads trust before every prompt, so the server connects at an open session's next message. `invalidateModelsCache()` runs after it.
- **The page learns the folder's new trust.** Every project add answers with `trust` (`.pi/mcp.json` alone makes a folder require trust), plus `trustedFolder` for the step; a `folder-not-fresh` refusal carries `trust` too. `McpConfig` hands it to AppShell (`onProjectTrustChanged(cwd, status)` → `handleProjectTrustChanged()`, applied only for the folder Settings shows), which reloads every mounted section in place through `projectTrustReloadKey()`; no session key changes.
- **The pane** (`components/McpAddServer.tsx`, helpers in `components/mcp-add-helpers.ts`; shared layout in [settings-ui.md](settings-ui.md)):
  - The draft survives showing another row. A changed paste or toggle keeps the name, values, variables and picked server only while it is the same server connecting to the same place (`mcpAddDraftWithPaste()`): a password typed for one paste must never reach the next one's URL through a field of the same id.
  - The box is a textarea (`ConfigAddSourcePanel` `multiline`): Enter adds a line, Cmd/Ctrl+Enter or the button adds, never while an input method composes (`addSourceKeySubmits()`). The pi-syntax toggle shows only where the importer reads the paste differently with it (`mcpAddOffersRawPi()`). Every format the importer reads has an example in `MCP_ADD_EXAMPLES`, read as that format with nothing to fill in (`mcp-add-helpers.test.mjs` fails otherwise). Importer notes render from their codes (`mcpImportNoteText()`); a paste of several servers gets a picker, one Add per server.
  - **The preview** (`mcpAddPreview()`) shows the command line or URL **as written**, hiding only typed password values; never mask it through `lib/mcp-secrets.ts` (ADR 0006: masking by shape lets a link's author choose what the user cannot read before the automatic test runs it). Env and header **names** only, plus the values that run a shell command and the host variables it reads.
  - Values to fill in and "Secrets in the paste" (each referenceable literal secret) offer "Read it from a variable" where pi resolves the value; ticking it opens a box holding a name pi accepts (`mcpSuggestedVariableName()`). A box emptied asks for a name (`field-reference-invalid`, `problem: "missing"`; Add waits with "Fill in … first"); an unusable value (a name pi refuses, an option not offered) says why under its box (`fieldProblems`, `aria-describedby`) and Add waits with "Correct … first" (`field-invalid`). Filled in, the config is checked before Add with the importer's port of the SDK validator (`validationProblem()`), its message showing a URL as the preview does, so a typed password stays hidden. A refusal the route still sends is worded as an Add's (`MCP_ADD_REFUSAL_KEYS`: `server-invalid` with the validator's message, which names fields, never values; `web-password`).
  - The Project option says why it is unavailable (`mcpAddProjectMode()` / `mcpAddProjectBlockText()`), with Trust… where the trust dialog would offer it, and explains the fresh-folder step; Add then reads "Add and trust this folder". Why Add waits is said under it (`McpAddSubmitBlock`), including a Project picked and blocked since (a secret typed): the switch explains only a disabled option.
  - **Literal secrets follow the route's rule exactly** (`mcpAddSecretPaths()`): a required password field not answered with a variable counts before anything is typed, an optional one only once something is typed, and a variable still being named counts as a variable.
  - The paste's own scope hint (`pi mcp add -l`, `--scope project`) picks Project only where a decision already trusts the folder: pasted text never preselects trusting a folder.
- **Nothing connects before Add; one Test after it.** An install link hides its command in base64 (the "CursorJack" deeplink attack), so nothing connects on paste. Add is a change like any other (`runAction()`, `busy` `add`); only an answer that wrote the server selects it and starts its Test (`postMcpTest()`, never aborted), unless `mcpTestBlock()` says the route would refuse it. The Added notice offers Sign in when that test found an OAuth server asking for one, not while its Sign out is on its way (which would cancel it on arrival). A refused Add keeps the pane and draft, says why under it (`role="alert"`), and reloads the listing as any refused change does. The pane stays editable while the request is out: an answer about a draft edited since (`addDraftRef`) is neither shown nor acted on (its host-variable confirmation, Use <name>), and a successful Add keeps what was typed since; it removes the pane, so focus goes to the new server's row (`McpFocusBack.toSelectedRow`).
- Test adds only against a temp `PI_CODING_AGENT_DIR`, as `app/api/mcp/route-add.test.mjs` does; never a real `~/.pi/agent`.

## Paste import (`lib/mcp-import.ts`)
- pi resolves `${NAME}`, `$NAME` and a leading `!command` in env values, header values and `oauth.clientSecret`; other clients store literals. Literals there are escaped (`$` → `$$`, a leading `!` → `$!`), or a pasted `"!curl … | sh"` would run on the host at every connection. `command`, `args`, `url` and `cwd` are used raw by the SDK: never escape them. Only `pi mcp add` and the rawPi toggle keep values as written, noting a `!command` (`shell-command-value`). `lib/mcp-import.integration.test.mjs` pins the round-trip through the SDK resolver, and `validationProblem()` against the SDK's validator.
- References (`${env:X}`, `{env:X}`, `%X%`, Gemini's `$X`) become `${X}` only in those three resolved fields. pi substitutes nothing elsewhere, so a reference in `command`, `args` or `url` becomes a field to fill in; only a leading `$HOME` / `${userHome}` becomes `~` and `${workspaceFolder}` `.`. Never trust `validateMcpServerConfig` to clean an entry: it returns the object it was given and accepts milliseconds as seconds. The importer builds a fresh object from known keys, notes every dropped key, and reads a timeout in its client's unit (Gemini milliseconds, Cline seconds; a guess is a warning).
- pi 1.0 fields: `description` (pi lists the server with it in the system prompt) is read only from pi syntax (`pi mcp add --description`, the rawPi toggle), since another client's text would reach the prompt unseen in the preview; `oauth.clientName` and `oauth.authServerMetadataUrl` are read like the other OAuth options; `auth` (a pi provider's token) is never imported. The old exposure `codemode-deferred` is written as `codemode`, as pi writes its validator's copy.
- The `pi mcp add` grammar ports the module-private SDK `cli.js` (`maxPositionals` 2, `-l`, an option on the wrong transport refused, split at the first `=`, `--help` anywhere prints help, an empty name refused). The integration test runs the real `runMcpCommand` into a temp dir and compares the written entry byte for byte, mixed shell quoting included, so an SDK change to the CLI fails it. Quoted and unquoted text of one word is joined before any grammar reads it (`'A=$'B` is `A=$B`).
- `parseMcpImport()` and `fillMcpImportFields()` never throw: the add route re-parses the request, and a throw is a 500. Guard every `decodeURIComponent` (a malformed `%zz` throws `URIError`), keep an impossible `$'\U…'` code point as text, and bound any regex run that can rescan (quadratic otherwise).
- Literal secrets and password fields follow `lib/mcp-secrets.ts` (`literalSecretFields`, `maskArgs`, `maskUrl`, `isSecretName`), never a classifier of the importer's own: the route's `secret-global-only` and the panel's masking must agree. `fillMcpImportFields()`'s `secretPaths` are typed password values plus literal secrets, never a `{ reference: "NAME" }` (stored as `${NAME}`); `PI_WEB_PASSWORD` is the route's to refuse.
- A server name pi accepts is kept as written; only an invalid one is sanitized. A derived name avoids `takenNames`; a source-chosen name already taken stays and gets `name-taken` with a `suggestedName`, for the route's typed 409.
- Command lines that manage a CLI (`pi mcp remove|login …`, `claude|codex|gemini mcp <subcommand>`, `pi install|remove|update …`) are refused with `cli-not-a-server`: imported as a stdio server, the Test after Add would run them on the host. `claude mcp serve` is a server and imports.
- Notes are `{ code, params }` (`MCP_IMPORT_NOTE_CODES`, 84 codes, severities in `MCP_IMPORT_NOTE_SEVERITY`); a field's `label` and `description` are source data, shown as they are. The browser preview and the server re-parse run the same pure code, so client code rules apply: no regex lookbehind and no `URL.canParse` (old Safari).
