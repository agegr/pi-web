# Settings › MCP: reads, panel and writes

## Settings › MCP reads (`lib/mcp-config-read.ts`)
- `GET /api/mcp` reads files only: it never spawns a server, opens a connection or resolves a value, so it lists an untrusted project as safely as the global file. Nothing on its path may call `createDefaultTransport()`, `resolveConfigValueOrThrow()` / `resolveHeadersOrThrow()`, `connection.oauthSettings()` (each runs `!command` values) or `McpOAuthCredentialStore` (a read creates `mcp-auth.json` and a lock). The signed-in hint is a raw parse of `mcp-auth.json`, keyed as the SDK keys it (`mcpOAuthStoreKeys()`: `mcp__<name>|<URL>` since pi 1.0, else the record older versions kept under `String(new URL(url))`, which the first server of the URL takes over), tokens meaning `tokens.access_token`; an unreadable file leaves `signedIn` unset, not false. `trust.json` is still read under the store's `lockSync` (a transient `trust.json.lock` directory), the Code mode preference under the settings lock.
- Each file is read on its own, never through `loadMcpConfig()`, which skips an untrusted project's file and merges by name, hiding the global entry a project entry replaces. Parse as the SDK does (`JSON.parse`, no BOM stripped, `{ mcpServers: {} }`, `autoEnableCodemode` a boolean); with the internals loaded each entry is checked with the SDK's `validateMcpServerConfig()`, and an invalid one is still listed with its reason. Without them (MCP off) entries are listed with `validated: false`, a leading `!` marks a command and any mention of `PI_WEB_PASSWORD` counts. A global entry is `shadowedByProject` only when the project's entry would load (the SDK skips an invalid one and keeps the global). A contract test checks that on a trusted merge the per-file reader gives exactly `loadMcpConfig()`'s servers. Beyond the validator, `refuseAsLoaderDoes()` refuses what `loadMcpConfig()` skips, in its order (global file first): a name whose namespace an earlier loaded entry has (`a-b` beside `a_b`; the later one) and, in the project file, an entry with a `url` and `auth` (a repository must not choose where a provider's token goes); `readConnectableMcpEntry()` refuses both too (409 `server-invalid`). An HTTP entry's `auth.provider` is reported as `authProvider` (it sends that pi provider's token, so `usesOAuth` is false and the Sign-in row points to Settings › Models), its `description` as written.
- The **project file** is repository-controlled and read before anyone trusts it, so it follows the file-access link rule: its real path (links in the file or in `.pi/` included) must be inside the allowed roots the route checked the cwd against; a dangling link is refused (`link-dangling`), never read as no file; the resolved path is opened once with `O_NOFOLLOW | O_NONBLOCK` and checked through `fstat` (regular file, at most 1 MiB), so a FIFO is never read. More than `MCP_PROJECT_MAX_SERVERS` (200) servers is `too-many-servers` and nothing is listed, as for a file over 1 MiB (otherwise 80,000 names cost seconds and a 32 MB answer). The **global file** is the user's: a link is followed wherever it leads (`realPath` reports where) and a dangling one reads as no file, as for the SDK. The SDK follows a trusted project's link outside the roots anyway when a session connects; the panel can only report `link-outside`.
- **Nothing literal reaches the browser.** Env and header **values** are never sent (names only). `command`, `args` and `url` are masked by `lib/mcp-secrets.ts`: URL userinfo, query parameters named like credentials or holding token-like values, bare token-like query parts and path segments, `--api-key=…` / `--token X` / `-k X` / `--auth X`, `Name: value` headers, `NAME=value` pairs, `Key=value;…` connection strings; a value of several words (a whole command line in `command`, `Bearer …` as one argument) is masked word by word, `Bearer` / `Basic` / `Token` or a credential `Name:` making the next word a secret. The SDK expands nothing in those three fields, so only placeholder-shaped values stay visible: `${NAME}`, or `$NAME` in environment-variable capitals (which a wrapper such as mcp-remote or `sh -c` expands); `$Passw0rd` is masked. The fields the SDK resolves (env, headers, `oauth.clientSecret`) use `isReferenceOnly()`, the SDK's syntax (`$name` of any case, `$$` / `$!` escapes). Exception: `command` and `args` of a project no decision trusts (`projectUntrusted`, `trust.decision !== true`, panel and trust dialog alike) are shown as written (ADR 0006); its URL is still masked, never its host. `lib/mcp-secrets.ts` is pure (the browser importer uses it); `literalSecretFields()` is the same classification for what may only be saved globally.
- A JSON syntax error never quotes the file (`jsonErrorMessage()`): V8 quotes text around an unexpected token, often a literal secret. `configKey`, which statuses are compared by, is an HMAC of the entry's `canonicalJson()` under a random per-process key (`mcpConfigKey()`, `lib/mcp-config-key.ts`, shared with the MCP host), never the JSON (it carries every literal value) nor a plain hash (a weak password in an otherwise visible entry would not survive it). `canonicalJson()` must stay total (a marker past 64 levels), or a deeply nested repository file overflows the stack, stopping a session's whole sync and failing GET.
- `commandFields`, `variableReferences` and `webPasswordField` come from `resolvedConfigValues()` (`lib/mcp-config-values.ts`, re-exported by `lib/mcp-transport.ts`), the walk the transport refuses `PI_WEB_PASSWORD` with: a stdio entry's `env`, an HTTP entry's headers and `oauth.clientSecret`, told apart by whether `url` is present (an `env` on an HTTP entry is never resolved, so its `!` runs nothing and is not labelled). `transport` and `usesOAuth` follow that rule, not the validator's branch: `{ type: "stdio", command, url }` validates as stdio, but `createDefaultTransport()` connects it over HTTP and runs its header `!command`s, so it is reported as HTTP; only an entry the validator refuses gets the validator's reading (a legacy SSE entry has no transport). `variableReferences` names the host variables those values read (the SDK's `getConfigValueEnvVarNames()`, or without internals `templateVariableNames()`, a port pinned against it), never their values: they resolve from Pi Web's whole `process.env`, not a stdio server's sanitized one, so a header `${GITHUB_TOKEN}` sends that token to the entry's URL. A `!command` value is in `commandFields` instead.
- Availability is a typed reason, checked in order: `operator-disabled` (`PI_WEB_DISABLE_MCP`), `internals-unavailable` (the loader's `detail`), `builtin-disabled` (the `settingsPath` whose `extensions` entry does it). `readBuiltinExtensionSwitches()` (`lib/builtin-extensions.ts`) resolves `±builtin:*` exactly as the resource loader does, through the SDK's `DefaultPackageManager` given only the two `extensions` lists (the project's only while trusted) and `onMissing: skip`, so no package is ever installed or looked up. Code mode reports the global preference, `-builtin:codemode` likewise, and `peekCodemodeSandbox()`: the settled self-test result, or `not-checked` until a normal session has run it; GET never starts the self-test.
- With a cwd whose settings sessions load (`trust.trusted`, `projectTrustReloadOptions()`'s rule; never with an unreadable store), `projectOverride` names the project's `.pi/settings.json` when its `defaultTools` decides Code mode there whatever the global choice (ADR 0006). `projectCodemodePreference()` (`lib/codemode-settings.ts`) never reimplements pi's merge: it runs the project's raw text through the SDK's `SettingsManager` beside each global choice, and an override is the two agreeing, malformed values included. Both reads of a trusted project's `.pi/settings.json` (this and the switches) go through `readRegularFileText()` (`lib/regular-file.ts`, at most `PROJECT_SETTINGS_MAX_BYTES`, 1 MiB), without pi's lock, never a plain `readFileSync()`, which waits on a FIFO and stalls the whole server. A file that is not regular or too large reads as unreadable (every built-in on, no override).
- `ProjectTrustStatus` carries the nearest decision (`decision`, `decisionPath` as `trust.json` keys it, `inherited` when an ancestor's, compared with `samePath()`), so exact trust, trust through a parent, an explicit `false` and no decision are told apart, for a fresh folder (`requiresTrust: false`) too. For a folder that requires no trust a broken `trust.json` goes to `decisionError`; one that requires trust still throws. `mayReadProjectConfigNow()` and `projectTrustReloadOptions()` check `hasTrustRequiringProjectResources()` first, so neither locks `trust.json` for a fresh folder on every prompt or session start.
- **The trust dialog lists the project's MCP servers** (`components/ProjectTrustDialog.tsx`; ADR 0006). `GET /api/project-trust` adds `mcpFile` and `mcpServers`: `readProjectMcpServers()`, the same file-only read and masking as `/api/mcp`, filtered to the project's entries; `replacesGlobal` marks one that replaces a global server once trusted (counterpart of `shadowedByProject`). Each entry shows its command line or URL, `!command` fields, the host variables it reads (for HTTP worded "sends … to this server": how a repository exfiltrates a token through a header) and, for `PI_WEB_PASSWORD`, a warning, not a reassurance (Pi Web refuses such an entry; the pi CLI, reading the same file, does not). A refused entry shows neither line. The dialog fetches the listing afresh when it opens and hands the fresh status to AppShell (`onStatus`); Trust waits until the listing answers, fails or times out (`MCP_LISTING_TIMEOUT_MS`, 10 s). The listing never depends on `trust.json`: an unreadable store is 500 `trust-unreadable` with the listing beside it. A project file reported `link-outside` or `too-large` is not listed, yet the SDK reads it once trusted (it follows links, has no size cap), so the dialog says so rather than "no servers".
- `/api/project-trust` refusals carry a `reason` (`cwd-invalid`, `cwd-not-directory`, `cwd-denied`; POST adds `request-denied` 403, `content-type` 415, `trust-not-required` and `session-busy` 409, `internal` 500); AppShell keeps `{ error, reason }` and the dialog renders `mcp.reason.<code>`, showing the English `error` only as an `internal` or network failure's diagnostic. Repository text (name, command, arguments, cwd, URL, field names) goes through `revealHiddenCharacters()` (`lib/mcp-server-display.ts`) in the dialog and the panel alike. Strings: `trust.mcp.*` plus the shared `mcp.transport.*`, `mcp.field.*`, `mcp.server.*`, `mcp.fileProblem.<reason>` and `mcp.reason.<code>`, which Settings › MCP reuses instead of adding its own. Layout is `.project-trust-*` in `app/settings.css`, never inline. The dialog is offered only while `requiresTrust && !trusted` (the restricted-mode banner; Settings › MCP's trust notice, above Settings), so a project trusted through an ancestor never shows it.

## Settings › MCP panel (`components/McpConfig.tsx`)
- **No project needed.** `mcp` is not one of `PROJECT_SECTIONS`; `settingsSectionRequiresProject()` (`lib/settings-navigation.ts`) is the one place deciding which sections need a project (SettingsPanel's tabs, the phone picker, the fall-back-to-General effect and AppShell's sidebar shortcuts read it). Without a cwd the panel lists the global file alone. It is keyed on `cwd ?? ""` and remembers its row per project (`["mcp", cwd]`, or `"mcp"`).
- **Row states** (`mcpServerRowState()`, `components/mcp-config-helpers.ts`) come from the files first, in order: `invalid`, `web-password`, `disabled`, `not-trusted`, `replaced`, `mcp-off`. Only an entry the file lets connect shows its last known status (`mcpStatusRowState()`): `connected`, `needs-auth` or `failed` from a test or a session, and from a session also `connecting`, `disconnected` and `conflict`; else `on`, which means a session would connect it, never that one did. A session's `not-trusted` (an older trust than the listing's) and a connection it closed since (`closedAt`) read `on`. Project servers count as read only while `trust.decision === true` (the host's `mayReadProjectConfigNow()` rule), never `trust.trusted`, which is true for a folder that requires no trust; a global entry is `replaced` only while the project's entry is read in its place. Listed tools come only from a test ([mcp-test-sign-in.md](mcp-test-sign-in.md)). The status dot is `aria-hidden`, so a state is never told by colour alone: it is in the row's `aria-label`, a short badge and the detail pane.
- **Notices.** MCP off, with its reason. Otherwise `hostInactive`: an open session whose `/mcp` is another extension's, naming its folder and that extension (only a session can tell). A project folder the route refuses (`cwd-*`) does not hide the global servers: `loadMcpOverview()` loads again without the cwd and the Project group says "Not listed" with the reason. Trust is reported only when the project has a `.pi/mcp.json` or a problem with one: untrusted (`ConfigTrustNotice`), an inherited `false` naming its folder, and inherited trust as "Trusted through <path>", the only place that trust is visible. A folder that requires no trust gets no trust notice unless a decision marks it untrusted: a dangling `.pi/mcp.json` link is listed (`link-dangling`), but the SDK's `existsSync` finds nothing to trust, so Trust would only meet `trust-not-required`. File problems go to the footer (`ConfigFooterStatus`). A load ends after `MCP_OVERVIEW_TIMEOUT_MS` (15 s, both requests together), since Refresh is disabled while one runs.
- **The detail pane shows only what GET sends:** the masked command line (`mcpServerTarget()`), working directory, env and header **names** (each only when set), the `!command` fields and host variables (left out for a refused entry, which never connects; kept for a disabled one), the Sign-in row (**Settings › MCP sign-in** in [mcp-test-sign-in.md](mcp-test-sign-in.md)), the exposure, the file. The Code mode pane holds the choice, the sandbox and `-builtin:codemode`.
- **Whether Code mode reaches a server's tools** (`mcpCodemodeReachNotice()`, which says how each case still reaches them): a `codemode` server (pi 1.0 reads the old `codemode-deferred` as `codemode`, and GET reports the validator's copy)'s Tools line warns when the sandbox failed, under `-builtin:codemode`, or with `autoEnableCodemode: false` under any effective choice but Always on (the MCP extension never activates codemode then). `mcpEffectiveAutoEnableCodemode()` merges that flag as `loadMcpConfig()` does: the project file's value where that file is read (`trust.decision === true`), else the global file's, else true; it applies to sessions started or reloaded afterwards.
- **The Code mode choice lives only here** (ADR 0006): Automatic / Always on, `PUT /api/tools/settings { codemode }` through `saveMcpCodemodePreference()`, under the load's 15 s deadline (`withinDeadline()`) so a hung request cannot keep the switch disabled. It reloads no session: `reload` carries the tool set pi rebuilt, so only new sessions see `defaultTools`. The PUT answers what the route read back after writing, and the overview is loaded again whatever the outcome. Always on is disabled, with the reason under the switch, while the sandbox failed or the **global** `extensions` set `-builtin:codemode` (`globalBuiltinSettingsPath`); an unchecked sandbox keeps it available. Never weigh it against `builtinDisabled`, which merges the trusted project's list: Always on writes the global `defaultTools`, so whether it is offered must not depend on the folder Settings was opened from; `readBuiltinExtensionSwitches()` therefore resolves the global list again on its own whenever a trusted project has a list (each switch's `global`), and a project-only `-builtin:codemode` keeps Always on available while the row and Tools lines report Code mode unavailable there. `/api/tools/settings` refusals carry a `reason` (`request-denied`, `content-type`, `invalid-request`, `internal`); the PowerShell UI reads only `error`. A project override is stated under the switch whether or not it agrees; the `autoEnableCodemode` warnings follow the effective choice (`mcpEffectiveCodemodePreference()`), while the switch and the sidebar row show the global choice they save.
- **Built-in tools** (`codemode.mode`: `on`, pi's default, or `only`) is the row between the choice and the budget, saved through `PUT /api/tools/settings { codemodeMode }`: `only` is written as itself, `on` removes the key (and a `codemode` object it leaves empty) and leaves an explicit `"on"` alone; a `codemode` that is not an object is refused for `only`. pi reads anything but `"only"` as `on`, so a value that is neither mode is reported (`invalid`), and choosing either option, the pressed one included (`mcpCodemodeModeChanges()`), replaces it. A trusted project decides it when the SDK's merge under a global `on` and `only` agrees (`projectCodemodeValue()`, shared with the budget), and the row names that file. Under an effective Automatic, `only` waits until an MCP server turns Code mode on, which the row says. The mode and the budget come from one read (`readCodemodeSettings()`), so a file that does not parse sets both `modeError` and `inlineBudgetError`. It shares `codemodeSave` (`target: "mode"`).
- **The tool list budget** (`codemode.inlineBudget`, pi's default 3000: the estimated tokens the codemode description spends declaring tools, shortest first) is the pane's second row, saved through `PUT /api/tools/settings { codemodeInlineBudget }`: a whole number from 0 to 1 000 000, or `null` to remove the key and a `codemode` object it leaves empty. `codemode.mode` is kept, and a `codemode` that is not an object is refused with the file untouched. GET reads it apart from the choice (`inlineBudgetError`), so a malformed `defaultTools` leaves it readable; a value pi ignores is reported as `invalid`. `CODEMODE_INLINE_BUDGET_DEFAULT` copies the SDK's unexported default, pinned by a contract test. A trusted project decides it when the SDK's merge under two different global budgets agrees (`projectCodemodeInlineBudget()`), and the pane names that file. Sessions read it when they start or reload. It shares `codemodeSave` with the choice (`target` picks the row), so the one-write-at-a-time rule covers it; while waiting the field is read-only, not disabled, so it keeps focus.
- **Trust from Settings.** AppShell owns trust: it passes its status for the folder Settings shows (`projectTrustCwd`, the cwd its dialog trusts) and `openProjectTrustDialog` through `SettingsPanel` to `McpConfig`. The untrusted notice offers Trust… only with that handler and while the panel's fresh status says `requiresTrust && !trusted` (`mcpProjectTrustable()`): not for an unreadable `trust.json`, nor an explicit `false` on a folder that requires no trust. Settings keeps every visited section mounted (hidden), so each section whose answer depends on trust takes the page's status and reloads **in place** when `projectTrustReloadKey()` (`components/settings-ui-helpers.ts`) changes: MCP its overview, Skills and Plugins their list, Agents its model list (`GET /api/models` leaves out an untrusted project's extensions); Models takes nothing (models.json, auth and `/api/models/enabled` do not follow trust). Never remount them on a trust `key`: they stay keyed on `cwd` alone, since a remount would drop pane state (a Code mode save, an install under way, a profile draft). The dialog renders after Settings in AppShell and stacks above it (`.project-trust-backdrop` z-index 1100 over 1000).
- **Escape stacking** (`lib/stacked-dialog.ts`). Settings closes on an Escape that reaches `document` in the bubble phase with `defaultPrevented` unset (`listenForPanelEscape()`). A dialog above it (`openStackedDialog()`) takes Escape on `document` in the **capture** phase, marks it handled and calls `stopPropagation()`, so one Escape closes only that dialog and no bubble-phase listener sees it; never gate Settings on a dialog-open flag instead. The window-level Stop shortcut (`handleGlobalEscape()`, `hooks/useKeyboardShortcuts.ts`) skips a `defaultPrevented` Escape, so closing Settings or a viewer never also stops a run. An Escape that cancels an IME composition (`isComposing`, or Safari's keyCode 229) closes nothing: the dialog stops it, Settings leaves it to the input method. The trust dialog ignores Escape while trusting, but still stops it. Where focus goes when a modal opens or closes, or its control disappears or is disabled, is documented on the module's helpers (`focusModalPanel()`, `focusIfLost()`, `focusAfterChange()`).
- **Strings and styles.** Keys picked at run time sit in literal maps in the helpers, so the translation test can find them. Every `.mcp-*` rule in `app/settings.css` must match a class McpConfig, McpSignIn or McpAddServer renders, and back (`MobilePwaLayout.test.mjs`).

## Settings › MCP writes (`lib/mcp-config-file.ts`, `POST /api/mcp`)
- **Every `mcp.json` write goes through `lib/mcp-config-file.ts`**, never the SDK's `add/update/removeMcpServerConfig()` (ADR 0006). Its output must equal theirs byte for byte (first indented line's indentation, always a trailing `\n`, `enabled: true` and `exposure: "codemode"` deleting their key, unknown keys kept; details in the module header), except that an edit changing nothing leaves the file alone; `lib/mcp-config-file.test.mjs` compares the bytes with the SDK editor's on every fixture and operation, so an SDK change fails it. Server names are read with `Object.hasOwn()` and written with `defineProperty`: `servers[name]` for `__proto__` is `Object.prototype`, and a patch would write `enabled` into every object in the process.
- **Lock, then atomic replace.** Writes to one real path queue on globalThis (`Symbol.for("pi-web:mcp-config-write-queue")`), then take a proper-lockfile lock on `<real path>.lock` (about 3 s of retries, then a typed `locked`) against other Pi Web processes; the pi CLI writes without a lock. The text goes to a temporary file beside the **real** file (created `wx`, 0600, then `chmod`ed to its final mode) and is renamed over the real path, so a reader (a host syncing before a prompt) sees the old file or the new one and a symbolic link stays a link (writing the configured path would replace a dotfiles link with a regular file). Modes: the **global** file always 0600 (it may hold literal secrets), a folder created for it 0700; the **project** file keeps its mode (`chmod`, not the umask), 0644 when new.
- **Where it writes.** Global: a link is followed wherever it leads, a dangling one by hand to the file it names, which the write creates. Project: the reader's link rule (`locateProjectMcpConfig()`, and `projectMcpConfigCreatePath()` for a new file): the real path, links in the file or `.pi/` included, must be inside the allowed roots, and a dangling link (file or `.pi`) is refused rather than taken for a missing file, or a cloned repository could aim the write anywhere. The file is read through `readResolvedConfigFile()` (`O_NOFOLLOW | O_NONBLOCK`, `fstat`, 1 MiB for the project). A refusal is an `McpConfigWriteError` (a `Symbol.for` brand, so a second module copy still counts) whose `reason` the route returns as 409, the file untouched: `unparsable` (never quoting the file), `invalid-shape`, `server-missing`, `name-taken`, `link-dangling`, `link-outside`, `not-a-file`, `too-large`, `locked`; `unreadable` is 500 `internal`.
- **`POST /api/mcp`** takes `enable` / `disable` / `remove` (`{ scope, name }`), `set-enabled` (`{ enabled, servers: [{ scope, name }] }`: one write per file, a `results` entry per server, so a refused one leaves the rest switched), `set-exposure` (`{ scope, name, exposure }`) and `undo` (`{ token }`), each with the panel's `cwd` when it has a project, and answers with the overview GET would give (plus `undo`, `restored` or `results`). Guards, in order: `isApiRequestAllowed` (403 `request-denied`), JSON content type (415), a JSON object (400 `invalid-request`), the cwd (`validateMcpProject()`, shared with Test, sign-in and `/api/project-trust`: `cwd-invalid` empty or relative, `cwd-denied` outside the allowed roots, with a `..` or missing, then `cwd-not-directory`), then **MCP off makes the server list read-only**: 409 `mcp-off` (`mcpInternalsOrRefusal()`, `lib/mcp-entry-request.ts`, shared with Test and sign-in) for `PI_WEB_DISABLE_MCP` or SDK modules that cannot load — **not** for `-builtin:mcp`, and never for the Code mode choice (the separate codemode built-in): whether a global switch works must not depend on the folder Settings shows. A project server needs the cwd (400) and a decision, exact or inherited, trusting the folder (403 `project-untrusted`; unreadable `trust.json` 409 `trust-unreadable`): `mayReadProjectConfigNow()`'s rule, never `trusted`. Turning on an entry that references `PI_WEB_PASSWORD` is 409 `web-password` (checked under the lock on the entry as it is then); off and Remove work. An entry that is not an object (`"name": "text"`, `null`, an array) cannot be switched: 409 `entry-not-object` (`setMcpServersEnabled()`'s `not-an-object`), never `server-missing`, which would say the file no longer defines it; Remove works, and the reader marks it `notAnObject` (its `enabled` reads true) so the panel offers no switch. The edit runs under the lock, so a server removed or renamed since the listing gets `server-missing`, never a stale write.
- **Exposure** is a dropdown in a validated server's Tools row (`MCP_EXPOSURE_OPTIONS`, the importer's `MCP_EXPOSURES`, which a test pins), a change like a switch (`busy` `exposure:<key>`, the switch's write block and note, focus back to the dropdown). `setMcpServerExposure()` writes it as the SDK's `updateMcpServerConfig({ exposure })` does: `codemode`, the default, removes the key, and `toolExposure` stays (GET counts its rules as `toolExposureCount`, which the row names). It connects nothing, so an entry that references `PI_WEB_PASSWORD` may change too and stays off. Open sessions apply it at their next message, when the host registers the changed entry again and the SDK reconnects the server: the TUI's `/mcp` changes exposure in place, but no public API does. The entry's status key changes with it, so the row reads untested until a Test or a session reports again. `mcpExposureReachNotice()` warns for the chosen exposure: Code mode's reasons for `codemode`, and `-builtin:tool-search` (GET's `toolSearchDisabled`) for `deferred`.
- **Undo** (`lib/mcp-undo.ts`). A removal holds the raw entry and its index in a globalThis map (`Symbol.for("pi-web:mcp-undo")`, at most 100) under a `randomUUID()` token for 60 s; the response carries `{ token, scope, name, path, expiresInMs }` (remaining time, so the browser's clock does not matter), never the entry, which may hold literal secrets. `undo` takes the record once (again: 410 `undo-unavailable`), re-checks a project's folder and trust as any write, and puts the entry back **where it stood** (`insertMcpServer()` with the index), byte for byte when nothing else changed. A name the file defines again is never replaced (409 `undo-name-taken`); a failed undo hands the record back for its remaining time. It restores the entry as it was, a `PI_WEB_PASSWORD` reference included. A server restart drops pending undos.
- **The panel's controls.** A server's detail header holds Remove and its switch (`ConfigDetailActions`), with a note both point at (`aria-describedby`): why they cannot be used (`mcp.reason.<block>` from `mcpWriteBlock()`: `mcp-off`, `project-untrusted`, `trust-unreadable`; `entry-not-object`; or `web-password` for such an entry's switch while off), or under `-builtin:mcp` (files still writable) that no session connects these servers. No note while the controls work: hosts read the files before every prompt, so a change applies at each open session's next message. The group switch ([settings-ui.md](settings-ui.md)) is described by the notice that blocks it. It never turns on an entry that references `PI_WEB_PASSWORD`, and no switch sends one that is not an object (`mcpGroupSwitchTargets()`); its `checked` is `mcpGroupSwitchChecked()`, never `enabled === total`, while the `n/m` count counts the file. Remove shows a notice with Undo until `expiresInMs` runs out.
- **One write at a time.** Every switch, Remove, Undo and Refresh wait while a change, a Code mode save or a load is on its way; both Code mode options wait while a server change is (its answer carries the Code mode choice read before the save). A change's answer drops a load still on its way, and any refusal or timeout loads the overview again (a timed-out change may have landed). The POST carries the cwd only when the listing covers the project: after a `cwd-*` refusal it would refuse global changes too. `postMcpAction()` shares the 15 s deadline.
- **Never exercise these writes against the live dev server or a real `~/.pi/agent`**: `app/api/mcp/route-write.test.mjs` runs every action against a `PI_CODING_AGENT_DIR` in a temp folder.
