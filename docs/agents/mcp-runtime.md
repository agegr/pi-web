# MCP in sessions

## MCP host (`lib/mcp-host.ts`)
- V3 subagents can use the same host with a frozen scope/name selection, never a parent's connection set. Scoped transport admission checks the actual live registration owner before value resolution; late closures stay bound to their original load. Delegated prompts use the wrapper's preparation/cancellation boundary. See [subagent-resources.md](subagent-resources.md) for the profile, source and aggregate-resource contract; normal sessions retain the default unscoped path.
- `createPiWebBuiltinExtensions()` returns `{ extensions, mcpHost }`; `startRpcSession()` passes the host to the wrapper. The host's inline extension reads the global and project `mcp.json` and registers servers with the SDK's MCP extension through `pi.registerMcpServer()`; the extension's own `loadConfig` stays empty (ADR 0006). The host stays inactive unless `/mcp` belongs to `builtin:mcp` (`isBuiltinMcpCommand()` in `lib/mcp-command.ts`, the composer's rule too): under `-builtin:mcp` or a third-party `/mcp`, another implementation would connect the servers through its own, unscrubbed transport.
- **Nothing connects until a prompt** (ADR 0006). Before a prompt sent while no run is going (`!inner.isStreaming`), the wrapper calls `prepareForPrompt()`: the host re-registers only entries whose canonical JSON changed, then waits up to 10 s for servers with `direct` tools (the server's `exposure` or any `toolExposure` entry, `ConnectAttempt.declaresTools`, the SDK's `hasDirectTools()`) still connecting; one that outlasts a full wait is not waited for again. Other servers connect in the background, as in pi 1.0: their tools are in no request, the SDK's extension activates `codemode` / `tool_search` from the config before they connect, and its `tool_call` handler waits (abortably) for the servers a codemode script names or searches, or for all of them when `tool_search` runs. The extension is created with `startupWaitMs: 0`: its own first-prompt wait for `direct` servers ignores Stop, and since pi 1.0 it covers servers registered right before the prompt. `before_agent_start` also syncs, without waiting, for prompts that bypass the wrapper. pi runs an extension command at the start of `prompt()` and starts no run, so `mcpPromptPreparation()` matches the message against the session's extension commands by invocation name: another extension's command skips MCP; the built-in `/mcp` registers without waiting (`{ wait: false }`). Never skip the built-in `/mcp`: it acts only on registered servers (`/mcp login docs` as a first message would answer "No MCP server named").
- **Stop during that wait** rejects the prompt unsent with `MCP_WAIT_STOPPED_MESSAGE`, so the client restores the draft. Never move the wait into `before_agent_start`: pi emits it before the run has an abort signal, and `AgentSession.abort()` does nothing until a run is active. `abort` waits for the withdrawn prompt to unwind before it checks `isRunning()`.
- **Connection state comes from the transports**; the extension reports none. `wrapTransportFactory()` wraps pi-web's factory; `watchTransport()` adds listeners and own `start` / `send` / `close` on each transport instance, never a wrapper object (the SDK checks `instanceof StdioTransport`). Ready (`watchConnection()`) means the extension has registered the server's tools. A transport that closes first, or a factory that throws (a `PI_WEB_PASSWORD` reference), is failed. Every transport of a registration is followed (an HTTP retry, the reconnect after a drop, the extension's `turn_start` reconnect once tokens were stored elsewhere): the latest speaks for the server (`attempt.current`), an older one closing late is ignored. The first outcome settles the attempt, all a prompt waits for; a failed server whose entry is unchanged is never retried (ADR 0006), only the extension's own reconnects change its state.
- **What a session sees goes to Settings** (`lib/mcp-status.ts`): each change of an attempt writes `{ origin: "session", state, sessionId, cwd, updatedAt, error?, stderr?, conflict?, closedAt? }` under `scope\0sourcePath\0name` with `mcpConfigKey()` (`lib/mcp-config-key.ts`) of the entry as `loadMcpConfig()` returned it (the validator's copy, aliases resolved, which GET keys by too through `mcpEntryConfigKey()`), never of the registered config, which `withReachableExposure()` may rewrite. Latest write for the same content wins, a test's or any session's; a session behind an edit writes under the old key (see **Status store** in [mcp-test-sign-in.md](mcp-test-sign-in.md)). States:
  - `connecting` (a transport opened), `connected`.
  - `needs-auth`: by the rejected error's name, as the SDK's `needsSignIn()` decides: `McpOAuthAuthorizationRequiredError`, or `McpAuthRequiredError` when the factory got an auth provider (its third argument, given exactly for an OAuth server; an `Authorization`-header server's 401 is a plain failure). Also when a later request asks for a sign-in.
  - `disconnected`: a ready transport closed with nobody calling its `close()` (a stdio server exited). A client close (reconnect, `/mcp logout`, a reload, whose closes finish before the host's `session_shutdown`) is not a drop. The host cannot see the connection, so after `/mcp logout` in a chat the record keeps its state until a connection asks for a sign-in.
  - `failed`: the first error `start` / `send` rejected with or the server's error answer to `initialize`, else "The connection closed before the server was ready", plus the stdio stderr tail. Both go through the Test's redactor (`createTestRedactor()` with that transport, for resolved values), then `maskStatusError()` / `maskStatusStderr()`: masked, then shortened (a printed literal env value is `•••`).
  - `conflict`: `pi.registerMcpServer()` refused; owner from `pi.getMcpServers()`, else the SDK's words (`already registered by extension "<path>"`). `serverStates()` keeps `not-registered` and adds `conflict`.
  - `not-trusted`: at most `MCP_UNTRUSTED_REPORT_MAX` (100) per sync, the rest logged as a count (each is a record in the shared 500-record store).
  - Problems (`conflict`, `not-trusted`, a refused registration) recur at every sync, so each is written only when it changed or its record was replaced since.
- **Letting go.** `letGo()` (unregister, idle release, session end, a reload's dispose) stops recording an attempt before the extension closes it, and amends the attempt's own record while nobody wrote another (`forgetMcpStatus()` / `replaceMcpStatus()` compare by identity): `connecting` is forgotten, `connected` gets `closedAt` (Settings shows `on`, "connected it at … and closed it at …"); `failed`, `needs-auth`, `disconnected` stay. A let-go attempt still settles, for a waiting prompt. Dispose also forgets the host's still-own problem and host-inactive records.
- **The wrapper disposes the host when it starts closing** (`McpHost.dispose()`, once, from `shutdown()` after extension binding and from `destroy()`), before any extension hears `session_shutdown`: handlers run in order, the host's last, and an MCP close may never return (a stdio grandchild holding stdout, an OAuth refresh), which would leave records for a gone session. The host's own `session_shutdown` only repeats it; a disposed host ignores a late `session_start`.
- **A `/mcp` the host does not own**: at `session_start`, another extension's `mcp` command records `{ owner, cwd, updatedAt }` under the session id (`recordMcpHostInactive()`, at most 100), forgotten at dispose or when a reload starts with Pi's own. Several extensions' `/mcp` (renamed `mcp:1`, `mcp:2`, …; the built-in is dropped) name the first; a prompt template named `mcp` is nobody's (`isMcpExtensionCommand()`). `-builtin:mcp` leaves no `/mcp`; Settings reads it from the files. GET reports the record for the panel's cwd, else the latest, as `hostInactive`.
- `lib/mcp-host.integration.test.mjs` pins through a real session the SDK behavior the states rest on (error names, reconnect after a sign-in, conflict wording); `lib/mcp-host.test.mjs`'s trust fixture checks the host's key agrees with `readMcpOverview()`'s.
- **Never unregister a server before its transport exists** (ADR 0006): the extension assigns `server.connection` only after loading the MCP runtime, and its removal closes only an assigned connection: unregistered earlier, the server still connects, out of reach. The host waits up to `replaceWaitMs` (5 s); once the transport exists, `close()` is safe even mid-handshake. A plain `mcp_servers_change` does not move the extension's `generation`, so the cap alone is no guarantee: a registration unregistered without a transport is counted (`abandoned`, by `name\0configKey`) and the factory refuses the next transport asked for it while no live registration claims it (`refuseAbandoned()`): nothing starts.
- **Idle release.** A host that has not run for `PI_WEB_MCP_IDLE_MS` (10 minutes; `0` disables) unregisters its servers unless `ctx.isIdle()` says a run is going; the next prompt registers them again. The timer stops from `agent_start` to `agent_end` and while a prompt waits in `prepareForPrompt()`, and restarts at `agent_end`, when `prepareForPrompt()` returns, and after every sync. Never rely on `agent_end` alone: a prompt that registers servers and starts no run (Stop during the wait, a slash command, a rejected preflight) never emits it, and a sync Stop gave up on still finishes later. A reload binds a new host instance with nothing registered.
- MCP tools register as `mcp__<server>__<tool>`, sanitized to `[A-Za-z0-9_]` (pi 1.0, like Codex: `-` becomes `_`, so `mcp__my-server__x` is `mcp__my_server__x`) and hashed past 64 characters or when another tool has the name, so a name cannot be split back (`docs.v2/search.pages` and `docs_v2/search_pages` sanitize alike; either part may hold `__`). Server names that differ only in `-` and `_` share a namespace: `loadMcpConfig()` skips the later one, and Settings lists it as refused. A tool card reads `server/tool` only from its result's details (`{ server, tool }`); a running call, the status line and codemode script calls show the registered name, which scripts call.
- Project `.pi/mcp.json` entries follow project trust, inherited included, as in the pi CLI: `loadMcpConfig` reads the file only when told the project is trusted, and every entry it returns connects; no per-entry approval (ADR 0006). A project entry replaces a global one of its name. Without a working codemode sandbox, `codemode`-exposure servers register as `deferred` (reached through `tool_search`).
- **Trust is read fresh on every sync** through the `mayReadProjectConfig(cwd)` option (default `mayReadProjectConfigNow()`, `lib/project-trust.ts`), never `ctx.isProjectTrusted()`, which is fixed until reload (ADR 0006). It is true only while a decision, exact or inherited, trusts a folder that requires trust — never `getProjectTrustStatus().trusted`, which is true for a folder with no trust-requiring resources: `loadMcpConfig` looks at the folder again, and a file landing in between would be read undecided. A decision made anywhere (the CLI too) reaches open sessions' MCP servers at their next prompt; their project extensions and `autoEnableCodemode` (read by the extension's `loadConfig` only on `session_start`) follow it only at reload (`/api/project-trust` rebuilds the cwd's wrappers). Each read, twice per prompt (`before_agent_start`, `prepareForPrompt()`), costs the SDK's `hasTrustRequiringProjectResources()` and, where trust is required, a `lockSync` and read of `trust.json`. An unparsable or still-locked `trust.json` (after the store's ~200 ms synchronous wait, which blocks the event loop) fails closed — connected project servers are unregistered until a read succeeds — with one warning per distinct error.
- **An untrusted project file** still has its names reported as `not-trusted` by `serverStates()` (at most `MCP_UNTRUSTED_REPORT_MAX`; keyed by scope and name, since a global entry may share one), read after `loadMcpConfig` so a file that just landed is reported. `untrustedProjectServerEntries()` parses only a regular file of at most 1 MiB whose real path is inside the project, opened once with `O_NOFOLLOW | O_NONBLOCK` and checked through `fstat` (a link elsewhere refused, a FIFO or device never read); entry values are only hashed into the status key.
- `loadMcpConfig()` hands over the validator's copy of each entry, with exposure aliases resolved (`codemode-deferred` → `codemode`), and the host keys statuses by it; Settings keys an entry the same way (`mcpEntryConfigKey()`), and the host keys an untrusted project's entries with the validator too.
- `loadMcpConfig()`'s `errors[]` are logged once per process each, at most 20 per sync plus a count (`logConfigErrorOnce()`). V8 quotes up to ten characters around an unexpected token, often a literal secret, in the SDK's `${path}: ${error.message}`, so `scrubMcpLoadError()` (`lib/mcp-json-error.ts`) rewords it through `jsonErrorMessage()` before logging, as the panel does.

## `/mcp` in the composer (`lib/mcp-command.ts`, `hooks/useAgentSession.ts`)
- **Only a bare `/mcp`, and only when pi's built-in owns it** (ADR 0006). `handleBuiltinSlashCommand` opens Settings › MCP (`onOpenSettings("mcp")`, AppShell → ChatWindow → the hook, like `/session`'s panel) when `bareMcpOpensSettings()`: the command list has the built-in `/mcp` (name `mcp`, `sourceInfo.path` `builtin:mcp`) or nothing named `mcp` (MCP off, `-builtin:mcp`, Chat-only, or several extensions' `mcp:1`, `mcp:2`, which pi looks up by exact name, so a bare `/mcp` would reach the model as text). Another extension's `/mcp` (the SDK then drops the replaceable built-in), a prompt template named `mcp` (expanded when no extension command has the name) and every subcommand (`login`, `logout`, `reconnect` act on the session's own connections) are sent. A third-party input handler that catches `/mcp` cannot be seen from the list.
- **Never guess the owner.** The palette starts `get_commands` as `/mcp` is typed, often unanswered at Enter, so the case awaits the request under way (`slashCommandsLoadRef`), else uses the loaded list (`slashCommandsRef`, written only through `replaceSlashCommands()`), else asks. Every request and set_tools' `clearSlashCommands()` (which also forgets the request under way) move `slashCommandsGenerationRef` on, and only a current request writes its answer, or one set_tools outdated would restore the replaced session's stale `/mcp`. A failed request is `null`, never `[]`: an empty list is a Chat-only session's and opens Settings; an unreadable one sends `/mcp`. Guessing would swallow another extension's `/mcp` or spend the host's 10 s wait on a message Settings should take.
- **Nothing of a prompt happens.** The case returns before `onSend`: no `/mcp` bubble, no `promoteNewSession()` sidebar row in a new chat (the command list still needs the session `ensureNewSession()` builds), and `complete()` shows no notice for an `action` (`openSessionStats`, `openSettings`). While a run streams, `sendQueued` offers a bare `/mcp` to the handler first and queues it as a steer / follow-up only when unhandled, and `handleSend` lets it through (`offersBuiltinSlashCommandWhileStreaming()`); `canRunBuiltinSlashCommandWhileStreaming()` lists only the composer's own built-ins. Enter on the palette's built-in `/mcp` submits at once (`submitsSlashCommandOnEnter()`); other extension commands complete to `/name ` first; `isExactSlashCommand()` matches built-ins only.
- **Focus moves into Settings** (`focusModalPanel()` from a layout effect in `SettingsPanel`): to the dialog element (`tabIndex={-1}`, no outline), back to the opener on close unless focus went elsewhere, never refocusing a text field on a coarse pointer (it would raise the keyboard). Otherwise the composer behind the modal keeps the keys: Escape reaches ChatInput first and stops a running agent instead of closing Settings, and a phone keeps its keyboard up.
- `lib/builtin-extensions.integration.test.mjs` pins the SDK facts this rests on (the built-in's path, its replacement, `mcp:1` / `mcp:2`, a bare `/mcp` reaching the model as text beside two) through a real wrapper; if it fails after an SDK upgrade, revisit `bareMcpOpensSettings()`, `isMcpExtensionCommand()` and `mcpPromptPreparation()`.
