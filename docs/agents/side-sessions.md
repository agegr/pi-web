# Side sessions

Why it is built this way: [ADR 0007](../adr/0007-side-sessions.md).

## Creation

- `/side` and `/side <prompt>` are client-side built-ins (`BUILTIN_SLASH_COMMANDS`, `case "side"` in `hooks/useAgentSession.ts`) with `availableWhileStreaming`: nothing reaches the model, no bubble. They post `{ side: true }` to `POST /api/sessions/[id]/fork`. The prompt is stashed per session id (`sideChatPrompts` in `AppShell`) and sent by the tab's `ChatWindow` as `initialPrompt`, once.
- While a run streams, the composer's Side chat icon left of Steer and Follow-up sends the draft the same way; it does not take images, as `/side` does not. A composer narrower than 480px (a panel open beside it) shows those two as icons as well, by a container query, so the draft keeps the width; a phone stacks them in their own row instead. The main agent's row in the Agents switcher has New side chat, which forks that session whichever family member the main chat shows, and answers refusals in the panel. The Agents button is always in the toolbar for this, with no badge while the family has no other member, and greyed on a fresh composer.
- The selected-text popover (Settings › General, off by default) is another way in: "Quote" puts the selection into the composer as a Markdown blockquote and a blank line, nothing else, so the same action serves a question, a correction or an instruction (#1373); `insertQuote()` starts it on a paragraph of its own, since a quote after text on the same line is no blockquote. "Ask in side chat" opens its small composer with the same quote and sends through the same `startSideChat()` (`hooks/useAgentSession.ts`). The file is copied on send, so abandoning it leaves nothing. It takes the selected text as the name (`{ side: true, name }`), not the first message's first line, which is the quote's line wrapped in `> `. A tab offers only "Quote", since a side chat does not nest. This replaced "Ask in new chat", which forked at the selected message and moved the main chat away; a branch to keep working on is the message's New session or the sidebar's Fork.
- `createSideSession()` (`lib/session-fork.ts`) is `forkSessionBranch()`'s copy with another name and one more step: the `pi-web:side` entry is written as the file's second line and the first copied entry is chained under it, because `readSessionRelationEntries()` reads only the first lines, and the boundary message is written last, as the leaf. Just before it goes the parent's tool pin: `readSessionToolSelection()` reads the whole file, so a pin set on another branch binds the parent but would not be in the copy, and the side chat would fall back to the branch's wider loadout (Read-only parent, `bash`; Chat-only parent, out of the Chat-only path). A shell-only branch works as it does for Fork. Refusals are `SessionForkError`'s; the client maps the codes to notices.
- A copy taken mid-run holds what is on disk: finished entries, so it can end on an unanswered prompt or on tool calls with no result (pi-ai sends "No result provided"). The parent's later turns never appear.

## Tools and prompt

- `startRpcSession()` treats a side chat as a normal session, or as Chat only when the parent's pin is empty. `sideToolNames()` gives its tools: the pin, else the loadout recorded in the transcript's system messages, else `read` and `bash`, cut down to `SIDE_TOOLS`. **That result is pi's `tools` allow-list, not `SIDE_TOOLS` itself**: `tools` overrides what pi restores from the transcript and registers and activates every listed tool, so a wider list gave a Read-only parent `bash` and showed tools the parent never had in the Tools panel. It also keeps extension, MCP, Code mode and subagent tools out of the registry. `resolveShellTools()` applies the PowerShell switch to it.
- pi-web's built-in extensions are not created, so no MCP server connects. Other extensions, skills and context files load as usual, so the extension's prompt additions and provider models stay.
- `navigateTree()` and `set_tools` cannot bring a tool back: the allow-list holds for the session's life, and `setRpcSessionTools()` refuses by metadata. Metadata that does not parse is refused by `startRpcSession()`.
- The prompt is the parent's. pi turns the tool change into one `role: "system"` message in the transcript before the first side message; Anthropic's request places it after that message (a system message must follow a user turn), OpenAI's before.
- **The boundary is a message, not a prompt section.** `SIDE_BOUNDARY_TEXT` is a `custom_message` with `display: false`: pi's `convertToLlm` sends it as a user turn, in place, on every provider, so it says it is not the user speaking. An addendum in the prompt told the model about "the first side-chat message" with nothing marking it: on models without mid-conversation updates it folds into the head, and a fork taken mid-run reads as two user messages in a row. Compaction serializes it like any user message (`[User]: [Side chat] …`), and "Edit from here" above it leaves a branch without it.

## Panel and switcher

- `components/SessionChatPanel.tsx` renders a side chat's or subagent's tab, tab id `agent:<sessionId>`: `ChatWindow` with `panel`, which leaves the global Esc to the main chat. Only the active tab is mounted. Side tabs and the active side tab are kept per main session in this browser tab's sessionStorage; switching sessions shows only that main session's tabs, and returning to it or reloading restores them once the session catalogue is loaded. A session without side tabs keeps no entry. A fork that returns after the main chat moved to another session is added to its parent's saved tabs, not opened beside the session now shown (`appendSideTab()`). Deleted side chats are discarded; subagent tabs remain open across session switches in the same project, but still drop on project switches and reloads. The Agents switcher can still reopen a closed tab.
- An extension's `ctx.shutdown()` in a side chat closes that session's tab through `onSessionEnded`, without changing the main chat.
- Rows work as subagent rows do: a click opens the side chat in the main chat (the URL holds it, a reload keeps it, the sidebar highlights the parent's row, the "Main agent" row goes back), the button toggles the tab. Search skips side chats. `isHiddenRelation()` is the one test for "a family member, not a sidebar row": unread, notifications, the sound and the tool preset control follow it.
- A side chat's row also has Delete: the sidebar's confirmation (`DeleteConfirm` from `SessionTree`, its `.session-tree-confirm-*` rules unscoped for it), then `DELETE /api/sessions/[id]` removes just that file (a run stops with its wrapper) and closes its `agent:<id>` tab. When the main chat shows it, the main chat goes back to the parent, as the Main agent row does, not to a fresh composer. The parent and its other members stay; deleting the parent still takes every side chat with it (`deleteSessions()` folds side chats into the parent's children like subagents).
- A tab acts as the main chat does on what leaves it: bare `/mcp` opens Settings › MCP, and `/clone` or a message's New session opens the copy in the main chat. Without these callbacks `/mcp` went to the model as text and the copy appeared nowhere.
- One session, one chat: two windows would share a draft key and stream the same run twice. An effect in `AppShell` closes the tab of whatever the main chat shows, and that row's tab button is greyed, not removed, so the rows keep their layout. Every row's actions sit on the right (`RowSideButton`): the main agent's is New side chat, which stays enabled when selected, and a side chat's are its tab toggle and Delete.
- `renderMessage()` in `ChatWindow` draws the boundary message as the line (`SIDE_BOUNDARY_MESSAGE_TYPE`, client-safe in `lib/session-family.ts`). If it is not loaded (an older page) or compacted away, there is no line.
- Names: `createSideSession()` starts with `SIDE_SESSION_NAME`, and the first prompt replaces it with its first line (`sideChatNameFrom()`, the wrapper's `prompt` command; commands name nothing), which `/name` can change. Rows and tabs show it through `sideChatTitle()` with the same family list: unnamed side chats are numbered in creation order (`Side chat 1`, `Side chat 2`), whether their tabs are open or not. `AppShell` rereads the list when a run in an open side tab starts or ends; opening or closing other tabs does not change the numbering.
- `POST /api/sessions/stats` and the toolbar's totals (`GET /api/sessions/[id]`) count `sideOwnEntries()`, what a side chat added after `createdAt`. `/session` in the main chat shows pi's own `getSessionStats()`, the whole file; a tab has no stats popover, so it answers with one line of the chat's own numbers (`formatSessionSummary()`).
