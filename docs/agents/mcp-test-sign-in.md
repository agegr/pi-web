# Settings › MCP: Test and sign-in

## Settings › MCP Test (`lib/mcp-test.ts`, `POST /api/mcp/test`)
- **The route re-checks what a session's start would** (`readConnectableMcpEntry()` in `lib/mcp-entry-request.ts`, shared with sign-in), since Test spawns a process or contacts a URL and may run a `!command`: origin (403 `request-denied`), JSON (415), `{ scope, name }` (400 `invalid-request`), the cwd as GET checks it (`cwd-*`; required for a project server), MCP off (409 `mcp-off`: `PI_WEB_DISABLE_MCP` or SDK modules that cannot load; not `-builtin:mcp`), and for a project server a decision, exact or inherited, that trusts the folder (403 `project-untrusted`, 409 `trust-unreadable`; `mayReadProjectConfigNow()`'s rule, never `trusted`). The entry comes from its file (`readMcpServerEntry()`, the listing's parse and link rule: a file problem is its 409, an absent name `server-missing`, `__proto__` just a name), never from the browser, and must be an object (409 `entry-not-object`), pass `validateMcpServerConfig()` and what `loadMcpConfig()` refuses beyond it (409 `server-invalid`: a name another entry's namespace has, `auth` in a project file) and not reference `PI_WEB_PASSWORD` (409 `web-password`). A switched-off entry can be tested. A global stdio server runs in the request's project (checked like any cwd), else `homedir()`; that folder is also its MCP root, and the result names it.
- **It connects as a session does**: the SDK's `McpServerConnection` through `createPiWebMcpTransportFactory()` (scrubbed env, `inheritEnv: false`), every transport captured, and the SDK's `McpOAuthCredentialStore` (`mcp-auth.json`, created as a session would), guarded for an OAuth entry (see sign-out below). An entry with `auth.provider` gets that pi provider's token as a session's extension reads it (`ModelRegistry.getApiKeyForProvider()` over `createModelRuntimeWithExtensions()`, built at the first request that asks). A 401 with no stored token reads `needs-auth`.
- **Bounded; an answer never waits on a close.** Each request gets min(the entry's `timeout`, 15 s) (`MCP_TEST_REQUEST_TIMEOUT_MS`; SDK default 60 s). The test has a 20 s deadline (`MCP_TEST_DEADLINE_MS`), aborted early once every caller's request signal has (refcounted across joined presses). On abort, call `connection.close()` and also close the captured transports: `close()` alone leaves a stdio child running until its request times out. Await closing at most `MCP_TEST_CLOSE_WAIT_MS` (2 s): a stdio close waits for the child's `close` event, which a grandchild outside the process group can hold off forever, and `connection.close()` waits for an OAuth refresh. The SDK's `connectOnce()` awaits `client.close()` inside a failed attempt, so a SIGTERM-ignoring server's plain failure takes up to the 2.5 s SIGKILL; the deadline covers that. Read `connection.state` before closing (`close()` sets `closed`), and close in a `finally`. Tool fields are untrusted: pi-mcp checks only `name` and `inputSchema` (`describeTool()` reads the rest only as strings), and the SDK's `getMcpToolExposure()` indexes `toolExposure` plainly (`toolExposure()` passes a prototype-free copy).
- **`!command` entries run one at a time.** A `!command` runs synchronously (`execSync`, up to 10 s), blocking the event loop and every timer. Tests of entries that resolve one (`runsShellCommand()`: a stdio entry's env, an HTTP entry's headers and `oauth.clientSecret`; env on HTTP runs nothing) queue in a globalThis chain (`Symbol.for("pi-web:mcp-test-command-queue")`) for at most the deadline again; one never given its turn answers `queueTimedOut` and is not recorded. Giving up a place releases it at once without letting the next jump the ones ahead. Presses on the same entry (scope, file, name, `configKey`, cwd, the server's sign-out count) join the running test (`Symbol.for("pi-web:mcp-test-flights")`); one every caller gave up on leaves that map at once, so the next press starts afresh.
- **Nothing literal reaches the browser.** The SDK quotes a failed `!command` (`… from shell command: <text>`) and a server may echo its env, key or URL, so `createTestRedactor()` masks all server-written text (`error`, `stderr`, tool names and descriptions, `serverInfo`): the `!command` text (at any length after `from shell command: `, elsewhere as a word of 6+ characters; the SDK discards its stderr); literal env / header / `oauth.clientSecret` values and what the transports resolved them to (the entry's own env names only, not the host's sanitized env); command, arguments and URL as GET masks them, the parts those masks hide when quoted alone (`urlSecretParts()` / `argSecretParts()` / `commandSecretParts()` in `lib/mcp-secrets.ts`, also percent-decoded), and the URL as `new URL().href` spells it. Values under 6 characters stay. A whole secret is replaced anywhere; a word split from a value (`Bearer <token>`) or command text only as a whole word. **Mask, then shorten:** mask over a 64 KiB window, then keep `error`'s first 2,000 characters and `stderr`'s last 2,000, so no cut leaves half a secret and no 16 MiB JSON-RPC error sits in the status store sent with every GET. `splitStderr()` moves the stderr tail the SDK appends to its message into `stderr`.
- **Status store** (`lib/mcp-status.ts`, `Symbol.for("pi-web:mcp-status:by-config")`): a test records `{ origin: "test", ...result }` under `scope\0sourcePath\0name` and the entry's `configKey` (`mcpConfigKey()`, the HMAC GET reports), unless every caller gave up first. One record per `configKey`, never per entry, so a writer behind the file (a session that has not synced an edit) never replaces the current content's record. `readMcpOverview()` attaches the matching record and deletes the entry's others (an edited entry reads untested, even edited back), and prunes names a file read without a blocking problem no longer defines; at most 500 records, least recently written first out. Session hosts (**MCP host** in [mcp-runtime.md](mcp-runtime.md)) and sign-ins write too; the latest write for the same content wins. A globalThis store whose shape changes needs a new symbol name: a dev server keeps `globalThis` across hot reloads.
- **The panel.** The **Connection** row under Status shows the last status (a timeout as "No answer": Pi Web stopped the test, for HTTP only its wait), server info, resources and a stdio server's folder; a connected test adds a read-only **Listed tools** row (a `read-only` tag for `readOnlyHint`, what read-only sessions require; the exposure where `toolExposure` differs). Why Test (`McpTestButton`) is disabled is visible text it points at (`aria-describedby`; `mcpTestBlock()`: `mcp-off` / `project-untrusted` / `trust-unreadable`, then `invalid`, `web-password`); a `!command` entry says its tests queue. A test writes no file and never sets `busy`: switches, Remove, Refresh and other servers' tests run beside it. Each answer is kept per server (`McpTestRun`) and shown over the listing's status while its `configKey` matches and it is newer (`mcpWithTestResults()`), so an in-flight load cannot hide it. A Sign out that worked drops the kept answer and any answer to a test started before it (`mcpTestRunAfterSignOut()`), or it would read Connected. A failed request or queue timeout keeps the last result beside a `role="alert"` line in a test's words (`MCP_TEST_REFUSAL_KEYS`; `mcp.reason.*` speaks of writes), hidden once the entry is edited (`mcpTestRunFor()`). Any refusal with a reason, or an answer for another `configKey` than listed, reloads the listing (`mcpTestAnswerOutdates()`).
- **Test requests are never aborted**, neither on closing Settings nor at the client's 60 s wait (`MCP_TEST_TIMEOUT_MS`, `withinDeadline(…, { abortAtDeadline: false })`): Next aborts `req.signal` with the request, and the route then stops the test and records nothing. Only closing the page stops one. Test takes focus back once answered (`focusIfLost()`).
- Testing: run routes against a temp `PI_CODING_AGENT_DIR` (and a temp `HOME`, with `PI_WEB_PASSWORD` set to check its absence from the child's env). A hanging fixture must exit by itself once re-parented or after 30 s (`lib/__fixtures__/mcp-hang-server.mjs`).

## Settings › MCP sign-in (`lib/mcp-sign-in.ts`, `/api/mcp/sign-in`)
- **It runs as `pi mcp login` does** (SDK `extensions/mcp/cli.js` login()) on one connection opened like a Test's (`openTestConnection()` / `observeTestConnection()` / `closeTestConnection()`, kept open): connect to learn whether a sign-in is needed and record the challenge (connected ends `done`, `alreadySignedIn`; another failure `failed`, `connect-failed`); then the SDK's `signInMcpServer()` with `connection.oauthSettings()` (resolved while holding the entry's `!command` queue place: `oauth.clientSecret` may be one), the challenge and a prompt; then `connection.reconnect()`. Each connect gets the test deadline once its queue turn comes, never across the wait for the browser. Only an HTTP entry without an `Authorization` header signs in (`mcpOAuthUrl()`, the SDK's `usesOAuth` rule, pinned against `connection.oauthUrl` in `lib/mcp-sign-in.integration.test.mjs`), else 409 `sign-in-not-oauth`.
- **The flow outlives every request** (ADR 0006): `POST /api/mcp/sign-in` runs the Test's checks, starts the flow and answers at once; the panel polls `GET /api/mcp/sign-in/[flowId]` about once a second. Flows live in a globalThis registry (`Symbol.for("pi-web:mcp-sign-in")`, `randomUUID()` ids, unref'd timers), tied to no request signal or stream (unlike the provider login route, which aborts on SSE close); Sign in again joins.
- **One flow per server per process** (keyed `mcpSignInKey(name, url)`, `mcp__<name>|<URL>` with `-` as `_`, as pi 1.0's `mcp-auth.json` keys it): the SDK keeps one PKCE verifier and one `state` per server, so two sign-ins of a server both fail (`invalid_grant`), while servers sharing a URL keep separate accounts. A second start joins (`joined: true`): the same name at the same URL, so the global and the project entry of a name; the reconnect's result is recorded only for the entry that started it, so a joining row names that entry and points to Test connection (`mcpSignInShared()`, `mcp.signIn.shared.*`). A flow whose server's previous run is still unwinding waits for it. A terminal `pi mcp login` is not serialized against.
- **Five minutes; the SDK cannot be aborted.** `signInMcpServer()` takes no AbortSignal and its loopback callback gives up after 5 minutes (pi-mcp `OAuthCallbackServer`), so a flow expires first, `MCP_SIGN_IN_TTL_MS` (5 min) after it starts; one already `finishing` gets `MCP_SIGN_IN_FINISH_GRACE_MS` (60 s) once. The only stop is answering `promptForRedirectUrl()` with "" (McpSignInCancelledError): a cancel or expiry answers a waiting prompt at once, else the prompt when it comes; before `signInMcpServer()` is called it stops the run there. An ended flow stays readable `MCP_SIGN_IN_KEEP_MS` (60 s), then 404 `sign-in-unknown`. Discovery, registration and token requests have no timeout of their own, so a run can outlive its flow without changing it.
- **A pasted address is checked first** (the SDK ends the whole sign-in on a bad one): `pasteMcpSignInRedirect()` answers 400 and keeps waiting for a non-URL (`redirect-invalid`), another `state` (`redirect-state-mismatch`, against the `state` the SDK last stored, watched through the store it was given; the page's only as fallback), an `error=` answer (`redirect-denied`, description as `error`) or no `code` (`redirect-no-code`); a paste while nothing waits is 409 `sign-in-not-waiting`. The loopback callback needs no paste: the SDK aborts the prompt's signal, moving the flow to `finishing`.
- A stored refresh token can finish a sign-in with no page (`refreshed`). Starting may drop the stored client registration and tokens (the SDK drops one whose redirect URI differs); the panel says so beside the button.
- **What it records**: the first connect's result as a Test's (`needs-auth` while the browser is awaited), the reconnect's with `afterSignIn: true` (worded by `MCP_SIGN_IN_SUMMARY_KEYS`). An open session's own record stays `needs-auth` until its next turn reconnects. Errors go through the test redactor plus the resolved client secret (`createTestRedactor(…, resolvedSecrets)`). Right before the reconnect, possibly minutes later, the route's `mayConnect()` re-checks a project entry's trust and MCP off; if either fails, the flow ends `done` unconnected.
- **Sign out** (`POST /api/mcp { action: "sign-out", scope, name }`): the URL comes from the entry's file under any change's checks (project trust included); the SDK store's `remove(name, url)` deletes its tokens and client registration, or the legacy record kept by URL alone when it has none of its own (`pi mcp logout`), never creating a missing `mcp-auth.json`; the entry's statuses are forgotten (`forgetMcpEntryStatuses()`). Sessions read the store per request and lose access at their next one (a refresh already in flight there can still write back, as with `pi mcp logout`). Answer: the overview plus `signedOut: { scope, name, removed }`.
- **Sign-out bars every earlier run of the server from writing, before removing anything.** A cancel only answers a waiting prompt, while a code exchange or refresh already in flight (the sign-in's or the connection's) would store tokens right after the removal, and its requests have no timeout to wait out. So `signOutMcpServer()` counts a sign-out for the sign-in key (`noteMcpSignOut()` in `lib/mcp-sign-out.ts`, `Symbol.for("pi-web:mcp-sign-outs")`), cancels the flow, then removes. Runs write `mcp-auth.json` only through stores that call their `McpSignInWriteGuard` before each write (`watchedStore()` for the SDK sign-in, `guardedCredentialStore()` passed to `openTestConnection({ credentials })` for the connection), which throws `McpSignedOutError` once the count moved since the run started; the SDK writes synchronously, so no removal fits between. **Tests count**: an OAuth entry's test takes its guard at start (`mcpSignOutGuard()`), so its in-flight refresh stores nothing and its result is not recorded; the sign-out count is in the flight key.
- **The panel** (`components/McpSignIn.tsx`): the signed-in hint (`signedIn`, an access token); Sign out unless nothing is stored (`oauthStateStored`: the record the server reads, its own or the URL's legacy one, incl. a cancelled sign-in's registration and PKCE state); while a flow runs, its phase (`role="status"`) and Cancel, disabled in `finishing` (the authorization server answered) with a visible reason. Sign in waits for the row's in-flight Sign out, which would cancel it. In `authorize`, `OAuthPastePanel` is always shown, with the page as a link (only `http(s)`: it comes from server metadata), the return address and the 5-minute limit; the box is never auto-focused (a phone keyboard would cover the link), has an accessible name, waits while a paste is checked, and submits by button or Cmd/Ctrl+Enter, never plain Enter (`plainEnterSubmits={false}`; Models' subscription box keeps it) nor mid-IME (`oauthPasteKeySubmits()`). Disabled buttons point at visible reasons (`mcpSignInBlock()`, the Test's; `mcpSignOutBlock()`, the write blocks and a refused entry). Needs-sign-in words never send the user to `/mcp` in a chat. "Signing in may replace what is stored" shows only while something is (`offersSignOut`). A sign-in writes no `mcp.json` and runs beside changes; Sign out goes through `runAction()` (`sign-out:<key>`). A polled flow's end (`mcpSignInJustEnded()`) reloads the overview and clears a failed cancel's or refused paste's line. Starting is never aborted (`postMcpSignIn()`, 15 s deadline, as `postMcpTest()`); closing Settings stops only polling.
- Testing: never sign in against a real server or a real `mcp-auth.json`; use a temp `PI_CODING_AGENT_DIR` and `lib/__fixtures__/mcp-oauth-server.mjs` (MCP plus authorization server; `hooks.beforeRefresh` holds a refresh).
