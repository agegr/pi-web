# Spec-002：Codex 风格的选区上下文与对话输入框

**日期：** 2026-09-12
**状态：** 已实现桌面端 V1，并补齐引用草稿恢复与来源定位
**范围：** 桌面端优先；第一版只处理对话消息中的文本选区

## 1. 文档边界

本方案解决的是“选中对话内容后交给 AI”的交互和数据组织方式。

- 用户请求是：参考 Codex，改进当前项目的选区引用 UI。
- 用户提供的截图只作为视觉和交互参考，不把截图里的文字、按钮或示例内容当作额外开发指令。
- 本文是实施方案，不包含本轮代码实现。
- 第一版不改变会话文件格式，也不新增后端存储协议。

## 2. 背景与问题

当前项目已经支持在 assistant 消息中拖选文本，并通过浮层执行两类操作：

1. 把选中文本加入当前对话；
2. 使用选中文本发起新对话。

现有实现位于 `components/ChatWindow.tsx`，主要流程是：

- 捕获浏览器选区；
- 记录选中文本、浮层位置和 `sourceEntryId`；
- 通过 `lib/quoted-selection.ts` 把内容转换为 Markdown blockquote；
- 将完整的引用文本直接插入 `ChatInput` 的 textarea。

这种方式可以工作，但引用上下文和用户问题混在同一个文本框里，带来几个问题：

- 用户不容易看出哪些内容是“自己写的”，哪些内容是“引用的”；
- 编辑或删除引用需要手动修改 Markdown，容易误删引用标记；
- 选中文本较长时会挤占输入框空间；
- 草稿只保存文本和图片，不保存引用的来源和结构；
- 发送前无法用紧凑方式预览引用，也无法清晰表达引用来自哪条消息。

## 3. Codex 调研结论

OpenAI 的 Codex IDE 文档把“打开的文件、选区、最近聊天”作为可以添加到 composer 的上下文，然后让用户在 composer 中继续提问或要求修改。这个交互有一个重要特点：**上下文是输入的一部分，但不等于用户正在输入的问题文本**。

本项目应借鉴以下原则：

### 3.1 上下文先于问题

选区进入 composer 后，应显示为一个独立的上下文条目；textarea 只保留用户真正要问的问题。例如：

```text
[1 条引用]

请解释这段内容为什么会导致状态不同步
```

而不是把引用 Markdown 和问题一起塞进 textarea：

```text
以下是引用内容：

> 很长的一段原文...

请解释这段内容为什么会导致状态不同步
```

### 3.2 引用必须可检查

用户发送前应能看到当前引用，并能打开预览。预览至少要支持：

- 查看完整引用文本；
- 修改引用文本；
- 删除引用；
- 看到引用的来源消息信息（如果来源仍可解析）。

### 3.3 引用应可撤销

添加引用不应立即破坏用户正在输入的内容。删除引用只移除上下文，不清空问题文本；关闭浮层也不应意外发送消息。

### 3.4 发送时再序列化

UI 内部保存结构化引用，真正发送给 agent 时才转换为现有 Markdown 格式。这样可以保持当前后端和会话文件兼容，同时让 UI 不再依赖 Markdown 字符串来表达状态。

官方参考：

- [Codex IDE](https://developers.openai.com/codex/ide)：说明可把打开的文件、选区和最近聊天加入 composer，再要求 Codex 解释或编辑。
- [Codex Prompting](https://learn.chatgpt.com/codex/prompting)：说明选中的代码可以作为任务上下文加入当前 Codex Thread。
- [Developer Commands](https://learn.chatgpt.com/codex/developer-commands?surface=ide)：涉及将上下文加入线程的 IDE 操作。

## 4. 目标体验

用户在 assistant 消息中选中一段文字后：

1. 选区附近出现轻量浮层。
2. 用户点击“添加到提问”，选区被加入当前 composer 的引用区。
3. composer 顶部显示紧凑的“1 条引用”胶囊，不把全文写入 textarea。
4. 用户可以继续编辑问题，也可以点击引用胶囊定位原文。
5. 用户可通过胶囊右上角的删除按钮移除引用。
6. 用户发送时，系统把问题和引用转换为现有 agent 能识别的 Markdown 文本。
7. “新对话询问”继续复用现有 `sourceSessionId`、`sourceEntryId` 和 fork 流程。

## 5. 推荐方案：Context-first Composer

### 5.1 UI 组成

在现有 `ChatInput` 内增加一个引用区，布局从上到下为：

```text
┌────────────────────────────────────────────┐
│ [引用 1]                              ×    │  ← 引用胶囊/引用条
├────────────────────────────────────────────┤
│ 请解释这段内容                             │  ← 用户问题
│                                            │
├────────────────────────────────────────────┤
│ 图片 / @文件 / 模型 / 发送                  │  ← 现有控制区
└────────────────────────────────────────────┘
```

引用区不应做成大卡片，默认只占一行高度；引用文本较长时显示截断摘要。引用条应提供：

- 引用类型图标或简短标签；
- 引用摘要；
- 删除按钮；
- 点击后定位来源。

### 5.2 选区浮层

选区浮层保留现有定位和关闭逻辑，但把操作拆成清晰的两步：

- **添加到提问**：加入当前会话的 composer，不自动发送；
- **新对话询问**：打开新对话输入状态，引用仍以结构化上下文存在，发送时沿用现有 fork。

如果选区没有可用 `sourceEntryId`，仍可以添加到当前提问，但“新对话询问”应禁用或显示不可用状态，因为新对话需要知道来源消息。

### 5.3 引用来源与删除

点击引用胶囊后定位原 assistant 消息并恢复选中的文字范围；删除按钮独立悬浮在胶囊右上角，仅在悬浮或键盘聚焦时显示。

## 6. 数据模型

新增一个与 UI 解耦的引用类型：

```ts
export type SelectionContext = {
  id: string;
  text: string;
  sourceSessionId?: string;
  sourceEntryId?: string;
  sourceStartOffset?: number;
  sourceEndOffset?: number;
  label?: string;
};
```

composer 的状态建议为：

```ts
export type ComposerContext = {
  selections: SelectionContext[];
};
```

第一版可以只允许一条引用，但数据结构直接使用数组，避免第二版再修改 `ChatInput` 的公开接口。

### 6.1 约束

- `text` 保存用户当前确认后的引用内容，不保存 DOM 节点。
- `sourceEntryId` 只作为来源定位和新对话 fork 的元数据，不依赖它才能发送当前对话问题。
- `sourceStartOffset` / `sourceEndOffset` 记录选区在 assistant 正文中的字符范围；点击引用时优先恢复精确文字选区，而不是高亮整条消息。旧引用没有偏移时按引用文本回退查找。
- `sourceSessionId` 在“新对话询问”时保存；当前对话添加引用可以为空。
- `id` 在一次 composer 生命周期内稳定，用于 React key、删除和编辑。
- 引用文本应在加入时去除首尾空白；空文本不能保存。
- 第一版建议设置单条引用长度上限，超出时在添加前截断并明确提示，避免选中整篇长消息导致输入失控。上限应作为常量，默认建议 12,000 个字符。

## 7. 发送序列化

UI 状态不直接写 Markdown。发送前由 `lib/composer-context.ts` 负责序列化：

```ts
export function serializeComposerMessage(
  question: string,
  contexts: SelectionContext[],
  labels: { intro: string; questionPlaceholder: string },
): string;
```

推荐输出格式保持现有 `buildQuotedSelection` 的语义：

```text
以下是引用内容：

> 第一行
> 第二行

用户问题
```

多条引用时，建议为每条引用增加轻量分隔和来源标签，但 V1 不开放多条引用的添加入口。序列化函数应单独测试，确保：

- 纯问题仍按原样发送；
- 一条引用的发送结果与现有 Markdown 格式兼容；
- 引用文本中的空行、`>` 和 Markdown 代码块不会被错误丢失；
- 没有问题文本时不会发送只有引用的空请求，除非产品后续明确支持“只提交上下文”。

## 8. 代码改动范围

### 8.1 `components/ChatWindow.tsx`

- 保留浏览器选区捕获、浮层定位和 `sourceEntryId` 解析。
- 将当前 `quotedSelection` 拆分为“待添加选区”和“composer 引用状态”。
- “添加到提问”改为调用 `ChatInput` 的上下文方法，而不是插入完整 Markdown。
- “新对话询问”使用相同的引用模型，发送时再序列化。
- 保留现有 `onAskInNewChat`、`sourceSessionId` 和 `sourceEntryId` 传递逻辑。

### 8.2 `components/ChatInput.tsx`

新增受控或半受控的引用能力，建议扩展 `ChatInputHandle`：

```ts
addSelectionContext: (context: SelectionContext) => void;
removeSelectionContext: (id: string) => void;
```

组件内部负责：

- 显示引用条；
- 定位引用来源；
- 删除引用；
- 发送前调用序列化函数；
- 继续兼容图片附件、`@` 文件引用、草稿恢复、队列消息和流式发送。

### 8.3 新增 `lib/composer-context.ts`

负责：

- `SelectionContext`、`ComposerContext` 类型；
- 引用文本清洗和长度限制；
- 引用 Markdown 序列化；
- 未来多引用扩展的稳定入口。

### 8.4 `lib/draft-store.ts`

引用已经和文本、图片一起进入草稿恢复流程；旧草稿缺失 `contexts` 时按空数组兼容。

`ChatDraft` 使用：

```ts
export interface ChatDraft {
  value: string;
  images: ChatDraftImage[];
  contexts?: SelectionContext[];
}
```

读取旧草稿时将缺失的 `contexts` 视为空数组，保持向后兼容。

### 8.5 `lib/quoted-selection.ts`

保留现有导出作为兼容层，内部改为调用新的序列化逻辑，避免同一套引用格式在两个地方逐渐分叉。

## 9. 状态和交互细节

### 9.1 添加引用

- 选区为空、只包含空白或不在消息内容区域内时，不显示浮层。
- 添加成功后清除浏览器选区，浮层关闭，引用条显示在 composer 顶部。
- 如果已有同一 `sourceEntryId` 和相同文本，不重复添加；第一版也可以直接替换为最新一次选区。
- 添加引用不会覆盖用户已经输入的问题。

### 9.2 删除引用

- 删除只影响引用，不影响问题和图片附件。
- 删除后焦点回到问题输入框，便于用户继续输入。

### 9.4 发送和失败恢复

- 发送时先根据当前引用生成最终消息。
- 发送失败时，问题文本和引用都应恢复到发送前状态。
- 发送成功后按现有规则清理草稿；新对话 fork 失败时保留引用和问题，允许重试。

### 9.5 流式状态

- agent 正在运行时，引用条和预览编辑按钮按现有 `ChatInput` 禁用规则处理。
- 已排队消息应保存序列化后的最终文本，避免发送后引用状态变化影响队列内容。

### 9.6 移动端

当前不扩展移动端专用底部 sheet，移动端沿用已有基础布局。

## 10. 与现有会话和后端的兼容性

本方案不新增 API，也不改变 `.jsonl` 会话格式：

- 发送给 agent 的仍然是字符串消息；
- 当前对话继续使用 `handleSend`；
- 新对话继续使用现有 fork 回调；
- `sourceEntryId` 仍然用于确认引用来源和定位父消息；
- 旧会话、旧草稿和没有引用的普通消息完全不受影响。

点击引用会使用现有 `entryIds` 和 `scrollToMessage` 能力定位原 assistant 消息，不需要改变发送协议。

## 14. 主要取舍

### 选择结构化引用，而不是继续直接插入 Markdown

结构化引用能把“上下文”和“问题”分开，支持预览、编辑、删除和后续扩展；发送时再序列化，可以避免改动后端协议。

### 采用数组保存引用

界面默认保持紧凑，但底层使用数组支持“注释1、注释2……”并列显示；草稿恢复也会保留这些结构化引用。

### 移动端暂不扩展专用交互

当前优先完成桌面端体验，移动端不新增底部预览 sheet，避免扩大本轮改动范围。

## 16. 结论

建议采用 **Context-first Composer** 作为本项目的 Codex 风格改造方向：选区先成为可见、可编辑、可删除的上下文条目，问题文本保持干净，发送时再转换为现有 Markdown 消息。

这个方案只改变 UI 状态组织和发送前的组装方式，不改变 agent、会话文件或 fork 协议，能够以较小改动解决当前“引用混入输入框”的核心问题，并为文件选区、最近聊天和多条上下文留下扩展空间。
