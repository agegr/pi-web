# Pi Web 认证机制设计

## 目标

为 Pi Web 增加单用户密码认证，保护公网部署时的页面、API 和 SSE 访问。认证不依赖 IP、域名或反向代理；认证会话失效、密码修改或浏览器断开时，不停止已经在服务端运行的 Pi Agent。

第一版不实现多用户、角色权限、数据库认证或外部 OAuth 登录。

## 已确认约束

- 账号模型：单用户。
- 首次初始化：启动向导配合一次性初始化 token。
- 密码修改：登录后在网页中修改，验证旧密码后生效。
- 密码存储：只保存安全哈希，不保存原始密码。
- 会话：短期固定有效期，默认 24 小时。
- 暴力破解：服务端内存限速，按来源和全局限制失败尝试。
- 认证失效：拒绝后续 Web 请求，但不停止后台 Agent。
- 配置目录：复用 `PI_CODING_AGENT_DIR` 对应的 Pi Agent 目录。
- 发布方式：兼容当前 npm/npx 启动方式；未来 Docker 通过挂载配置目录持久化认证配置。

## 配置和初始化

认证状态保存在 Pi Agent 配置目录下的专用文件：

```text
<agent-dir>/pi-web-auth.json
```

配置文件只包含版本、密码哈希、随机 salt、更新时间和必要的认证元数据，不包含密码或会话明文 token。写入采用临时文件后原子替换，并尽力将权限设置为仅当前用户可读写。

当配置文件不存在时，服务启动时生成高熵的一次性初始化 token，并仅输出到启动终端。初始化页面只能在提交有效 token 后设置初始密码。成功写入密码配置后，token 立即失效且不能再次使用。初始化接口不返回 token，也不把 token 注入前端页面。

如果 token 丢失，部署者需要通过本地文件操作删除认证配置并重启服务，重新进入初始化流程。该操作不通过公网接口提供。

## 密码处理

使用 Node.js 内置 `crypto.scrypt` 生成带随机 salt 的密码哈希。密码比较使用安全的常量时间比较；登录、初始化和改密错误返回统一信息，不泄露配置是否存在或具体失败原因。

密码修改流程：

1. 已登录用户提交当前密码、新密码和确认密码。
2. 服务端验证当前密码和新密码强度。
3. 生成新 salt 和密码哈希，原子替换配置文件。
4. 递增认证配置版本或生成新的认证代次。
5. 吊销所有已有 Pi Web 登录会话，当前请求完成后也必须重新登录。

密码修改不会停止或取消 AgentSession；正在执行的模型请求、工具调用和 SSE 事件生产继续由服务端处理。

## 请求和会话架构

Next.js `proxy.ts` 继续执行已有的跨站 Origin/Fetch Metadata 检查，并新增统一认证检查。公开路由仅包括：

- 登录页和登录 API。
- 首次初始化页和初始化 API。
- 必要的静态资源。

所有业务页面、`/api/*` 业务接口和 Agent SSE 接口默认要求有效会话。未认证的页面请求重定向到登录页；未认证的 API/SSE 请求返回 `401` JSON 或等价的 HTTP 错误，不返回业务数据。

登录成功后设置随机、不可预测的 session cookie：

- `HttpOnly`，禁止 JavaScript 读取。
- `SameSite=Lax`，降低跨站请求风险。
- HTTPS 请求使用 `Secure`。
- 固定有效期 24 小时，不采用滑动续期。

服务端只在内存中保存 session token 的哈希、创建时间、过期时间和认证代次。原始 token 不写入日志或配置文件。服务重启后会话失效；密码修改后通过认证代次变化立即使全部会话失效。登出只清理当前 cookie 和对应会话。

## 暴力破解防护

登录失败采用通用错误响应，不区分密码错误、初始化状态或其他验证失败。服务端维护内存限速状态：

- 按请求来源记录失败次数和最近失败时间。
- 使用逐步延迟和临时拒绝。
- 增加全局失败速率限制，防止攻击者轮换来源压垮校验逻辑。
- 限速状态不持久化，服务重启后清空。
- 不把任意 `X-Forwarded-For` 头当作绝对可信身份；如使用代理头，需要明确的部署信任边界。

认证 API 应限制请求体大小，并避免在日志中输出密码、token、cookie 或完整请求体。

## Agent 生命周期边界

Pi Web 登录会话只控制浏览器能否读取和调用服务端 API，不拥有 AgentSession 的生命周期控制权：

- 会话过期：阻止新的页面/API/SSE 请求，但不停止已运行 Agent。
- 浏览器关闭或网络断开：不停止已运行 Agent。
- Pi provider API key/OAuth 失败：Pi Web 登录仍有效；当前 Agent 调用可能以错误结束，但不会影响 Pi Web 会话。
- 修改 Pi Web 密码：吊销 Web 会话，但不停止 Agent。
- Node.js 服务进程重启：当前 in-process AgentSession 会丢失；这是现有进程生命周期限制，不由认证机制解决。

重新登录后，客户端通过现有会话读取和状态接口恢复 Agent 状态；后台运行通知仍使用现有 SSE 和运行状态机制。

## npm 和 Docker 兼容性

项目当前通过 npm 包、`npx` 或全局 `pi-web` 启动，不包含 Dockerfile 或 compose。认证实现不新增生产依赖，也不将密码写入 `NEXT_PUBLIC_*` 配置。

npm 部署直接使用现有 Pi Agent 配置目录。Docker 部署需要将包含 `pi-web-auth.json` 的 Pi Agent 配置目录挂载为持久化 volume，并保证容器运行用户对该目录有读写权限。容器删除后若未挂载 volume，认证配置会丢失并重新进入初始化流程。

## 错误处理

- 未初始化：业务页面进入初始化流程，业务 API 返回明确的初始化状态，而不是暴露内部路径。
- 初始化 token 无效或过期：返回通用失败信息并继续限速。
- 登录失败：返回 `401`，不泄露具体原因；触发限速时返回 `429` 和合理的重试提示。
- 会话过期或被吊销：页面请求跳转登录，API/SSE 返回 `401`。
- 配置文件读取或写入失败：服务端记录不含敏感信息的错误，并拒绝改变认证状态；不能回退到无认证模式。
- 密码修改写入失败：保留旧密码和旧会话，不返回半成功状态。

## 测试范围

单元测试覆盖：

- 密码哈希生成和校验，错误密码不能通过。
- 配置文件缺失、损坏、原子写入和权限处理。
- 一次性初始化 token 只能成功使用一次。
- session cookie 的创建、过期、吊销和认证代次变化。
- 登录失败限速、延迟和恢复。
- 认证 middleware 对公开路由、页面、API 和 SSE 的分流。
- 改密后所有 Web session 失效。
- 认证失败不会调用 AgentSession 的 destroy、abort 或 shutdown 操作。

集成验证覆盖：

- 未登录访问首页和业务 API。
- 初始化、登录、登出、过期后重新登录。
- 登录会话过期期间 Agent 仍继续运行，重新登录后可读取结果。
- npm 启动方式下配置目录可用。
- 配置目录作为 Docker volume 时可跨重启保留认证状态。
