# 调试经验教训

## 核心原则

### 1. 先收集信息，后假设原因
- **错误做法**：看到症状就假设原因，立即开始修改
- **正确做法**：先收集完整信息（日志、diff、复现步骤），再分析原因

### 2. 先找变更，后找 bug
- **错误做法**：假设问题原因，盲目修改代码
- **正确做法**：用 `git diff` 找出所有变更，问题往往就在变更中

### 3. 逐个排除，不要批量修改
- **错误做法**：一次修改多处，无法定位哪个修改解决了问题
- **正确做法**：每次只改一处，测试确认后再改下一处

### 4. 修复后必须验证
- **错误做法**：修复后不测试，继续修改其他地方
- **正确做法**：修复后测试，确认没有引入新问题

### 5. 引入新问题立即回滚
- **错误做法**：修复引入新问题后继续修补，越改越远
- **正确做法**：立即回滚到上一个可用状态，重新分析

## 标准调试流程

### 第一步：收集信息
```bash
# 问题是什么？
# 什么时候发生？
# 日志说了什么？
# 有没有报错？
# 能否稳定复现？
```

### 第二步：找出变更
```bash
git diff                    # 看看最近改了什么
git log --oneline -10       # 看看最近的提交
git diff HEAD~5             # 对比几个版本前
```

### 第三步：验证原版
```bash
git stash                   # 暂存当前修改
# 测试原版有没有问题
git stash pop               # 恢复修改
# 如果原版没问题，问题就在 diff 里
```

### 第四步：二分排查
```bash
# 如果变更很多，用二分法
git stash                   # 暂存所有修改
git stash pop -- <file1>    # 只恢复一个文件
# 测试
# 逐个文件排查
```

### 第五步：逐个修复
- 每次只改一处
- 测试确认后再改下一处
- 记录每个修改的效果

### 第六步：验证修复
- 修复后必须测试
- 确认没有引入新问题
- 如果引入了，立即回滚

## 常见调试陷阱

### 陷阱 1：假设症因
```
症状：页面卡住，显示 "Waiting for model..."
错误假设：SSE 连接时序问题
实际原因：SSE 连接重复建立
```

**避免方法**：先看日志，再看代码，最后假设

### 陷阱 2：修修补补
```
第一次修复：分离创建会话和发送 prompt
新问题：消息发送两次
第二次修复：添加延迟
新问题：其他地方也出问题
...
```

**避免方法**：修复引入新问题时，立即回滚

### 陷阱 3：过度工程化
```
原作者设计：POST /api/agent/new 同时创建会话和发送 prompt
我的修改：拆分成三步（创建会话 → 等待 SSE → 发送 prompt）
结果：引入新问题
```

**避免方法**：尊重原设计，除非有充分理由

### 陷阱 4：不看 diff
```
问题：新对话卡住
我的做法：假设是 SSE 时序问题，开始修改
正确做法：先 git diff，发现 useEffect 逻辑被改了
```

**避免方法**：遇到问题第一件事是 `git diff`

## 案例分析

### 案例：新对话卡住

**症状**：
- 新对话发送消息后卡住
- 显示 "Waiting for model..."
- 刷新页面后才能看到响应

**错误排查过程**：
1. 假设 SSE 连接时序问题
2. 分离创建会话和发送 prompt
3. 添加延迟
4. 等待 connected 事件
5. 引入新问题（消息发送两次）
6. 继续修补...
7. 越改越远

**正确排查过程**：
1. 收集信息：日志显示事件被接收，但没有后续事件
2. 找出变更：`git diff` 发现 useEffect 逻辑被改了
3. 对比原版：原作者只在 isStreaming 时连接 SSE
4. 恢复原版：问题解决

**根因**：
- useEffect 中无条件调用 `connectEvents`
- 导致 SSE 连接重复建立
- 事件被发送到错误的连接实例

**教训**：
- 一开始就应该 `git diff`
- 问题往往在变更中
- 不要假设，要验证

## 快速检查清单

遇到问题时，按顺序检查：

- [ ] `git diff` 看看最近改了什么
- [ ] `git stash` 测试原版有没有问题
- [ ] 如果原版没问题，问题就在 diff 里
- [ ] 逐个文件排查，找出问题文件
- [ ] 逐个修改排查，找出问题修改
- [ ] 修复后测试，确认没有引入新问题
- [ ] 如果引入新问题，立即回滚

---

## 总结

> **调试的核心是：收集信息 → 找出变更 → 逐个排除 → 验证修复**
>
> **不要假设，要验证。不要批量修改，要逐个排除。不要修修补补，要立即回滚。**
