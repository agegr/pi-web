# Pi Web - Development Notes

## Quick Start

```bash
npm run dev   # port 30141
```

Typecheck: `node_modules/.bin/tsc --noEmit`  
Lint: `npm run lint`  
**Never run `next build` during dev** — pollutes `.next/` and breaks `npm run dev`.

### Dev server troubleshooting

- Before starting a server, run `lsof -nP -iTCP:30141 -sTCP:LISTEN` and reuse the existing Pi Web process when it is healthy. A second `next dev` for the same checkout cannot use a different port as a workaround because both processes contend for `.next/dev/lock`.
- A browser-only `Module ... factory is not available` overlay usually means that tab has a stale Turbopack/HMR graph; it does not prove the server or source is broken. First call the browser's explicit reload action, then compare the current server log and a direct HTTP/API request.
- Restart only after the failure reproduces from a fresh page and the server-side checks also fail. Stop the exact dev process gracefully, move `.next` into a `mktemp -d` backup, and restart with the standard `npm run dev` command.
- Do not use `next dev --webpack` as a fallback. This repository's development graph can fail on `undici` imports such as `node:console`; development is expected to use Turbopack.
- Next.js may append a generated `BEGIN:nextjs-agent-rules` block to `AGENTS.md` when `next dev` starts. Treat that as generated tooling output, verify it with `git status`, and do not include it in an unrelated feature commit.

## Architecture

```
Browser                Next.js Server              AgentSession (in-process)
  │                        │                               │
  ├─ GET /api/sessions ────▶ reads ~/.pi/agent/sessions/   │
  ├─ GET /api/sessions/[id] reads .jsonl file directly     │
  ├─ GET /api/agent/running ───────▶ running id snapshot   │
  │                        │                               │
  ├─ send message ─────────▶ POST /api/agent/[id]          │
  │                        │   startRpcSession() ─────────▶│ createAgentSession()
  │                        │   session.send(cmd) ─────────▶│ session.prompt()
  │                        │                               │
  ├─ SSE connect ──────────▶ GET /api/agent/[id]/events    │
  │                        │   session.onEvent() ◀─────────│ session.subscribe()
  │◀── data: {...} ─────────│                               │
```

**Session browsing** (read-only): reads `.jsonl` files through SDK `SessionManager` helpers and `lib/session-reader.ts` — no AgentSession created.  
**Sending a message**: `startRpcSession()` in `lib/rpc-manager.ts` creates an AgentSession in-process.

## Key Design Decisions & Traps

### AgentSession lifecycle (`lib/rpc-manager.ts`)
- One `AgentSessionWrapper` per session id, keyed in `globalThis.__piSessions`
- `globalThis` survives Next.js hot-reload; plain module-level Map does not
- Idle timeout: 10 minutes by default (`PI_WEB_IDLE_TIMEOUT_MS`, `0` disables). Concurrent `startRpcSession()` calls share a single start Promise (`globalThis.__piStartLocks`)
- Stop cannot cancel an SDK run that awaits a promise ignoring the abort signal (a third-party extension handler or tool): `inner.abort()` never returns and the session keeps reporting running. Stop (`abort`, and `abort_bash` likewise) therefore sets `forceShutdownOnIdle` and arms the idle timer, which shuts the wrapper down one idle timeout after the first Stop even though it is still running, so the session recovers without a server restart. Commands that arrive meanwhile — a reload's `get_tools`, Stop pressed again — keep that deadline instead of pushing it back, or a user retrying would keep the stuck run alive. With `PI_WEB_IDLE_TIMEOUT_MS=0` the timer still arms after Stop, at the 10-minute default (#656).
- A wrapper is closing from the moment `shutdown()` or `destroy()` starts, not once it is disposed: `isAlive()` turns false before extensions have handled `session_shutdown`, so the routes that check it stop sending commands to one that is about to be disposed, and `startRpcSession()` builds a fresh wrapper — but only once the closing one has disposed (`closingRpcSessionWait()`, at most the deadline below plus a second, counted from the first caller that waits, so a shutdown still binding extensions can be overtaken; `setRpcSessionTools()` waits for that or for a start already under way, then applies the selection to the wrapper it left instead of writing through a second `SessionManager`). Until then the closing wrapper still owns the session: an extension's `session_shutdown` may append to the file, which a replacement opened earlier would branch away from, and `dispose()` releases provider resources such as a Codex websocket by session id, which the replacement shares. During `shutdown()`, `isRunning()` still reports a stuck run until disposal, so it still counts as busy. The closing wrapper stays in `__piSessions` until it is disposed or replaced, and its `onDestroy` removes the entry only while the entry still points at it; deleting by id let a late cleanup unregister the replacement, leaving it orphaned beside a third wrapper on the same file. A wrapper registered before a hot reload still deletes by id, so `registerRpcWrapper()` clears the callback of the entry it replaces. Extensions get `PI_WEB_SHUTDOWN_DEADLINE_MS` (5 s by default; `0` or an invalid value keeps the default) to handle `session_shutdown`, after which the wrapper logs once and disposes anyway (`shutdown()` still waits for extension binding to finish first, without a deadline): closing an MCP connection has no upper bound, since it waits for a token refresh in flight and for a stdio child whose grandchild may keep stdout open. The deadline timer is unref'd, so it never holds a quitting process open.

### Fork never touches the running AgentSession
Never fork through `AgentSession.fork()` / `AgentSessionRuntime.fork()`: they replace the session in place (after fork, `inner.sessionId` is the *new* id, and the runtime aborts the current run first, because the TUI holds one session per process). A wrapper still registered under the old id would then serve the forked state and corrupt the `parentSession` chain.

`send("fork")` and `send("fork_branch")` instead open a separate `SessionManager` on the source file and `createBranchedSession()` from it, so the source's in-memory session is never mutated. That is why forking is allowed **while the source is running** (only a running `!` shell command refuses it): the copy needs only finished entries, and pi appends each one synchronously in this same process, so the file on disk already holds them. The in-flight assistant message lands at `message_end`, after the fork point. A source whose first user message has not landed has no file yet, and fork refuses it with the upstream "has not been saved yet" wording. After a fork, an idle source is shut down because the browser moves to the child; a running source is left alone and keeps its run, and the sidebar keeps showing it as running. `clone` still refuses a running session: it copies the current branch, which is the run in progress.

### In-session branching waits for the run
pi's `navigateTree()` refuses while streaming or compacting, and that is structural: one file has one leaf pointer, a running agent appends every finished message under it, and navigating also swaps the agent's context. Moving the leaf mid-run would hang the rest of the turn off another branch. "Edit from here" is therefore hidden while the session is busy, and the BranchNavigator renders read-only (`locked`) with a note instead of switching; `handleLeafChange` refuses too, because switching only the view would render the live run under a different branch while the server leaf stayed put. To branch from a running session, fork it.

### Two kinds of branching — don't confuse them
- **Fork** ("New session" on user message): creates a new independent `.jsonl` file. Shown as a child in the sidebar tree via `parentSession` header field.
- **In-session branch** ("Edit from here" / BranchNavigator): calls `navigate_tree` within the same file. Multiple entries share the same `parentId`. Switching between them calls `/api/sessions/[id]/context?leafId=`.

### Session files can be fully rewritten
`parentSession` in the header is **display metadata only** — has zero effect on chat content. Safe to `writeFileSync` the entire file (pi does this itself during migrations). Used when cascade-reparenting children on delete.

### ToolCall field normalization
Pi stores toolCall blocks as `{type:"toolCall", id, name, arguments}` but `ToolCallContent` uses `{toolCallId, toolName, input}`. `normalizeToolCalls()` in `lib/normalize.ts` handles this — called in both `session-reader.ts` (file load) and `handleAgentEvent` in `hooks/useAgentSession.ts` (streaming).

### New session tool preset
Tool names are passed at session creation (`POST /api/agent/new` -> `toolNames[]`) and persisted in versioned `pi-web:tool-selection` custom entries. No entry means a legacy session and keeps Pi's default behavior; an empty array means Chat only. Chat only resolves before services are created, loads no extensions/skills/prompts/themes, and replaces Pi's base prompt with the ordered contents of Pi's discovered context files. Crossing the Chat-only boundary rebuilds the wrapper; changing between nonempty presets updates it in place.

**Exact system prompts go through `before_agent_start`.** Since pi 0.86 the prompt lives in the transcript: `agent.state.systemPrompt` is a getter replayed from persisted system messages (assigning it throws), and the agent loop's request context has no `systemPrompt` field, so neither mutating the state nor patching `prepareNextTurnWithContext` reaches the model. Chat-only sessions and reopened legacy sub-agent sessions whose profile was in replace mode register `lib/exact-system-prompt.ts` as an inline extension factory on the resource loader; its `before_agent_start` handler returns `{ systemPrompt }`, which the SDK projects as the provider's leading system prompt for the whole run while the transcript keeps recording Pi's structured sections. `get_state.systemPrompt` reports the exact prompt for those wrappers because the SDK state only shows the structured sections. Legacy subagent sessions (from the removed built-in engine) reopen with the active tools plus profile-level skill and extension loading switches persisted in `resourceSnapshot`; the reserved `Agent`, `get_subagent_result`, and `steer_subagent` tools stay excluded from their own tool list so a reopened run cannot nest another dispatch. See `docs/adr/0002-chat-only-tool-selection.md` and `docs/adr/0006-delegate-subagents-to-pi-subagents.md`.

The last preset explicitly selected by the user is stored in browser `localStorage` and initializes fresh-session composers only. Existing sessions never trust that preference; they use their live `get_tools` state or pi's default when no wrapper exists.

**Tool exposure (pi >= 0.99).** Every tool reports an `exposure`: pi activates `direct` and `model-only` tools on registration unless their definition sets `defaultActive: false` (`codemode` and `tool_search` do), leaves `codemode` and `deferred` tools undeclared until something activates them, and ignores `hidden` (withdrawn) tools in `setActiveToolsByName()`; `get_tools` leaves hidden tools out. A preset replaces only the coding tools. `resolveActiveToolNames()` carries every other tool that is active and still registered and not hidden, so what an extension, `tool_search`, or a `defaultTools` entry such as `+codemode` activated survives startup, `set_tools`, and `reload`, and a tool an extension switched off stays off; a preset never turns `codemode` on by itself. It adds nothing else: pi activates extension tools itself — every one it would activate on registration when it builds or reloads a session, then each newly registered one — so re-adding them on every apply would override an extension (or a branch's recorded loadout) that keeps a `direct` tool off. `reload` carries the set pi rebuilt from the previous one after extensions started again, not the previous set, so a tool an extension switched off while restarting stays off. `navigateTree()` restores the target branch's loadout from its transcript, which brought `write` back under a Read-only pin and dropped `codemode`, so after navigation a normal session applies its pinned selection again (the restored set when it has none) and carries the session's own tools over from the branch it left: `codemode`, `tool_search`, and pi-web's subagent tools, which the built-in subagent setting turns on for the whole session. Other extension tools follow the target branch's recorded loadout, as in the pi CLI, so a tool registered after that branch point stays off there until a reload. Chat-only and subagent wrappers keep what pi restored. **Built-in extensions.** The pi CLI prepends its built-in `codemode`, `tool-search`, `mcp` and `llama.cpp` extensions from a module the SDK does not export. `lib/builtin-extensions.ts` rebuilds the first three from the factories the SDK root does export, under the CLI's names with `replaceable: true, builtin: true`, so `-builtin:<name>`, project overrides and replacement by a third-party extension behave as in the CLI; `noExtensions` turns them off too. Only normal sessions load them, never Chat-only or subagent wrappers. The MCP extension gets a `loadConfig` that returns no servers (only the file's `autoEnableCodemode`, with the MCP host's fresh trust read, though the extension asks only on `session_start`), so it connects nothing from `mcp.json` on `session_start` and its startup wait, which ignores Stop, never arms; pi-web registers the servers a session should connect itself (see **MCP host** below). Servers it is given connect through `createPiWebMcpTransportFactory()`, and `openUrl` opens no browser on the server host. MCP is off — the `mcp` entry registers nothing — when `PI_WEB_DISABLE_MCP` is set to anything but empty, `0` or `false`, or when `lib/pi-sdk-internals.ts` cannot load; pi-web never falls back to the SDK's own transport. `codemode` is offered only after a once-per-process self-test has run a script through the SDK's own sandbox (`checkCodemodeSandbox()`): its QuickJS worker and wasm are resolved from the SDK's files at run time, and a tool that fails every call is worse than none. A built-in that cannot run keeps its `builtin:<name>` entry with an empty factory, so a setting naming it still means the same. Normal sessions also load `lib/mcp-read-only-policy.ts`: while the session's pinned selection is read-only (it names tools and none of `bash`, `powershell`, `edit`, `write`; no pin is not read-only), its `tool_call` handler blocks every MCP tool — the MCP extension's, or any named `mcp__` — whose definition lacks `annotations.readOnlyHint: true`. A codemode script's calls pass through `tool_call` too, so they are blocked the same way. It reads the pin from the session entries, which `set_tools` writes before applying it and cannot change mid-run. The hint is the server's word: the policy guards against model mistakes, not a malicious server. Code mode's choice is **Automatic** (nothing written; the MCP extension activates `codemode` when a `codemode`-exposure server connects) or **Always on** (`+codemode` in the global `defaultTools`); there is no Never. `/api/tools/settings` is the only writer of that key, for this and the PowerShell switch, through `lib/global-settings-file.ts`, which takes the lock pi's `SettingsManager` takes on the same file. `lib/codemode-settings.ts` edits only the entries naming `codemode` and appends `+codemode`, which works on a plain and a modifier-only list alike; a modifier-only list it leaves empty is removed, because `defaultTools: []` means no tools at all, not pi's defaults. `defaultTools` may hold `+name` / `-name` modifiers: read the resolved list through `SettingsManager.getDefaultTools()`, and `lib/powershell-settings.ts` resolves the raw global list with the same rule before it edits it, since appending a plain name to a modifier-only list would drop pi's default tools.

### MCP host (`lib/mcp-host.ts`)
- `createPiWebBuiltinExtensions()` returns `{ extensions, mcpHost }`; `startRpcSession()` passes the host to the wrapper. The host's inline extension reads the global and project `mcp.json` itself and hands the servers it wants to the SDK's MCP extension with `pi.registerMcpServer()`, so the extension's own `loadConfig` stays empty (ADR 0006). It stays inactive unless `/mcp` belongs to `builtin:mcp` (`isBuiltinMcpCommand()` in `lib/mcp-command.ts`, the rule the composer applies too): with `-builtin:mcp`, or a third-party extension that registers `/mcp`, another implementation would connect the servers through its own, unscrubbed transport.
- **Nothing connects until a prompt.** Before a prompt sent while no run is going (`!inner.isStreaming`), the wrapper calls `prepareForPrompt()`: the host diffs `mcp.json` against what it registered, unregisters and re-registers only entries whose canonical JSON changed, then waits up to 10 s for servers still connecting. A server that outlasts one full wait is not waited for again. `before_agent_start` also syncs, without waiting, for prompts that do not come through the wrapper. **An extension command is no run:** pi runs it at the very start of `prompt()` and returns, so `mcpPromptPreparation()` (`lib/mcp-command.ts`) reads the message against the session's extension commands by invocation name, as pi does: another extension's command skips MCP altogether (it waited up to 10 s and started servers for nothing), and the built-in `/mcp` registers without waiting (`prepareForPrompt(signal, { wait: false })`). Never skip the built-in `/mcp`: it looks its servers up among the registered ones, and the host registers them only before prompts, so `/mcp login docs` as a session's first message would answer "No MCP server named".
- **Stop during that wait** aborts it, and the prompt is rejected unsent with `MCP_WAIT_STOPPED_MESSAGE`, so the client restores the draft. It cannot live in `before_agent_start`: pi emits it before the run has an abort signal, and `AgentSession.abort()` does nothing until a run is active. The `abort` command waits for the withdrawn prompt to unwind before it checks `isRunning()`.
- **Connection state comes from the transports.** The extension reports none, so `wrapTransportFactory()` wraps pi-web's transport factory and `watchTransport()` follows each transport it creates (listeners plus own `start`, `send` and `close` on the instance, never a wrapper object: the SDK checks `instanceof StdioTransport`). Ready (`watchConnection()`) means every `tools/list` / `resources/list` / `resources/templates/list` request is answered and a macrotask passed without another page being requested; the extension registers the tools in the microtasks that settle the last list. A transport that closes first, or a factory that throws (such as a `PI_WEB_PASSWORD` reference), is failed. **Every transport of a registration is followed, not only the first** (`attemptFor()` used to skip a settled attempt): an HTTP retry, the reconnect at the next call after a drop, and the extension's `turn_start` reconnect once tokens were stored elsewhere (Settings, `pi mcp login`) each open a new one, the latest speaks for the server (`attempt.current`), and an older one closing late is ignored. The first outcome still settles the attempt, which is all a prompt waits for, and the host still never retries a failed server whose entry is unchanged (ADR 0006): only the extension's own reconnects change its state.
- **What a session sees goes to Settings** (`lib/mcp-status.ts`). Every change of an attempt is written as `{ origin: "session", state, sessionId, cwd, updatedAt, error?, stderr?, conflict?, closedAt? }` under the entry's `scope\0sourcePath\0name` with `mcpConfigKey()` (`lib/mcp-config-key.ts`) of the entry as `loadMcpConfig()` returned it — the validator hands back the parsed value itself, so that is the key GET lists — never of the config the host registered, which `withReachableExposure()` may rewrite. The latest write for the same content wins, a test's or any session's, so a global stdio server shows the last report with that session's folder. A session syncs `mcp.json` only before its prompts, so one still holding an entry from before an edit reports about the old content under the old key, beside the record for the file as it is now, never in its place. States: `connecting` (a transport opened), `connected`, `needs-auth`, `failed`, `disconnected`, `conflict`, `not-trusted`.
  - **needs-auth** is told from the error `start` or `send` rejected with, by name, as the SDK's `needsSignIn()` decides: `McpOAuthAuthorizationRequiredError`, or `McpAuthRequiredError` when the connection passed an auth provider (the factory's third argument, given exactly for an OAuth server; one with an `Authorization` header gets a plain failure). It used to read "failed" with a generic message. A later request that asks for a sign-in reads `needs-auth` too.
  - **disconnected** is a ready transport that closed with nobody calling its `close()`: a stdio server that exited. One the client closed (a reconnect, `/mcp logout`, the session ending) is not news; the host's `session_shutdown` runs only after the MCP extension's handler has awaited every close, so this is what keeps a session's end from reading as drops. The host cannot see the connection itself, so after `/mcp logout` in a chat the record keeps its last state until the next connection asks for a sign-in.
  - **failed** carries the first error `start` / `send` rejected with (a spawn error, an HTTP error) or the server's error answer to `initialize`, else "The connection closed before the server was ready" (a request on a closed transport, `McpConnectionClosedError`, says nothing), and the stdio stderr tail read at close. Error and stderr go through the Test's redactor (`createTestRedactor()` with that transport, for resolved values) and `maskStatusError()` / `maskStatusStderr()`: masked, then shortened. A literal env value a server prints is `•••`.
  - **conflict**: when `pi.registerMcpServer()` refuses, the owner comes from `pi.getMcpServers()`, else from the SDK's words (`already registered by extension "<path>"`); `serverStates()` keeps `not-registered` and adds `conflict`. **not-trusted**: `untrustedProjectServerEntries()` returns the values too, only to hash them into the key; a sync reports at most `MCP_UNTRUSTED_REPORT_MAX` (100) of them and logs the rest as one count, since each is a record in the shared store of 500 and a repository can declare tens of thousands, which evicted the user's Tests and blocked the event loop on every prompt. Every entry is keyed in its own `try`, so one the host cannot key never drops the others or the global servers. Every sync finds these problems again, so each is written only when it changed or its record was replaced since.
  - The host stops recording an attempt it lets go (`letGo()`: unregister, idle release, session end, a reload's dispose) before the extension closes it. Its own record, while nobody wrote another since (`forgetMcpStatus()` / `replaceMcpStatus()` compare by identity), is amended where it would describe a connection nobody holds: `connecting`, which nothing would finish, goes, and `connected` gets `closedAt`, which Settings shows as `on` with "closed that connection at …". Sessions idle out after 10 minutes, so without it most "Connected in a session" rows described closed connections for as long as the server process ran. `failed`, `needs-auth` and `disconnected` stay as they are: still true of the server. At dispose the host also forgets its problem records (`conflict`, `not-trusted`, a refused registration) still its own, and its host-inactive record: those are found again at every sync, and a host that stopped syncing no longer sees them. **The wrapper disposes the host when it starts closing** (`McpHost.dispose()`, once, from `shutdown()` after extension binding and from `destroy()`), before any extension hears `session_shutdown`: handlers run in order, the host's inline extension after the MCP extension and every third-party one, and a close that never returns (a stdio grandchild holding stdout, an OAuth refresh in flight) kept it from ever running once the wrapper disposed at its deadline, leaving "Connected in a session" rows and a host-inactive notice for a session that was gone. The host's own `session_shutdown` handler only repeats the dispose; a released attempt records nothing its transports do afterwards, and a disposed host ignores a late `session_start`. A let-go attempt still settles, for a prompt waiting on it.
  - **A `/mcp` the host does not own**: at `session_start`, an `mcp` command from another extension than `builtin:mcp` records `{ owner, cwd, updatedAt }` under the session id (`recordMcpHostInactive()`, at most 100), forgotten when the wrapper starts closing (the host's dispose), or when a reload starts with Pi's own. Several extensions' `/mcp`, which pi renames `mcp:1`, `mcp:2`, … (the built-in is dropped then too), name the first as the owner; a prompt template named `mcp` is nobody's (`isMcpExtensionCommand()`). `-builtin:mcp` leaves no `/mcp` at all and is read from the files. GET reports the record for the panel's cwd, else the latest of any folder, as `hostInactive`.
  - Tests: `lib/mcp-host.test.mjs` pins each state with fake transports (`drop()` closes one by itself, `close()` as the client; `sendError` rejects a request), the reconnect after a sign-in, masking (a transport failure's message as well as a factory that throws), the let-go rules (a closed mark at idle release and session end, a fresh connection without one, problem records gone at session end), conflicts from the registry and from the SDK's words, recording once per change, a session behind an edit leaving the current entry's test standing, the raw-entry key without a codemode sandbox, and the inactive-host record; its trust fixture checks that `readMcpOverview()` attaches what a session saw (key agreement). `lib/mcp-host.integration.test.mjs` runs a real session: a connected fixture as GET lists it, a killed fixture (`PI_WEB_FIXTURE_PID_FILE`) reads `disconnected`, a crashing server's stderr (and an echoed literal env value masked), a local HTTP server that answers 401 until `mcp-auth.json` holds its token reads `needs-auth` and then `connected` after the next turn, and an inline extension's server of the same name a `conflict` naming `<inline:…>`.
- **Never unregister a server before its transport exists.** The extension assigns `server.connection` only after loading the MCP runtime, and its removal closes that connection; unregistering earlier finds nothing to close, and the extension connects the server anyway with no way left to close it. The host waits (at most `replaceWaitMs`, 5 s) for the transport before unregistering. Once it exists, `close()` is safe even mid-handshake: the connection throws away the client when the handshake finishes. The cap is no guarantee by itself: a plain `mcp_servers_change` does not move the extension's `generation`, so a connection it assigns after the unregister is never closed. The host therefore counts each registration it unregistered without a transport (`abandoned`, by `name\0configKey`), and its factory refuses the next transport asked for one while no live registration claims it (`refuseAbandoned()`): the connection fails and nothing is started. Today the gap is a few microtasks, since Pi Web imports the SDK's `runtime.js` (the same module instance) before any host exists, so `loadMcpRuntime()` is a cache hit.
- A host that has not run for `PI_WEB_MCP_IDLE_MS` (10 minutes; `0` disables) unregisters its servers, unless `ctx.isIdle()` says a run is still going; the next prompt registers them again. The timer is stopped from `agent_start` to `agent_end` and while a prompt waits in `prepareForPrompt()`, and started again at `agent_end`, when `prepareForPrompt()` returns, and whenever a sync finishes. Never rely on `agent_end` alone: a prompt that registers servers and then starts no run (Stop during the wait, a slash command, a rejected preflight) never emits it, and a sync Stop gave up on still finishes in the queue afterwards. A reload binds a new host instance with nothing registered.
- MCP tools register as `mcp__<server>__<tool>`, sanitized to `[A-Za-z0-9_-]` and hashed past 64 characters, so the name cannot be split back: `docs.v2/search.pages` and `docs_v2/search_pages` register alike, and either part may hold `__`. A tool card reads `server/tool` only from its result's details (`{ server, tool }`); a running call, the status line and a codemode script's calls keep the registered name, which is also what scripts call.
- Project `.pi/mcp.json` entries follow the project's trust, as in the pi CLI, inherited trust included: `loadMcpConfig` reads the project file only when told the project is trusted, and the host connects every entry it returns. There is no per-entry approval, because a trusted project's `.pi/extensions` already run inside the same boundary, and earlier (on browsing, not on the first prompt). A project entry replaces a global one of the same name. Without a working codemode sandbox, servers with `codemode` exposure are registered as `deferred`, reachable through `tool_search`.
- **Trust is read fresh on every sync**, through the host's `mayReadProjectConfig(cwd)` option (by default `mayReadProjectConfigNow()` in `lib/project-trust.ts`), never from `ctx.isProjectTrusted()`. That is the wrapper's `SettingsManager` flag: fixed when the wrapper is built — `true` for a folder that needed no trust then — and refreshed only on reload, so a `.pi/mcp.json` that appeared later (`git pull`, `pi mcp add -l`, the model's `write` tool) connected on the next prompt with no trust decision. The read is true only while a decision, exact or inherited, trusts a folder that requires trust — not `getProjectTrustStatus().trusted`, which is `true` for a folder with no trust-requiring resources: `loadMcpConfig` looks at the folder again when it opens the file, and a file landing between the two looks would be read with no decision. Nothing is lost, since `.pi/mcp.json` alone makes a folder require trust. A decision made anywhere, the CLI included, reaches an open session's MCP servers on its next prompt, while its project extensions keep the trust the wrapper was built with until a reload (`/api/project-trust` rebuilds the cwd's wrappers anyway). The cost, twice per prompt (`before_agent_start` and `prepareForPrompt()`), is the SDK's `hasTrustRequiringProjectResources()` (up to 8 `existsSync` in `.pi/`, then one per ancestor for `.agents/skills`) and, for a folder that requires trust, a `lockSync` and read of `trust.json`. An unparsable `trust.json`, or one still locked after the store's ~200 ms wait (synchronous: it blocks the event loop that long), counts as untrusted — fail closed, so connected project servers are unregistered until a read succeeds — with one warning per distinct error, naming the file. The MCP extension's `loadConfig` uses the same read for `autoEnableCodemode`, but the extension calls it only on `session_start`, so that flag follows a trust change only at the next reload. While the project file may not be read, `serverStates()` reports every name it declares as `not-trusted` (problems are keyed by scope and name, since a global entry may share it); the names are read after `loadMcpConfig`, so a file that just landed is reported at once. They come from a file nobody has trusted, so only a regular file of at most 1 MiB whose real path is inside the project is parsed, and only for its `mcpServers` keys: the resolved path is opened once with `O_NOFOLLOW | O_NONBLOCK` and checked through `fstat`, so a link elsewhere is refused before opening, and a FIFO or a device is opened without blocking and never read. `loadMcpConfig()`'s `errors[]` (an unparsable file, an entry the SDK skipped) are logged once per process each instead of dropped, at most 20 per sync and the rest as a count (the dedupe set holds 200 and evicts its oldest, so a file with more errors would log them all at every sync). The SDK words a parse error as `${path}: ${error.message}`, and V8 quotes up to ten characters either side of an unexpected token, often a literal secret, so `scrubMcpLoadError()` (`lib/mcp-json-error.ts`) rewords such a message through `jsonErrorMessage()` before it reaches the log, as the panel does.

### Settings › MCP reads (`lib/mcp-config-read.ts`)
- `GET /api/mcp` reads files only: it never spawns a server, opens a connection, or resolves a value, so it lists an untrusted project as safely as the global file. Nothing on its path may call `createDefaultTransport()`, `resolveConfigValueOrThrow()` / `resolveHeadersOrThrow()`, `connection.oauthSettings()` (each runs `!command` values) or `McpOAuthCredentialStore` (a read creates `mcp-auth.json` and a lock); the route test pins that a `!touch` value never ran and that the agent dir holds nothing new afterwards. The signed-in hint is a raw parse of `mcp-auth.json`, keyed as the SDK keys it (`String(new URL(url))`), with tokens meaning `tokens.access_token`; an unreadable file leaves `signedIn` unset, not false. Reading `trust.json` still takes the store's `lockSync` (a transient `trust.json.lock` directory), and the Code mode preference the settings lock, like every other reader.
- Each file is read on its own, never through `loadMcpConfig()`: that skips an untrusted project's file and merges by name, hiding the global entry a project entry replaces. The text is parsed as the SDK parses it (`JSON.parse`, no BOM stripped, `{ mcpServers: {} }` shape, `autoEnableCodemode` a boolean) and each entry checked with the SDK's `validateMcpServerConfig()` when the internals load; an invalid entry is still listed with the SDK's reason. Without the internals (MCP off) entries are listed unvalidated (`validated: false`), a leading `!` marks a command, and any mention of `PI_WEB_PASSWORD` counts. A global entry is `shadowedByProject` only when the project's entry would load: the SDK skips an invalid one and keeps the global. The contract test checks that, on a trusted merge, the per-file reader gives exactly `loadMcpConfig()`'s servers.
- The **project file** is repository-controlled and read before anyone trusts it, so it follows the file-access rule for links: its real path (a link in the file or in `.pi/` above it) must be inside the allowed roots the route already checked the cwd against, a dangling link is refused (`link-dangling`) rather than read as no file, and the resolved path is opened once with `O_NOFOLLOW | O_NONBLOCK`, checked through `fstat` (regular file, at most 1 MiB), so a FIFO is never read. A project file declaring more than `MCP_PROJECT_MAX_SERVERS` (200) servers is reported as `too-many-servers` and none of them is listed, as one over 1 MiB is: 80,000 names fit in 1 MiB, and describing each cost seconds and a 32 MB answer, in the panel and in the trust dialog. The **global file** is the user's: a link is followed wherever it leads (`realPath` reports where) and a dangling one reads as no file, as for the SDK. A trusted project's link outside the roots is still followed by the SDK when a session connects — the panel can only report `link-outside`.
- Nothing literal reaches the browser: env and header **values** are never sent (names only), `command`, `args` and `url` go through `lib/mcp-secrets.ts` — except `command` and `args` of a project no decision trusts (`projectUntrusted`, `trust.decision !== true`, in the panel and the trust dialog alike), shown as written because the masking rules let the repository's author pick what is hidden of what trusting it would run; its URL is still masked, and never its host — (userinfo, query parameters named like credentials or holding token-like values, bare token-like query parts and path segments, `--api-key=…` / `--token X` / `-k X` / `--auth X`, `Name: value` headers, `NAME=value` pairs and `Key=value;…` connection strings), and a value of several words — a whole command line in `command`, `Bearer …` as one argument — is masked word by word, where `Bearer` / `Basic` / `Token` or a credential `Name:` makes the next word a secret: checking only whitespace-free values left a spaced token whole. Those three fields are used as written (the SDK expands nothing there), so only placeholder-shaped values are kept as references: `${NAME}`, or `$NAME` in environment-variable capitals, which a wrapper such as mcp-remote or `sh -c` expands; `$Passw0rd` is masked. The fields the SDK resolves (env, headers, `oauth.clientSecret`) use `isReferenceOnly()`, the SDK's own syntax (`$name` of any case, `$$` / `$!` escapes). A JSON syntax error never quotes the file: for an unexpected token V8 quotes up to ten characters on either side instead of giving a position, which is how a single-quoted secret leaked, so the message keeps the token only when it is punctuation and gives the position that context stood for (`Unexpected token ''' in JSON at position 65 (line 1 column 66)`); messages that already give a position quote nothing and are kept. `configKey`, which later statuses compare against, is an HMAC of the entry's canonical JSON (`canonicalJson()`, total: an array or object past 64 levels prints as a marker instead of being followed, since a 6 KB repository file nested thousands deep overflowed the stack, stopped every server of the session's sync and made GET answer 500) under a random per-process key (`mcpConfigKey()`, both in `lib/mcp-config-key.ts`, which the MCP host imports too), never the JSON: that would carry every literal value, and a plain hash would not survive a weak password in an otherwise visible entry. `lib/mcp-secrets.ts` is pure, for the browser-side importer too; its `literalSecretFields()` is the same classification for deciding what may only be saved globally.
- `commandFields`, `variableReferences` and `webPasswordField` come from `resolvedConfigValues()` in `lib/mcp-transport.ts`, the walk the transport itself refuses `PI_WEB_PASSWORD` with: a stdio entry's `env`, an HTTP entry's headers and `oauth.clientSecret`, told apart by whether `url` is present. An `env` on an HTTP entry is never resolved, so a `!` there runs nothing and is not labelled. `transport` and `usesOAuth` follow the same rule, not the validator's branch: `{ type: "stdio", command, url }` validates as stdio but `createDefaultTransport()` connects it over HTTP and runs its header `!command`s, so it is reported as HTTP. Only an entry the validator refuses, which never connects, gets the validator's reading (a legacy SSE entry has no transport). `variableReferences` names the host variables each of those values reads (`${NAME}` / `$NAME`, through the SDK's `getConfigValueEnvVarNames()`, or `templateVariableNames()`, a port pinned against it, when internals are unavailable), never their values: they resolve from Pi Web's whole `process.env`, not the sanitized one a stdio server starts from, so a header `${GITHUB_TOKEN}` sends that token to the entry's URL. A `!command` value is in `commandFields` instead.
- Availability is a typed reason, checked in this order: `operator-disabled` (`PI_WEB_DISABLE_MCP`), `internals-unavailable` (with the loader's `detail`), `builtin-disabled` (with the `settingsPath` whose `extensions` entry does it). `readBuiltinExtensionSwitches()` in `lib/builtin-extensions.ts` asks the SDK's `DefaultPackageManager` with only the two `extensions` lists (the project's only while trusted) and `onMissing: skip`, so `-builtin:mcp`, project `+`/`-` overrides and `!builtin:*` patterns resolve exactly as the resource loader resolves them, and no package is ever installed or looked up; it still scans the auto-discovered resource folders, read-only. Code mode reports the global preference, `-builtin:codemode` likewise, and `peekCodemodeSandbox()`: the settled self-test result, or `not-checked` while no normal session has run it since the server started — it never starts the self-test. With a cwd whose settings sessions load (`trust.trusted`, the rule `projectTrustReloadOptions()` applies when a session starts, inherited trust included; an unreadable store, never), `projectOverride` names the project's `.pi/settings.json` when its `defaultTools` decides Code mode there whatever the global choice: a list with a plain name replaces the global list, `+codemode` and all, and a modifier-only list is appended to it, so a `+codemode` / `-codemode` in it has the last word. `projectCodemodePreference()` (`lib/codemode-settings.ts`) does not reimplement that merge: it hands the project's raw text to the SDK's own `SettingsManager` twice, once beside each global choice, and an override is exactly the two agreeing, malformed values included (pi resolves `"defaultTools": null` to no tools at all). The file is read without pi's lock, as `readBuiltinExtensionSwitches()` reads it. Both reads of a trusted project's `.pi/settings.json` go through `readRegularFileText()` (`lib/regular-file.ts`): opened once with `O_NONBLOCK`, checked through `fstat`, at most `PROJECT_SETTINGS_MAX_BYTES` (1 MiB). A plain `readFileSync()` waits on a FIFO until something writes to it and, being synchronous, stalls the whole server; the switches read came first in the same GET, so guarding only the Code mode read left GET hanging. A file that is not regular (or too large) throws in the switches read, which the overview already treats as an unreadable file (every built-in on), and reports no override.
- `ProjectTrustStatus` also carries the nearest decision (`decision`, `decisionPath` as `trust.json` keys it, and `inherited` when that is an ancestor, compared by real path with `samePath()`), so exact trust, trust through a parent, an explicit `false` and no decision at all can be told apart, the last also for a fresh folder (`requiresTrust: false`). Reading it for a folder that requires no trust is new, and such a folder never failed on a broken `trust.json` before, so that failure goes to `decisionError` instead of throwing; a folder that requires trust still throws. `mayReadProjectConfigNow()` and `projectTrustReloadOptions()` do not need the decision and check `hasTrustRequiringProjectResources()` first, so neither locks `trust.json` for a fresh folder on every prompt or session start. `trustProject()` builds the status it returns from what it wrote instead of reading `trust.json` back: a second read can fail on the lock, and `POST /api/project-trust` would then answer 500 for a decision already on disk and skip rebuilding the cwd's wrappers.
- **The trust dialog lists the project's MCP servers** (`components/ProjectTrustDialog.tsx`), the visibility ADR 0006 traded per-entry approval for. `GET /api/project-trust` adds `mcpFile` and `mcpServers` to the status: `readProjectMcpServers()`, the same file-only read and masking as `/api/mcp`, filtered to the project's entries, where `replacesGlobal` marks one that replaces a global server of its name once trusted (the counterpart of `shadowedByProject`). Each entry shows its command line or URL, its `!command` fields, the host variables it reads (worded "sends … to this server" for HTTP, which is how a repository exfiltrates a token through a header) and, for `PI_WEB_PASSWORD`, a warning rather than a reassurance: Pi Web refuses such an entry, but the pi CLI reads the same file and does not. A refused entry shows neither line, since it never connects. AppShell's page-load fetch of the same route gets the listing too and ignores it; the dialog fetches it again when it opens, since the file can change in between, and hands the fresh status to AppShell (`onStatus`), so a folder trusted meanwhile, or no longer needing trust, is told so and not offered Trust. Trust stays disabled until that listing answers (`MCP_LISTING_TIMEOUT_MS`, 10 s), so the list cannot appear under a click already on its way; a listing that fails or times out stops holding it back. The listing never depends on `trust.json`: when the store cannot be read (unparsable, or locked past its ~200 ms wait while the pi CLI writes), GET answers 500 `trust-unreadable` with the listing beside it, otherwise the dialog would enable Trust with nothing listed and a later click would trust the folder unseen. A project file reported `link-outside` or `too-large` is not listed, yet the SDK reads it anyway once the project is trusted (it follows links and has no size cap), so those problems say so in the dialog rather than reading as "no servers". Every refusal carries a `reason` code (`cwd-invalid`, `cwd-not-directory`, `cwd-denied`; POST adds `request-denied` 403 and `content-type` 415 as the plugins route checks them, `trust-not-required` and `session-busy` 409, `internal` 500); AppShell keeps `{ error, reason }` and the dialog renders `mcp.reason.<code>`, showing the English `error` only as the diagnostic of an `internal` or network failure. Repository text (name, command, arguments, cwd, URL, field names) goes through `revealHiddenCharacters()` in `lib/mcp-server-display.ts`: controls, format characters (bidi overrides, zero-width), separators, variation selectors, blank fillers and every space but U+0020 become `\u{XXXX}` (never `\n`, which a Windows path like `C:\new` would collide with), an argument holding one is quoted, and the entry gets a warning line; the CSS keeps `white-space: normal`, so a run of spaces cannot push a value's tail out of view either. The command is quoted like an argument: the SDK spawns it with `cross-spawn` and no shell, so `./tools/lint --check` is one file name. Strings: `trust.mcp.*` for the dialog, and the shared `mcp.transport.*`, `mcp.field.*`, `mcp.server.*`, `mcp.fileProblem.<reason>` and `mcp.reason.<code>` keys, which Settings › MCP reuses instead of adding its own. Layout lives in `app/settings.css` (`.project-trust-*`), never inline: only the body scrolls, the trust error and buttons sit outside it, and the backdrop pads with the safe area, plus the iOS standalone fallback Settings uses. The dialog is offered only while `requiresTrust && !trusted` (by the restricted-mode banner, and by Settings › MCP's trust notice, which opens it above Settings), so a project trusted through an ancestor never shows it; Settings › MCP is where those servers are visible.

### Settings › MCP writes (`lib/mcp-config-file.ts`, `POST /api/mcp`)
- **Every `mcp.json` write goes through `lib/mcp-config-file.ts`**, never the SDK's `add/update/removeMcpServerConfig()` (the internals adapter loads them only for the contract test): those write in place with `writeFileSync`, with no lock, no atomic replace, no mode, and an untyped throw. The writer keeps their semantics byte for byte — parse (no BOM stripped), apply the edit to the parsed object, write the whole document back with the indentation of its **first indented line** (`"  "` when none) and **always** a trailing `\n` (whatever the file had), `enabled: true` and `exposure: "codemode"` delete their key, unknown keys at both levels stay, CRLF and compact arrays are rewritten as the SDK rewrites them — and `lib/mcp-config-file.test.mjs` compares its bytes with the SDK editor's on every fixture and operation, so an SDK change fails the test. It differs only where the SDK would write for nothing: an edit that changes nothing (switching on a server that is on) leaves the file's bytes alone. Server names are read with `Object.hasOwn()` and written with `defineProperty`: a plain `servers[name]` for `__proto__` returns `Object.prototype`, and a patch would then write `enabled` into every object in the process.
- **Lock, then atomic replace.** Writes to one real path run in a globalThis queue (`Symbol.for("pi-web:mcp-config-write-queue")`), so Pi Web's own writes never wait on each other's lock, and under a proper-lockfile lock on `<real path>.lock` (`realpath: false`, about 3 s of retries, then a typed `locked`) for other Pi Web processes; the pi CLI writes without a lock, so nothing serializes against it. The new text goes to `.<name>.<uuid>.tmp` beside the **real** file, `wx` and 0600 while written, then `chmod` to its final mode and `rename` over the real path, so a reader (an MCP host syncing before a prompt) sees the old file or the new one, and a symbolic link stays a link. Writing to the configured path instead would replace a dotfiles link with a regular file. Modes: the **global** file is always 0600 (it may hold literal secrets) and a folder created on the way 0700; the **project** file, often committed, keeps the mode it had (`chmod`, not the umask) and is 0644 when new.
- **Where it writes.** The global file is the user's: a link is followed wherever it leads, a dangling one by hand to the file it names, which the write creates. The project file is the repository's and follows the reader's link rule — `locateProjectMcpConfig()` and, for a file that does not exist yet, `projectMcpConfigCreatePath()` in `lib/mcp-config-read.ts`: the real path, a link in the file or in `.pi/` included, must be inside the allowed roots, and a dangling link (file or `.pi`) is refused rather than taken for a missing file, or a cloned repository could aim the write anywhere. The file is read through `readResolvedConfigFile()` (`O_NOFOLLOW | O_NONBLOCK`, `fstat`, 1 MiB for the project). Every refusal is an `McpConfigWriteError` (told by a `Symbol.for` brand, so a second module copy still counts) whose `reason` the route passes on as a 409 — `unparsable` (the message never quotes the file: `jsonErrorMessage()`), `invalid-shape`, `server-missing`, `name-taken`, `link-dangling`, `link-outside`, `not-a-file`, `too-large`, `locked` — with the file left untouched; `unreadable` is a 500 `internal`.
- **`POST /api/mcp`** takes `enable` / `disable` / `remove` (`{ scope, name }`), `set-enabled` (`{ enabled, servers: [{ scope, name }] }`, one write per file and a `results` entry per server, so a refused one leaves the rest switched) and `undo` (`{ token }`), each with the panel's `cwd` when it has a project, and answers with the overview GET would give (plus `undo`, `restored` or `results`), so the panel replaces its listing without a second request. Guards, in order: `isApiRequestAllowed` (403 `request-denied`), JSON content type (415), a JSON object (400 `invalid-request`), the cwd as GET checks it (`validateMcpProject()`, shared with Test, sign-in and `/api/project-trust`: `cwd-invalid` for an empty or relative path, `cwd-denied` for one outside the allowed roots, a `..` or a folder that does not exist, then `cwd-not-directory`), then **MCP off makes the server list read-only** (409 `mcp-off`, `mcpInternalsOrRefusal()` in `lib/mcp-entry-request.ts`, which Test and sign-in share) — `PI_WEB_DISABLE_MCP` (the operator's word, and the pi CLI reads the same files) or SDK modules that cannot load (nothing can be checked) — but **not** `-builtin:mcp`, and not the Code mode choice in the same panel, which belongs to the separate codemode built-in and is saved through `/api/tools/settings`, which a project can reverse: whether a global switch works must not depend on the folder Settings shows. A project server needs the cwd (400) and a decision, exact or inherited, that trusts the folder (403 `project-untrusted`; an unreadable `trust.json` 409 `trust-unreadable`): the MCP host's `mayReadProjectConfigNow()` rule, never `trusted`, which a fresh folder has with no decision. Turning on an entry that references `PI_WEB_PASSWORD` is refused (409 `web-password`, checked under the lock on the entry as it is then); turning it off and removing it work. An entry that is not an object (`"name": "text"`, `null`, an array) has no `enabled` to write: switching it is refused as `entry-not-object` (409, a `setMcpServersEnabled()` outcome of its own, `not-an-object`), never reported as `server-missing`, which would tell the user the file no longer defines it; Remove works. The reader marks such an entry `notAnObject` (its `enabled` reads true), so the panel never offers its switch. The edit itself runs under the lock, so a server removed or renamed since the listing gets `server-missing`, never a stale write.
- **Undo** (`lib/mcp-undo.ts`). A removal hands the raw entry and its index to a globalThis map (`Symbol.for("pi-web:mcp-undo")`, at most 100, oldest first) under a `randomUUID()` token with an unref'd 60 s timer whose cleanup deletes only the record it was set for; the response carries `{ token, scope, name, path, expiresInMs }` — remaining time, not a timestamp, so the browser's clock does not matter — and never the entry, which may hold literal secrets. `undo` takes the record once (a second click gets 410 `undo-unavailable`), re-checks a project's folder and trust as any write, and puts the entry back **where it stood** (`insertMcpServer()` with the index, rebuilding `mcpServers` in place so its position in the file stays), byte for byte when nothing else changed. A name the file defines again since is never replaced (409 `undo-name-taken`); a failed undo hands the record back for the time it had left, so it works once the cause is gone. It restores the entry as it was, a `PI_WEB_PASSWORD` reference included: undo returns the file to what it held a moment ago, and the panel shows such an entry as refused. A server restart drops pending undos.
- **The panel** (`components/McpConfig.tsx`): a server's detail header holds Remove and its switch (`ConfigDetailActions`, as Plugins does; a sidebar row is a button and cannot hold one), and under them a note both point at with `aria-describedby`: why they cannot be used (`mcp.reason.<block>`, from `mcpWriteBlock()`: `mcp-off`, `project-untrusted`, `trust-unreadable`; `entry-not-object` for an entry that is not an object; or `web-password` for the switch of such an entry while off), or under `-builtin:mcp`, which leaves the files writable, "Changes are saved to the file, but no session connects these servers", so the note never contradicts the banner; while the controls simply work there is no note, and the switch points at nothing (hosts read the files before every prompt, so a change applies at each open session's next message). The group heading's `n/m` count became `ConfigSidebarGroupSwitch`, described by the banner that blocks it — the MCP-off notice and the trust notice each add a sentence saying the servers cannot be changed here, and carry an `id` (`ConfigNotice`, `ConfigTrustNotice`, `ConfigSwitch` and `ConfigSidebarGroupSwitch` take `id` / `describedBy`). Switching a group on never sends an entry that references `PI_WEB_PASSWORD`, and no switch sends one that is not an object (`mcpGroupSwitchTargets()`); the note says how many PI_WEB_PASSWORD entries stayed off, and what the route refused goes under the heading (`ConfigSidebarGroupStatus`). **The switch reads on by `mcpGroupSwitchChecked()`, passed as `checked`, not by `enabled === total`:** some server is on and every server it *can* turn on is. With the plain rule a group holding a switched-off PI_WEB_PASSWORD entry stayed partial for good, so the switch always read off, every click asked to turn the group on and sent nothing, and the group could never be switched off from its heading. The `n/m` count still counts the file. Remove shows a notice with Undo until `expiresInMs` runs out, and focus moves to Undo when the removal took the focused pane with it, and to the selected row when the notice goes (`focusIfLost()`). One write at a time: every switch, Remove, Undo and Refresh wait while a change, a Code mode save or a load is on its way, and both Code mode options wait while a server change is (a change's answer carries the Code mode choice as read before a save still on its way, and `applyOverview()` would put it back over what the save had applied); a change's answer drops a load still on its way (it may predate the write). Waiting disables the pressed control, and a focused element that becomes disabled loses focus to `body` behind Settings: each handler notes the focused button before the change (`pressedButton()`) and hands it back as `focusBack` once answered, and the view gives it focus once nothing waits any more — after a refused change's reload too — or the selected row when the control went away or stays disabled (`focusAfterChange()` in `lib/stacked-dialog.ts`, only when focus fell to the page). A removal or an undo that worked does not: its focus goes to Undo and to the restored row, from effects declared before that one. Any refusal or timeout loads the overview again, because the file may no longer say what the panel showed and a change that timed out may have landed. The POST carries the cwd only when the listing covers the project: after a `cwd-*` refusal it would refuse global changes too. `postMcpAction()` shares the 15 s deadline (`withinDeadline()`).
- **Never exercise these writes against the live dev server or a real `~/.pi/agent`**: `app/api/mcp/route-write.test.mjs` runs every action against a `PI_CODING_AGENT_DIR` in a temp folder.

### Settings › MCP Test (`lib/mcp-test.ts`, `POST /api/mcp/test`)
- **The route re-checks what a session's start would** (`readConnectableMcpEntry()` in `lib/mcp-entry-request.ts`, which sign-in shares), because Test starts a process or contacts a URL and may run a `!command`: origin (403 `request-denied`), JSON (415), `{ scope, name }` (400 `invalid-request`), the cwd as GET checks it (`cwd-*`; required for a project server), then MCP off — `PI_WEB_DISABLE_MCP` or SDK modules that cannot load (409 `mcp-off`), but not `-builtin:mcp`, under which Test stays an explicit action — and for a project server a decision, exact or inherited, that trusts the folder (403 `project-untrusted`, 409 `trust-unreadable`; the host's `mayReadProjectConfigNow()` rule, never `trusted`). The entry is read from its file by `readMcpServerEntry()` (`lib/mcp-config-read.ts`, the listing's parse and link rule: a file problem is its 409, an absent name `server-missing`, looked up among the parsed entries so `__proto__` is just a name), never taken from the browser, then must be an object (409 `entry-not-object`), pass `validateMcpServerConfig()` (409 `server-invalid`, new) and not reference `PI_WEB_PASSWORD` (409 `web-password`). A switched-off entry can be tested before it is turned on. A global stdio server runs in the panel's project when the request names one (checked like any cwd), else in `homedir()`; the result names the folder. That folder is also the MCP root the server is sent.
- **Connecting is a session's connection**: the SDK's `McpServerConnection` with `createPiWebMcpTransportFactory()` (scrubbed env, `inheritEnv: false`) wrapped to capture every transport, and the SDK's `McpOAuthCredentialStore` (`mcp-auth.json` in the agent dir, which a test of an OAuth server creates as a session would), guarded for an OAuth entry so a sign-out during the test bars its writes and its record (see **Settings › MCP sign-in**). A 401 with no stored token reads `needs-auth`.
- **Bounded at every step, since a response must never wait on a close.** Each request gets min(the entry's `timeout`, 15 s) (`MCP_TEST_REQUEST_TIMEOUT_MS`, a copy of the entry; the SDK default is 60 s). The test has a 20 s deadline (`MCP_TEST_DEADLINE_MS`), aborted early once every caller's request signal has (refcounted: a press joined by another tab keeps it alive). On abort it calls `connection.close()` (marks it closed before its first await, which also ends an HTTP retry between attempts) and **closes the captured transports directly**: that fails the pending handshake at once, while `connection.close()` alone leaves a stdio child running until its request times out. Closing is awaited only `MCP_TEST_CLOSE_WAIT_MS` (2 s): `StdioTransport.close()` waits for the child's `close` event, which a grandchild outside the process group can hold off for good, and `connection.close()` waits for an OAuth refresh; both carry on in the background. The SDK's own `connectOnce()` awaits `client.close()` inside a failed attempt, so even a plain failure of a SIGTERM-ignoring server takes up to the 2.5 s SIGKILL; the deadline race covers that too. Read the connection's `state` before closing it: `close()` sets it to `closed`. **Closing is in a `finally`**: building the result must never leave a stdio server running, and pi-mcp checks only a listed tool's `name` and `inputSchema`, so `describeTool()` reads `description` / `title` / `annotations` only where they are strings (a numeric description used to throw, answer 500 and leak one process per press). The SDK's `getMcpToolExposure()` indexes `toolExposure` plainly, so a tool named `constructor` got `Object.prototype`'s function as its exposure; `toolExposure()` passes it a prototype-free copy and falls back to the server's exposure for anything but the five values. An injected `connect` that ignores the abort is still cut off `closeWaitMs + 500` after it.
- **`!command` entries run one at a time.** A `!command` runs synchronously (`execSync`, up to 10 s) and blocks the event loop, deadline timers included, so nothing interrupts one. Tests of entries whose resolved fields hold one (`runsShellCommand()`: a stdio entry's env, an HTTP entry's headers and `oauth.clientSecret`; an env on an HTTP entry runs nothing) wait in a globalThis promise chain (`Symbol.for("pi-web:mcp-test-command-queue")`) for at most the deadline again; one that never got its turn answers `queueTimedOut` and is not recorded. A test that gives up its place releases it at once without letting the next jump the ones ahead. Presses on the same entry (scope, file, name, `configKey`, cwd) join the test under way (`Symbol.for("pi-web:mcp-test-flights")`). A test every caller gave up on leaves that map at once, while it still closes, so a press in that window starts a new test instead of joining one that can only answer "no answer" and record nothing.
- **Nothing literal reaches the browser.** The SDK quotes a failed `!command`'s text (`Failed to resolve … from shell command: <text>`), and a server may echo its env, its key or its URL, so `createTestRedactor()` masks, in `error`, `stderr`, the tool names and descriptions and `serverInfo` (all server-written text): a `!command` text wherever the SDK quotes it after `from shell command: ` (any length; the SDK discards the command's own stderr, so nothing else can print it) and elsewhere as a word from 6 characters; literal env / header / `oauth.clientSecret` values and what the transports resolved them to (the entry's own env names only; the rest is the host's sanitized env); the command, arguments and URL as GET masks them; and the parts those masks hide, also where a message quotes one on its own (`urlSecretParts()` / `argSecretParts()` / `commandSecretParts()` in `lib/mcp-secrets.ts`: a query value, a userinfo password, a flag's value, each also percent-decoded) and the URL as `new URL().href` spells it. Values shorter than 6 characters stay, so `1` or `true` cannot garble a message. A whole secret is replaced wherever it appears; a word split from a value (`Bearer <token>`) or a command text only where it is not part of a longer word, so `!gh auth token` leaves "authentication" alone and `!env` never masks the SDK's own `env "TOKEN"`. **Mask, then shorten:** `error` keeps its first 2,000 characters and `stderr` its last 2,000 (the transport keeps 64 KiB), each masked over a 64 KiB window first, so a cut never leaves half a secret; an `error` used to be unbounded (a JSON-RPC error may be 16 MiB) and sat in the status store, sent with every GET. The SDK appends the stderr tail to its message; `splitStderr()` moves it to `stderr` at the first line break whose remainder is part of the transport's stderr.
- **Status store** (`lib/mcp-status.ts`, `Symbol.for("pi-web:mcp-status:by-config")`). A test records `{ origin: "test", ...result }` under `scope\0sourcePath\0name` with the entry's `configKey` (`mcpConfigKey()`, the HMAC GET reports), unless every caller gave up before it settled. Each entry holds one record per `configKey`, never one in all: a writer behind the file (a session that has not synced an edit yet) must not replace the record for the entry as it is now, which the next read would then drop as stale. `readMcpOverview()` attaches the record whose key matches the file and deletes the entry's others (an edited entry reads untested, even once edited back), records of a file read without a blocking problem whose name it no longer defines are pruned, and the map holds at most 500 records, the oldest of the entry written longest ago first out. Session hosts write theirs too (see **MCP host**), and so does a sign-in (`afterSignIn` on the reconnect after it, see **Settings › MCP sign-in**); the latest write for the same content wins. The symbol changed name with that shape: a dev server keeps `globalThis` across hot reloads, and the new code would otherwise read the old map. Any later change of a globalThis store's shape needs a new name for the same reason.
- **The panel** gives each server a **Connection** row right under Status: the last status (`connected` with its tool count and time, `needs-auth`, `failed` with the SDK's message and a scrolling `<pre>` of stderr, a timeout as "No answer"), the server's name and version, its resources, and for stdio the folder it ran in; then why Test cannot be used (`mcpTestBlock()`: the write blocks `mcp-off` / `project-untrusted` / `trust-unreadable`, then `invalid`, `web-password`) as visible text that the disabled button, which sits in the detail header before Remove (`McpTestButton`), points at with `aria-describedby`; an entry with a `!command` field (env, header or `oauth.clientSecret`) adds that its tests wait for other such tests; "No answer" says Pi Web stopped the test, not the server, which for HTTP it only stopped waiting for. A connected test adds a read-only **Listed tools** row: each name, a `read-only` tag for `readOnlyHint` (what read-only sessions require), its exposure where `toolExposure` makes it differ from the server's, and the description's first line. A test writes no file, so it never sets `busy`: switches, Remove and Refresh keep working, and one test per server runs beside them. Each answer is kept per server (`McpTestRun`) and shown over the listing's status while it is about the entry shown (same `configKey`) and newer (`mcpWithTestResults()`), so a load already on its way cannot hide it; a Sign out that worked drops the kept answer, and an answer to a test sent before it (`startedAt` ≤ `signedOutAt`, `mcpTestRunAfterSignOut()`), since the route forgot the entry's statuses and the old answer would otherwise read Connected until Settings closed; a failed request or a queue timeout keeps the last result beside a `role="alert"` line, worded as a test's (`MCP_TEST_REFUSAL_KEYS`: also the file problems, `entry-not-object` and `invalid-request`, whose `mcp.reason.*` wording speaks of writes) rather than a change's, and carries the `configKey` it was about (`mcpTestRunFor()` hides it for an entry edited since). **An answer that shows the listing is stale loads it again** (`mcpTestAnswerOutdates()`), as a refused change does: any refusal with a reason, or an answer for another `configKey` than the listed one (edited outside the panel), whose result the listing would otherwise never show. **Test requests are never aborted** — not when Settings closes, not at the client's 60 s wait (`MCP_TEST_TIMEOUT_MS`: deadline, queue, close and a blocking `!command`; `withinDeadline(…, { abortAtDeadline: false })`): Next aborts `req.signal` when the request is aborted, and the route stops a test nobody waits for and records nothing, so an aborted request would lose the result the "press Refresh" message promises. Only closing the page stops one. Test is disabled while it runs, so it takes focus back once answered (`focusIfLost()`).

### Settings › MCP sign-in (`lib/mcp-sign-in.ts`, `/api/mcp/sign-in`)
- **It runs as `pi mcp login` does** (SDK `extensions/mcp/cli.js` login()): connect once through the same connection a Test opens (`openTestConnection()` / `observeTestConnection()` / `closeTestConnection()` in `lib/mcp-test.ts`, kept open) to learn whether the server asks for a sign-in and to record its challenge; already connected ends `done` (`alreadySignedIn`), any other failure `failed` (`connect-failed`); then the SDK's `signInMcpServer()` with `connection.oauthSettings()` (resolved while the entry's place in the `!command` queue is held: `oauth.clientSecret` may be one), the challenge and a prompt; then `connection.reconnect()` with the new tokens. Each connect has the test's deadline once it has its turn in the queue, never across the wait for the browser. Only an HTTP entry without an `Authorization` header signs in (`mcpOAuthUrl()`, the SDK's `usesOAuth` rule; the integration test pins it against `connection.oauthUrl`), else 409 `sign-in-not-oauth`.
- **The flow outlives every request.** `POST /api/mcp/sign-in` runs the route checks a Test runs (`readConnectableMcpEntry()`), starts the flow and answers at once with it; the panel then polls `GET /api/mcp/sign-in/[flowId]` about once a second. Flows live in a globalThis registry (`Symbol.for("pi-web:mcp-sign-in")`) under a `randomUUID()` id, with unref'd timers, and nothing ties one to a request signal or a stream (the provider login route aborts its flow when its SSE closes, so it could not be reused): a sleeping phone or a closed Settings loses nothing, and pressing Sign in again joins the flow.
- **One flow per server URL per process** (keyed as `mcp-auth.json` keys it, `String(new URL(url))`): the SDK keeps one PKCE verifier and one `state` per URL in that file, so two sign-ins of a URL overwrite each other's and both fail with `invalid_grant`. A second start, from another entry of the URL or another tab, joins (`joined: true`; the flow names the entry that started it, and the reconnect's result is recorded for that entry only, so the joining row's ending names that entry and sends the user to Test connection instead of pointing at its own Connection row: `mcpSignInShared()`, `mcp.signIn.shared.*`). A flow of a URL whose previous run is still unwinding (cancelled or expired while a network request had not answered) waits for that run before it connects. A `pi mcp login` in a terminal is not serialized against.
- **Five minutes, and the SDK cannot be aborted.** `signInMcpServer()` takes no AbortSignal, and its loopback callback gives up after 5 minutes (pi-mcp `OAuthCallbackServer`). The flow expires `MCP_SIGN_IN_TTL_MS` (5 minutes) after it starts, so first; the only way to stop the SDK is to answer its `promptForRedirectUrl()` with "" (McpSignInCancelledError). A cancel or an expiry answers a waiting prompt at once; one that arrives before the SDK asks (discovery still running) is kept and answered the moment it asks; one before `signInMcpServer()` was called stops the run there. An ended flow stays readable for `MCP_SIGN_IN_KEEP_MS` (60 s), then `GET` answers 404 `sign-in-unknown`. Discovery, registration and token requests have no timeout of their own (undici's defaults apply), so a run can outlive its flow; it then changes nothing about the flow.
- **A pasted address is checked first**, since the SDK ends the whole sign-in on a bad one: `pasteMcpSignInRedirect()` refuses with 400 and leaves the flow waiting when the text is not a URL (`redirect-invalid`), carries another `state` (`redirect-state-mismatch`; compared with the `state` the SDK stored last, watched through the store it is given, which is the one it checks against, the page's own `state` only as a fallback), is an `error=` answer (`redirect-denied`, with the server's description as `error`), or has no `code` (`redirect-no-code`); a paste while nothing waits is 409 `sign-in-not-waiting`. The loopback callback (a browser on the same computer) finishes the flow with no paste: the SDK then aborts the prompt's signal, which moves the flow to `finishing`.
- **No browser at all is a normal ending**: a stored refresh token renews the tokens inside `signInMcpServer()`, which never shows a page (`refreshed`). Starting a sign-in may also delete the stored client registration and tokens (the SDK drops a registration whose redirect URI is not the new one), so the panel says so beside the button.
- **What it records.** The first connect's result is the entry's status, as a Test's would be (`needs-auth` while the browser is awaited); the reconnect's is recorded with `afterSignIn: true`, which the Connection row sums up in sign-in words (`MCP_SIGN_IN_SUMMARY_KEYS`). An open session's own record stays `needs-auth` until it reconnects at its next turn, and the sign-in's record is the newer one. Errors go through the test's redactor plus the resolved client secret (`createTestRedactor(…, resolvedSecrets)`). Before the reconnect, which may come minutes after the route's checks, the route's `mayConnect()` asks again whether a project entry's folder is still trusted (and MCP not off); if not, the flow ends `done` without connecting.
- **Sign out** is `POST /api/mcp { action: "sign-out", scope, name }`: the URL is read from the entry's file under the checks of any change to it (a project entry's folder must be trusted), the SDK store's `remove(url)` deletes the URL's tokens and client registration (`pi mcp logout`), a missing `mcp-auth.json` is not created to find nothing in it, and the entry's status records are forgotten (`forgetMcpEntryStatuses()`), since signed-out connections no longer see what they found. Open sessions read the store on every request, so they lose access at their next one (a refresh one of them already has on its way can still write its tokens back, as with `pi mcp logout`). The answer is the overview plus `signedOut: { scope, name, removed }`.
- **Signing out bars every run of the URL from writing, before it removes anything.** Cancelling is not enough: a cancel only answers a prompt that still waits, while a code exchange (a pasted address, the loopback callback) or a refresh (`signInMcpServer()`'s, or the connection's own during a connect) that is already on its way stores its tokens whatever happens to the flow, which signed the URL back in right after the removal while the panel said "Signed out". So `signOutMcpServer()` first counts a sign-out for the URL key (`noteMcpSignOut()` in `lib/mcp-sign-out.ts`, under `Symbol.for("pi-web:mcp-sign-outs")`, which takes over the map an older dev-server registry held as `signOuts`), then cancels the active flow, then removes; every run writes `mcp-auth.json` only through stores that call its `McpSignInWriteGuard` before each write (the SDK sign-in's store through `watchedStore()`, the connection's through `guardedCredentialStore()`, a subclass of the SDK's store passed to `openTestConnection({ credentials })`), which throws `McpSignedOutError` once the count moved since the flow started. The SDK's writes are synchronous, so the check and the write cannot be split by the removal. A run started after the sign-out writes normally. Waiting for the run to unwind instead would not do: its network requests have no timeout of their own. **A Test is such a run too**: an OAuth entry's test connection gets `guardedCredentialStore()` with a guard taken when the test starts (`mcpSignOutGuard()`), so a refresh it has on its way when the URL is signed out (an expired access token is refreshed before the first request, up to 15 s per request) stores nothing; its result is then not recorded, since the sign-out forgot the entry's statuses, and the URL's sign-out count is part of the flight key, so a press after a sign-out never joins a test started before it.
- **The panel** (`components/McpSignIn.tsx`, in an HTTP server's Sign-in row): the signed-in hint, Sign in (primary) and, unless `mcp-auth.json` holds nothing for the URL, Sign out (`oauthStateStored`: any record under the URL key, which includes the client registration and PKCE state a cancelled or expired sign-in leaves without tokens and which Sign out removes as `pi mcp logout` does; `signedIn`, an access token, only words the hint); while a flow runs, its phase as a `role="status"` line and Cancel instead (disabled in `finishing`, the authorization server having answered, with a visible line saying so that Cancel's `aria-describedby` points at). Sign in waits while a Sign out of the row is on its way, which would cancel it on arrival. In `authorize`, `OAuthPastePanel` is always shown with the page as a link (only an `http(s)` URL becomes a link: the page comes from the server's metadata), the address the browser is sent back to, and the 5-minute limit; the box is never focused by itself (a phone keyboard would cover the link), has an accessible name, waits while a paste is checked, and submits from its button or Cmd/Ctrl+Enter, never a plain Enter (`plainEnterSubmits={false}`, the cross-cutting paste-box rule; Models' subscription box keeps plain Enter); no Enter submits while an input method composes (`oauthPasteKeySubmits()`). A failed cancel's or a refused paste's line goes once a poll reads the flow ended. Blocks (`mcpSignInBlock()`, the Test route's; `mcpSignOutBlock()`, the write blocks and a refused entry) are visible text the disabled buttons point at. The Connection row's needs-sign-in words never send the user to `/mcp` in a chat. "Signing in may replace what is stored for this URL" shows only while something is stored (`offersSignOut`). A sign-in writes no `mcp.json`, so it runs beside changes like a Test; Sign out goes through `runAction()` (`sign-out:<key>`). When a polled flow ends (`mcpSignInJustEnded()`), the overview is read again. Starting is never aborted (`postMcpSignIn()` leaves the request running at its 15 s deadline, as `postMcpTest()` does), and closing Settings stops only the polling.
- Tests: `lib/mcp-sign-in.test.mjs` drives the registry with a stub connection and `signInMcpServer` (phases, every paste refusal keeping the flow, the stored state, the loopback callback, refresh without a page, already signed in, connect failures, masked errors, cancel before the run / before the page / while waiting, expiry and forgetting, joining, a run waiting for the previous one, no poller, `mayConnect`, the resolved `oauth.clientSecret` masked by the connection's own `redact()`, sign-out, and a sign-out barring a code exchange or a cancelled run's refresh still on its way while a sign-in started after it stores normally, with `guardedCredentialStore()` over the SDK's own store); `lib/mcp-sign-in.integration.test.mjs` runs the SDK's own flow against `lib/__fixtures__/mcp-oauth-server.mjs` (a local MCP server and authorization server with registration, PKCE and refresh tokens) in a temp `PI_CODING_AGENT_DIR`: a pasted address, the loopback callback, already signed in and a connection-side refresh, a cancel closing the loopback listener, sign-out, and a sign-out while a sign-in's or a Test's refresh is held at the token endpoint (`hooks.beforeRefresh`) storing nothing; `app/api/mcp/sign-in/route.test.mjs` covers the routes' guards, 404s, refusals, an untrusted project's `!command` header never run, a project sign-in finished after trust is revoked or MCP is turned off ending without the reconnect (the route's own `mayConnect()`), joining, and the sign-out action.   - **One step per folder at a time** (a globalThis chain, `Symbol.for("pi-web:fresh-folder-trust-locks")`, keyed by the real path), and inside it the folder is **checked again**: the SDK's `hasTrustRequiringProjectResources()`, and `hasTrustRelevantEntries()`, an `lstat` of the same entries (`TRUST_REQUIRING_PROJECT_ENTRIES`, a copy of the SDK's module-private list that `lib/project-trust.test.mjs` compares with the SDK's source), a `.pi` that is a link to nothing and `.agents/skills` in an ancestor, because `existsSync` skips a dangling link that starts counting the moment its target appears; then `getEntry()` must be null. ### Paste import (`lib/mcp-import.ts`)
- Other clients store literals, but pi resolves `${NAME}`, `$NAME` and a leading `!command` in env values, header values and `oauth.clientSecret`. Literals there are escaped (`$` → `$$`, a leading `!` → `$!`); unescaped, a pasted `"!curl … | sh"` would run on the Pi Web host at every connection. `command`, `args`, `url` and `cwd` are used raw by the SDK and must never be escaped. Only `pi mcp add` and the rawPi toggle keep values as written, and a `!command` is then noted (`shell-command-value`). `lib/mcp-import.integration.test.mjs` pins the round-trip through the SDK resolver.
- References are translated into `${X}` (`${env:X}`, `{env:X}`, `%X%`, Gemini's `$X`) only in those three resolved fields. pi substitutes nothing anywhere else, so a reference in `command`, `args` or `url` becomes a field to fill in; only a leading `$HOME` / `${userHome}` becomes `~` and `${workspaceFolder}` becomes `.`. Never trust `validateMcpServerConfig` to clean an entry: it returns the object it was given and accepts milliseconds as seconds. The importer builds a fresh object from known keys, notes every dropped key, and reads a timeout in its client's unit (Gemini milliseconds, Cline seconds; a guess is a warning).
- The `pi mcp add` grammar is a port of the module-private SDK `cli.js` (`maxPositionals` 2, `-l`, an option on the wrong transport refused, splitting at the first `=`, `--help` anywhere prints help, an empty name refused). The integration test runs the real `runMcpCommand` into a temp dir and compares the written entry byte for byte, mixed shell quoting included, so an SDK change to the CLI fails the test. Quoted and unquoted text of one word is joined before any grammar reads it (`'A=$'B` is `A=$B`).
- `parseMcpImport()` and `fillMcpImportFields()` never throw: the add route (`POST /api/mcp`, action `add`) re-parses the request body, and a throw is a 500. Decode with a guarded helper (a malformed `%zz` in userinfo threw `URIError`), keep an impossible `$'\U…'` code point as text, and bound any regex run that can rescan (the `…_here` placeholder pattern was quadratic). The robustness test feeds every prefix of every sample through parse and fill.
- Literal secrets and password fields follow `lib/mcp-secrets.ts` (`literalSecretFields`, `maskArgs`, `maskUrl`, `isSecretName`), never a classifier of the importer's own: the server's `secret-global-only` refusal and the panel's masking must agree (the add preview masks none of it, only typed passwords). `fillMcpImportFields()` returns `secretPaths` (typed password values plus literal secrets) and accepts `{ reference: "NAME" }` for a field whose targets pi resolves, stored as `${NAME}` and not a secret path; `PI_WEB_PASSWORD` is the route's to refuse.
- A server name pi accepts is kept as written; only an invalid one is sanitized. A derived name avoids `takenNames`; a name the source chose that is already taken keeps its name and gets `name-taken` with a `suggestedName`, so the route can answer its typed 409.
- Command lines that manage a CLI (`pi mcp remove|login …`, `claude|codex|gemini mcp <subcommand>`, `pi install|remove|update …`) are refused with `cli-not-a-server`: imported as a stdio server, the Test after Add would run them on the host. `claude mcp serve` is a server and still imports.
- Notes are `{ code, params }` (`MCP_IMPORT_NOTE_CODES`, 84 codes with severities in `MCP_IMPORT_NOTE_SEVERITY`); a field's `label` and `description` are source data, shown as they are. The browser preview and the server re-parse run the same pure code, so client code rules apply: no regex lookbehind and no `URL.canParse` (old Safari).

### `/mcp` in the composer (`lib/mcp-command.ts`, `hooks/useAgentSession.ts`)
- **Only a bare `/mcp`, and only when pi's built-in owns it.** `handleBuiltinSlashCommand` opens Settings › MCP (`onOpenSettings("mcp")`, AppShell → ChatWindow → the hook, as `/session` does with its panel) when the session's command list has the built-in `/mcp` (name `mcp`, `sourceInfo.path` `builtin:mcp`) or nothing that answers `/mcp` (MCP off, `-builtin:mcp`, Chat-only): `bareMcpOpensSettings()`. Another extension's `/mcp` (the SDK then drops the replaceable built-in) and a prompt template named `mcp` (pi expands it when no extension command has the name) keep the message, which is sent as before. Several extensions' `/mcp` open Settings: pi renames them `mcp:1`, `mcp:2`, … and looks a command up by its exact name, so a bare `/mcp` would run neither and reach the model as the text "/mcp"; the panel's `hostInactive` notice names the first. Every subcommand is sent too: `/mcp login`, `logout` and `reconnect` act on that session's own connections. A third-party input handler that catches `/mcp` cannot be seen from the list.
- **Never guess the owner.** The palette starts `get_commands` as `/mcp` is typed and Enter often comes first, so the case awaits the request under way (`slashCommandsLoadRef`), else uses the loaded list (`slashCommandsRef`, written only through `replaceSlashCommands()`), else asks. Every request and set_tools' clear (`clearSlashCommands()`, which also forgets the request under way) move `slashCommandsGenerationRef` on, and only a request still current writes its answer: a request set_tools outdated used to put back the list of the session it replaced, so after a switch to Chat only another extension's stale `/mcp` kept sending a bare `/mcp` to the model. A failed request is `null`, never an empty list: an empty list is a Chat-only session's and opens Settings, while a list that cannot be read sends `/mcp` as before. Guessing either way would swallow another extension's `/mcp` or spend the host's 10 s connect wait on a message Settings should have taken.
- **Nothing of a prompt happens.** The case returns before `onSend`: no `/mcp` bubble, no `promoteNewSession()` sidebar row in a new chat (the command list still needs the session `ensureNewSession()` builds, as typing `/` does), and `complete()` shows no notice for an `action` (`openSessionStats`, `openSettings`). It works while a run streams: `sendQueued` offers a bare `/mcp` to the handler first and queues it as a steer / follow-up only when unhandled, and `handleSend` lets it through (`offersBuiltinSlashCommandWhileStreaming()`); `canRunBuiltinSlashCommandWhileStreaming()` still lists only the composer's own built-ins. Enter on the palette's built-in `/mcp` submits at once (`submitsSlashCommandOnEnter()`), as Enter does before the list has loaded; other extension commands still complete to `/name ` first, and `isExactSlashCommand()` is unchanged.
- **Focus moves into Settings.** `SettingsPanel` focuses its dialog element (`tabIndex={-1}`, no outline) in a layout effect and gives focus back to the opener on close (`focusModalPanel()`), unless focus went elsewhere meanwhile; on a coarse pointer a text field is not refocused, since that raises the keyboard again. Before, focus stayed on the composer behind the modal, as the textarea is disabled for one render only: the next Escape reached ChatInput's handler first (React listens on `document` and registered before Settings did), stopped a running agent and marked the key handled, so Settings stayed open; typing went into the hidden composer, and a phone kept its keyboard up over Settings. Opened from the sidebar, Settings left focus behind it too, though Escape worked there.
- `lib/mcp-command.test.mjs` pins the rule, `lib/builtin-extensions.integration.test.mjs` the SDK facts it rests on (the built-in's path, its replacement, `mcp:1` / `mcp:2`, and that a bare `/mcp` runs the replacement but reaches the model as text beside two) through a real wrapper, `hooks/mcp-slash-command.test.mjs` runs the hook's own callbacks (outdated requests included), `components/ChatInput.test.mjs` the streaming and Enter paths, and `lib/stacked-dialog.test.mjs` the focus move, with the composer's Escape that used to win.

### Model defaults for new sessions
`GET /api/models` returns `defaultModel` read from `~/.pi/agent/settings.json`. `ChatWindow` pre-selects this on mount for new sessions. Explicit browser model/thinking selections are applied atomically during AgentSession construction and are **session-scoped**: startup never writes `settings.json`, and neither does a mid-session `set_model` / `set_thinking_level`. That matches pi since 0.84.3, where `/model` and `/thinking` only persist on Ctrl+S; before that pi-web wrote every new-session pick back, so a one-off model silently became the TUI's default too (#871).

The explicit "save as default" is the star on each row of the model selector and the reasoning menu, the Web counterpart of Ctrl+S: `PUT /api/models/default` writes `defaultProvider`/`defaultModel` or `defaultThinkingLevel` (`lib/default-preferences.ts`), and the hook then also selects that row for the current chat, as Ctrl+S does. The route only accepts a model the selector can offer (in the resolved `enabledModels` scope), so a saved default always takes effect. A project `.pi/settings.json` value for a written key wins over the global one, so the route refuses with `409 { reason: "project-scope", settingsPath }` instead of reporting a save the user would never see. The model star marks the resolved `defaultModel`; the reasoning star marks `savedDefaultThinkingLevel`, the raw setting, because the resolved `defaultThinkingLevel` also folds in `:level` pins and per-model levels that the global write does not change. Both menus render `SelectorRow` (`components/SelectorRow.tsx`), which highlights the whole row like a session-list row and keeps one right-hand gutter for the star: the default row shows a small static filled star there, and every other row's save button floats into the same spot on hover or keyboard focus (always visible on touch screens, which have no hover). `ModelSelector` only shows stars when given `onSetDefault`; the subagent profile form reuses it without one.

The reasoning control stays usable while a run streams (#851). pi-agent-core snapshots `reasoning` into the loop config when a run starts, but `AgentSession`'s `prepareRequest` / `prepareNextTurnWithContext` hooks re-read `agent.state.thinkingLevel` before every model request, so `set_thinking_level` mid-run applies from the next request; only the response already streaming keeps its level. `lib/thinking-level-mid-run.integration.test.mjs` pins that SDK behavior with the faux provider — if an SDK upgrade breaks it, disable the control again rather than let it change nothing.

### Remote provider catalogs
pi's built-in model lists are generated when the SDK is built and pi-web pins one SDK version, so a model a provider ships after that release is invisible until pi-web publishes a new version (#914). The SDK carries the other half: each built-in provider is wrapped in a pi.dev catalog overlay that `ModelRuntime.refresh()` fetches and persists to `~/.pi/agent/models-store.json`, and restoring that overlay needs no network. Both of pi-web's refresh paths ask for the offline half only (`createAgentSessionServices()` and `lib/provider-usage.ts` pass `allowNetwork: false`), which is why running the pi CLI once used to be the fix — the CLI refreshed with the network on and pi-web read what it left behind.

`lib/model-catalog-refresh.ts` runs that network pass, and **only when the user asks for it**: the "Refresh catalog" button in `EnabledModelsSection` posts to `/api/models/refresh`. Nothing refreshes catalogs on a timer or on another request's path — a pass fetches a catalog per authenticated provider, and a save must not wait on a slow one, the same reason `/api/auth/api-key/[provider]` stores the credential itself instead of calling `ModelRuntime.login()`. `refresh()` is called with `force: true`, since pressing the button is exactly a request to skip the SDK's four-hour freshness window, but *without* `allowNetwork`, so the runtime keeps applying its own `PI_OFFLINE` rule instead of pi-web overriding it; the module reports `reason: "offline"` rather than pretending a pass ran. `shareModelCatalogRefresh()` joins concurrent presses for the same providers so two tabs cannot race over the store file.

Change detection compares the model ids and names the runtime exposes, never the stored bytes: a successful revalidation rewrites `checkedAt` and `etag` on every pass. It only decides whether `invalidateModelsCache()` runs and whether the panel reloads — the overlay itself reaches the UI through the ordinary `/api/models` and `/api/models/enabled` loads, which build a fresh runtime that restores the store, so the refresh route never returns a model list of its own.

### `enabledModels` scoping
The `enabledModels` setting uses pi's `--models` syntax: minimatch globs against `provider/modelId` or a bare `modelId`, fuzzy matching for non-glob patterns, and an optional `:thinkingLevel` suffix. Never compare those patterns as literal strings — `lib/model-scope.ts` delegates to the SDK's `resolveModelScopeWithDiagnostics()` so pi-web and the TUI agree on the visible model list, and falls back to all available models when patterns resolve to nothing. `startRpcSession()` resolves that scope before creating an AgentSession and passes the selected initial model, thinking pin, and SDK-native `scopedModels` atomically; `GET /api/models` reuses the helper only for selector data, `thinkingLevelPins`, and `modelScopeWarnings` display.

Editing that setting from the Models panel goes through `/api/models/enabled`, never through pattern strings composed in the browser. Each toggle is a **minimal edit** of the stored list (`lib/enabled-models.ts`): a pattern that matches no available model is preserved verbatim, only the pattern covering the switched-off model is expanded in place (keeping its `:level` suffix), and every provider that ends up fully enabled with two or more entries collapses back into one glob — pi refreshes provider catalogs from the network into `models-store.json`, so an enumerated list rots when a model is renamed (deepseek's `deepseek-v4-flash` became `deepseek-flash`), while a glob heals itself. A lone exact reference is a deliberate pick and is left alone. **Never assume `provider/*` covers a provider**: pi matches with minimatch, whose `*` stops at `/`, so that glob silently misses every nested model id (`commandcode/sakana/fugu-ultra`, most OpenRouter ids) — writing it turned "enable all" into 15 of 71 models. `resolveProviderGlobs()` resolves `provider/*` then `provider/**` and keeps one only when its match set is exactly the provider's models; a provider that neither covers is written model by model. Also never rewrite the whole list from `getAvailable()` the way the TUI's `/scoped-models` does — it only sees providers that currently pass `checkAuth()`, so that would delete every entry for a provider whose credential is missing right now, and flatten globs and pins.

Disabling the last enabled model is refused with `409 { reason: "last-model" }`: pi falls back to every model when a scope resolves to nothing, so an empty list silently means the opposite. Writes always target the global settings file; a project `.pi/settings.json` replaces the global array instead of merging, so the route reports `scope: "project"`, renders the switches read-only, and returns that file's path as `settingsPath` — the banner names the file it just wrote (`~/.pi/agent/settings.json · enabledModels 20/104`) instead of describing the effect in prose. Built-in *and* extension-registered providers get per-model switches; models.json providers are switched as a whole by `EnabledModelsProviderSwitch` in their detail header, next to Delete, because a custom model can simply be deleted and both bulk buttons only ever sent the same provider-wide write. That switch is on only when every model of the provider is on, so a partial selection reads as off beside the sidebar's `1/2` badge and one click completes it; reading it as "any enabled" would leave partial unreachable in both directions once the last-model guard blocks the way down. Why it cannot move is its tooltip, not body text. `op: "prune"` is the only operation that drops unmatched entries, for cleaning up after such a rename; everything else preserves them. Saving models.json re-reads the switches through `op: "resync"`, which repairs the stored patterns against the new catalog: it rewrites renamed **models** and then renamed **providers**, **cuts back entries whose provider prefix no longer scopes them**, and re-asserts the providers that were fully enabled before the save. (Model references first: they still spell the old provider id, which the provider rewrite would otherwise have replaced already.) All three are needed because a pattern's meaning depends on the catalog. pi matches a pattern against the bare `modelId` as well as `provider/modelId`, so `stepfun/*` also matches another provider's model whose id *is* `stepfun/Step-5-Preview` — renaming a provider to `stepfun` silently enabled three `commandcode` models, and switching stepfun off then wrote them into the file. In the other direction, renaming a model to an id with a slash drops it out of `provider/*` (minimatch `*` stops at `/`), so a fully enabled provider silently loses it. A model renamed in the panel is a known move, not the kind of mismatch worth preserving: leaving `stepfun/ddd` behind after it became `stepfun/ddd1` loses the selection, and when it was the only entry the scope resolves to nothing, which pi reads as "no scope" and quietly enables every model. `ModelsConfig` mirrors every array move of the draft in `savedModelIdsRef` so `collectModelRenames()` can tell a rename from an add or a delete without guessing. Only `resync` repairs entries; ordinary toggles stay minimal edits and never rewrite what the user did not touch. A models.json provider missing from the runtime (unsaved edits, no models, a key that does not work) must not be reported as a sign-in problem, which is why it has its own control: the switch renders disabled with that reason as its tooltip, while `EnabledModelsSection` — now built-in only — keeps the sign-in empty state. See `docs/adr/0004-enabled-models-toggles.md`.

### SSE reconnect on page refresh mid-stream
On `ChatWindow` mount, `GET /api/agent/[id]` is called. If `state.isStreaming === true`, SSE is reconnected automatically. `thinkingLevel` and `isCompacting` are also synced from this response.

### Compaction SSE events
Newer pi emits `compaction_start` / `compaction_end`; older versions emitted `auto_compaction_start` / `auto_compaction_end`. `handleAgentEvent` accepts both sets to keep `isCompacting` in sync. Manual compact is a blocking POST — the button stays disabled until the response returns.

### Tool execution events on the SSE stream
- Calls a tool makes itself through `ctx.executeTool()` (a codemode script's) emit `tool_execution_*` with `parentToolCallId` and ids `<parent>/<n>`. `toClientAgentEvent()` sends their start and end slim with `parentToolCallId`, and drops their updates. Test for nesting *before* rebuilding an update: the rebuild keeps only `toolCallId`, `toolName` and `partialResult`, so a nested update would reach the browser as a top-level tool. `handleAgentEvent` keeps nested events out of the running-tools phase, and `AgentSessionWrapper` never records them for replay; a parent's end also forgets every id under `<parent>/`, and `agent_end` clears the replay set.
- `tool_execution_end` never carries `result`, which can hold up to 1 MiB of bash output in `structuredContent`: the browser reads only its ids and renders the tool result message that follows. `entry_appended` is omitted, since nothing reads it and a custom entry can be 1 MiB.
- A codemode update publishes every call made so far each time one starts or ends, so its `details.calls` is cut to the newest 200 with `omittedCalls` counting the rest.
- A codemode card shows the script and the calls it made (`details.calls`) as rows inside the card, never as cards of their own: those calls never reach the model as tool calls. `handleAgentEvent` keeps a running script's progress snapshot in `activeToolResults`, as it does for shell output, so the card lists calls while they run; a snapshot has no content, which is how the card tells it from a finished result and skips the empty output. The finished result's "Script completed / Wall time / Output:" header is dropped from the output, since the card's colour and duration already say it.
- `createAgentEventStream()` coalesces `tool_execution_update` per `toolCallId` (latest wins, `TOOL_UPDATE_COALESCE_MS`). Before forwarding a `tool_execution_end` it discards that id's pending update, and `agent_end` discards them all: an update delivered after the end would put the tool back in the running phase. Everything else is forwarded at once, so a pending update can arrive after unrelated events.

### Transcript system messages, usage entries and context edits (pi >= 0.86)
- Every new session's first request persists a `message` entry with `role: "system"` holding the prompt sections and tool declarations; later prompt or tool changes append more. The agent loop announces them with `message_start` / `message_end` like any message. They are provider input, never conversation: `toClientAgentEvent()` drops them before the SSE stream (they carry every tool schema), `handleAgentEvent` skips any that slip through, `entryToUiMessage()` returns null for them, and `BranchNavigator` / `lib/project-tree.ts` never label or preview a branch with one. They still count toward `messageCount` and `totalMessages`, exactly as the SDK counts them.
- `usage` entries (`kind: "cache_warm"`) record prompt-cache warming that is billed but never enters model context. `computeSessionStats()` adds them like compaction usage so the token/cost counters match `/session` in the TUI.
- `context_edit` entries omit or replace an earlier entry's model context without changing raw history; the UI ignores them. A retain-none compaction stores its own id in `firstKeptEntryId`.
- `SessionManager.listAll()` now reads files newest-mtime first (then reverse filename) so `--resume` can render progressively; its stable sort keeps that order for sessions with equal activity time, and `listSessionsIncremental()` reproduces it from the stat fingerprints it already keeps.

### Running state polling + reconciliation
- The sidebar polls `/api/agent/running` every 2.5 seconds while the tab is visible and pauses polling in background tabs. The session-list response remains the initial fallback.
- `invalidateSessionListCache()` bumps the generation but **keeps** the previous scan, and the cache is fresh only while its recorded generation matches. Ordinary agent activity invalidates it constantly, and rebuilding costs hundreds of milliseconds because `loadAllSessions()` re-reads every forked and subagent session. Callers that only need metadata — mapping search hits to sidebar rows — pass `listAllSessions({ allowStale: true })` to read the previous scan and let the rebuild happen in the background. A stale scan is a complete catalogue apart from sessions created seconds ago, so those callers accept a brief window where a brand-new session is not yet listed.
- `useAgentSession` treats per-session SSE as primary for chat events and opens it before each prompt. `prompt_done` completes the current UI stage and notification immediately, but the idle SSE stays open for a 30-second grace window and is reused by the next prompt. `agent_start` cancels that close timer; `agent_settled` finishes extension-injected runs that have no wrapper-level `prompt_done` and starts a fresh grace window. Do not close on the first `agent_end`: retries, compaction, and extension-queued messages can continue the same logical prompt.
- While a run is active, `useAgentSession` periodically calls `GET /api/agent/[id]` and also reconciles on `visibilitychange`/`online`. This fixes missed terminal events from background tabs or half-open connections.
- Prompt runs use a monotonic run id; late SSE or slow reconciliation responses from an old run must be ignored so they cannot resurrect stale streaming bubbles.
- Every SSE (re)connection in `useAgentSession` is gated on `sessionHookMountedRef`. React Strict Mode (on by default in `next dev`) re-runs effects in declaration order after a simulated unmount: the mount-only effect's cleanup sets that ref to `false`, and it is only restored when that effect re-runs, *after* the warm-session effect. The warm-session effect therefore re-asserts the ref before `maintainEventsConnected()`. Without it a dev-server tab never opened the event stream on mount or when switching back to a running session, so streamed output and new messages stayed invisible until the 15-second reconcile poll or a page refresh (`next start` was unaffected).

### Worktrees and project grouping
- `lib/worktree.ts` resolves linked worktree top-levels back to the main repo `projectRoot`; `listAllSessions()` attaches that to each `SessionInfo` so all worktrees for one repo are grouped together in the sidebar.
- Worktree operations are served by `/api/worktrees` and guarded by the same allowed-root rules as `/api/files`.
- New worktrees are created under `<repoRoot>-worktrees/<sanitized-branch>`. Existing branches are reused; otherwise `git worktree add -b` creates the branch.
- Removing a dirty worktree returns `409` with `{ dirty: true }` so the UI can ask before retrying with `force`.
- Sessions whose cwd points at a removed worktree are inferred back into the main project instead of becoming a phantom project row.
- git prints POSIX-style absolute paths even on Windows, so every path read out of git goes through `toNativePath()` (`lib/paths.ts`) before it is compared or returned. Compare paths with `samePath()`, never `===` — raw equality made `isTopLevel` permanently false on Windows and hid the worktree switcher entirely. Branch names are not paths and must keep their forward slashes. Browser code cannot apply Node path rules, so `/api/worktrees` resolves `currentWorktreePath` server-side; the sidebar must use that identity for highlighting and removal fallback.

### File access allow-list
- `/api/files` is intentionally not a general filesystem browser. Allowed roots come from session cwds, their resolved project roots, and roots explicitly added with `allowFileRoot()`.
- `/api/files/...?sessionId=` also reads (never lists) a file outside the roots when that exact path appears in the session, so a chat link to it opens (`lib/session-file-references-core.ts`). Four things never count: transcript system messages (they carry every tool schema), the codemode script store, `context_edit` replacements (the UI never shows them, and they often restate a tool result), and the result of any tool other than pi's coding tools and the subagent tools — MCP, codemode, third-party extensions relay text a remote party controls, and any string in it would become readable. Such a result still authorizes its `details.fullOutputPath` and the arguments of the coding-tool calls it made through `ctx.executeTool()` (`nestedCalls`); arguments of its nested MCP calls do not count, because a script hands one MCP result to the next call without the model reading it. User and assistant messages, the model's own tool call arguments (MCP calls included) and the other entries count as before. Tools are matched by name, so keep the list in step with `CODING_TOOL_NAMES`.
- `/api/cwd/validate` and `/api/worktrees` call `allowFileRoot()` when they make a new location browsable. "Use default directory" is no exception: `/api/default-cwd` only creates `~/pi-cwd/YYYYMMDD`, and the sidebar selects it through `/api/cwd/validate` like any other directory.
- Allowed roots are stored slash-normalized, but that is a Set-key convention, not a correctness requirement: `isPathWithinRoots()` (`lib/path-security.ts`, the single implementation behind `isFilePathAllowed()`) re-resolves and case-folds both sides, so either path form authorizes correctly. Keep that one implementation — it is the security boundary.
- A UNC cwd (`\\host\share\dir`) must survive the `/api/files/[...path]` round-trip. `encodeFilePathForApi()` folds the `//` root into the first segment (`%2F%2Fhost`) because a literal `//` URL prefix is 308-normalized away before routing; `filePathFromApiSegments()` decodes it back. Never split UNC paths into segments and rejoin them — that silently turns `\\host\share` into the relative-looking `host/share` and every allow-check fails with 403.
- What `type=list` leaves out is visibility, never access: hidden entries stay readable by path. `lib/file-tree-visibility.ts` matches a listing's entries against the ignore rules with one `git check-ignore --no-index --stdin`, then asks one `git ls-files` which of the matched names hold a tracked path, since ignoring never applies to what Git tracks — so a tracked `build/` is listed and an ignored directory with a force-added file shows just that file. Never let check-ignore consult the index itself: it scans the whole index once per name, which took seconds for a 1,000-entry folder in a 200k-file repository and then fell back at the 5s timeout. `.git` and `.DS_Store` are always hidden. The fixed name list (`node_modules`, `dist`, `build`, …) applies only where Git has no view: outside a work tree, when git fails or times out, and inside a directory that is itself ignored with nothing tracked below it (otherwise a scratch dir under a dotfiles repo that ignores `*` would list empty). Names go to check-ignore as `./name`, since it rejects pathspec magic such as a leading `:(` for the whole batch, and to ls-files under `--literal-pathspecs`, so `*.log` or `[id]` cannot match a tracked `app.log` or `i`. Both calls pass `-c core.fsmonitor=false`, because reading the index otherwise runs a hook configured by whatever repository the user just expanded.
- A directory link (symlink or Windows junction) is authorized by where it resolves, so one inside a root that leads outside every root is listed but refused beneath it (#748). Never authorize the lexical path instead: a link committed to a cloned repo would then expose `~/.ssh` or `/` without the operator doing anything. The listing reports such a link's target as `outsideLinkTarget`; the explorer shows it with an "Allow browsing" button that posts `?type=allow-link` with that target. `checkLinkedDirectoryApproval()` (`lib/linked-directory.ts`) requires the link to sit in a directory that is inside the roots after resolving links and to still point where the operator was shown, then the route `allowFileRoot()`s the target until the server restarts — exactly the grant `/api/cwd/validate` gives any directory, so the endpoint widens nothing a caller could not already reach.
- `isExistingPathWithinRoots()` refuses any path with a `..` segment. Authorization (lexical, and Node's JS `realpathSync` alike) collapses `..` before resolving links, while the filesystem applies it after, so `link/../x` names a file beside the link's target: `/api/file-index?cwd=<project>/link/..` listed the folder holding it. Query-string and body paths reach the check verbatim; in `/api/files/[...path]` URL parsing drops literal `..` segments, and an encoded slash inside one segment (`link%2F..%2Fx`) is refused by the route itself, because a file referenced by the session skips the existing-path check. A link whose target contains a root or the home folder (`/`, `~`, a parent of the project) is listed with `outsideLinkEncloses`, and the explorer asks for confirmation before allowing it.

### Plugins and skills
- `/api/plugins` uses pi's `SettingsManager` + `DefaultPackageManager` for global/project package install, remove, update, enable, and disable. Disabling writes empty `extensions/skills/prompts/themes` arrays for that package entry.
- `/api/skills` uses `DefaultResourceLoader` so settings paths, package skills, and project `.agents/skills` are listed the same way the runtime sees them.
- Skill toggling edits only the `disable-model-invocation` frontmatter key on the target `SKILL.md`; keep that surgical so user formatting survives.
- `/api/skills/install` shells through `npx skills add ... --agent pi`; project installs run with the selected cwd.
- Each sidebar group of the Skills, Plugins and MCP panels (a skill scope, a package scope, an `mcp.json`; not standalone extensions) has a small switch in its heading (`ConfigSidebarGroupSwitch`), with the same rule as the Models panel's provider switch: on only while every row is, so a partial group reads as off beside its `n/m` count and one click completes it. A panel whose group can hold rows its switch never turns on passes its own `checked` (MCP: `mcpGroupSwitchChecked()`), or that rule would keep the switch off for good. It lives in the heading row so the sidebar loses no height, which matters in the 190px phone layout. A switch sends one request with a list (`PATCH /api/skills` with `filePaths`, `POST /api/plugins` with `packages`, `POST /api/mcp` `set-enabled` with `servers`) and gets a result per item, so a refused row does not stop the rest; what it left undone is shown under that group's heading (`ConfigSidebarGroupStatus`). `SettingsManager` records load and write failures instead of throwing, and `flush()` still resolves; the bulk plugin path reads them back with `drainErrors()`, or an unreadable settings.json would report success. An entry already in the requested state is left alone, and enabling keeps an entry's own keys such as `autoload`. Disabling empties the four resource lists and nothing keeps the filters they replaced, so switching a group off leaves an enabled filtered package on (the SDK reports every object entry as `filtered`) and says so, and the bulk route refuses one. `PATCH /api/skills` edits only `.md` files: the roots it allows also hold `auth.json`, settings and project files.
- The Skills and Plugins panels are built from the shared blocks in `components/SettingsUi.tsx` (`ConfigScopeTag`, `ConfigScopeSwitch`, `ConfigAddSourcePanel`, `ConfigDetailGrid`, `ConfigFooterStatus`, `ConfigTrustNotice`), `itemsToSwitch()` in `components/settings-ui-helpers.ts`, and `lib/display-path.ts`; a new settings section reuses them instead of copying a panel. Why a control is unavailable is visible text — a scope switch's `disabledReason` (under the switch's whole line, so controls passed as its `children` stay level with it), the note under a detail header, a footer summary that opens its diagnostics — never only a `title` tooltip, which a touch screen cannot show. `SettingsUi.tsx` takes every word as a prop and holds no state, so it renders outside the i18n provider; the panels pass `t()` strings. `ConfigTrustNotice` shows its button only when given `onTrust`. Settings › MCP passes one, AppShell's trust dialog threaded through `SettingsPanel` (see **Trust from Settings**). The Skills and Plugins panels already take the page's `trust` and reload after a trust decision, but have no Trust button yet: that needs `onOpenTrustDialog` passed to them and `mcpProjectTrustable()`'s rule.

### Subagents
- Sub-agent delegation is owned by the user-installed `pi-subagents` package, a normal pi extension that is not a Pi Web dependency. Its tools load with every session like any other installed package; Pi Web neither bundles it nor strips, suppresses, or manages it. Pi Web ships no sub-agent engine and provides no feature switch for this.
- Legacy sessions created by the removed built-in engine still render. Their metadata types (`pi-web:subagent`, `pi-web:subagent-status`, `pi-web:subagent-result`) are read by `readSubagentRun()` / `readSubagentSessionResources()` in `lib/subagents.ts`, `relation.kind === "subagent"` in `lib/session-reader.ts`, `AgentSessionPanel`, and `GET /api/subagents/[id]`. Only the GET survives: `POST /api/subagents/[id]` (steer/abort) was removed with the engine.
- Agent profile files (`~/.pi/agent/agents/*.md`, project `.pi/agents/*.md`) are shared with `pi-subagents` and other runtimes, so a save round-trips the frontmatter keys this app does not own (`name`, `package`, `allowed_subagents`, `exclude_extensions`, `mutationTools`, …). Managed keys are exactly the pi-subagents spellings `description`, `display_name`, `tools`, `excludeTools`, `extensions`, `subagentOnlyExtensions`, `skill`, `skills`, `skillPath`, `model`, `thinking`, `systemPromptMode`, `inheritProjectContext`, `inheritGlobalContext`, `inheritSkills`, `defaultContext`, `async`, `timeoutMs`, `toolTimeoutMs`, `maxSubagentDepth`, `allowNestedSubagents`, `allowedAgents`, `advertise`, `output`, `defaultReads`, `defaultProgress`, `acceptanceRole`, `aliases`. The editor lives in `AgentsConfig.tsx`, backed by `GET/PUT/DELETE /api/subagents/profiles` and `GET /api/subagents/tools`.
- **Scope shadowing.** Same-name profiles in a higher-precedence scope shadow lower ones: project > workspace > global, per `lib/subagent-profile-precedence.ts`. The panel still lists every configured source and marks shadowed rows "Overridden".
- **`tools` is stored raw.** A save writes every entry verbatim — builtin names, extension and package tool names, `mcp:<server>[/<tool>]`, and path-like selectors — and filters nothing. `tools` omitted (the editor's "inherit default tools" toggle) means the child inherits Pi's default tools; an explicit empty list means no tools. `excludeTools` is the raw deny list, applied after resolution in both cases.
- **`extensions` is a tri-state.** An absent key loads the parent's ambient extensions in a background child, an empty value loads none, and a comma/block list loads exactly those paths. Legacy files written by the removed editor migrate on read: `load_skills`→`inheritSkills`, `load_extensions` (whitelist / `false` / `none`)→`extensions` list or none, `inherit_context`→`inheritProjectContext`, `run_in_background`→`async`, `prompt_mode`→`systemPromptMode`, `disallowed_tools`→`excludeTools`, and the `tools` sentinels `none`→`[]` / `all`/`*`→the builtin 8. A save drops those retired keys: they were ours, pi-subagents ignores them, and keeping them would claim semantics pi-web no longer owns.
- **Enabling is not ours to invent, but the panel now exposes it.** `subagents.agentOverrides.<name>.disabled` owns enable/disable. `lib/subagent-overrides.ts` writes only the user settings file (`<agentDir>/settings.json`, the same path `FileSettingsStorage` derives): disabling sets `disabled: true` on the override entry, enabling deletes that key and prunes an empty entry / `agentOverrides` / `subagents` like pi-subagents' own `enable` action. Everything else in the file survives (JSON read, targeted mutate, atomic write), and the write resolves a symlinked settings path first so dotfile-managed setups keep the link. That writer takes no file lock, matching pi-subagents' own unlocked writer; the lost-update window against SDK `SettingsManager` writes is parity by design, not a bug to fix here. `PUT /api/subagents/overrides` backs the switch on a read-only catalog row; the UI refetches profiles + catalog after a toggle so the row's effective state comes from the catalog's disable ladder, never re-derived. `POST /api/subagents/eject` copies a catalog agent file verbatim into the global or project agent directory (a same-name copy conflicts with 409); the source must be a **builtin or package** file the catalog discovered for that cwd (`user`/`project` scan-dir rows are rejected 400, matching pi-subagents' `handleEject`), and a copy that fails to parse is removed before the error is returned. The tool checkboxes come from `/api/subagents/tools`, which loads the same `createAgentSessionServices()` the models route does and reads `resourceLoader.getExtensions()` — extension tools register at load time, so no session starts. The route caches per cwd for 60 s; `powershell` is filtered out off Windows. MCP enumeration is out of scope.
- **Disable provenance, not file shadowing, drives the lock.** A catalog row's `disabledSource` (`{ scope: "user" | "project"; via: "override" | "bulk" }`) records which settings entry disabled it; it is set whenever the row's effective `disabled === true` and the same-name winner's value is projected onto every shadowed row, because the winner is what the runtime dispatches. `overriddenBy` stays purely file-shadowing provenance. The switch locks only when the user-scope toggle could not undo the disable: `via === "bulk"` at either scope, or a project-scope override. A user-scope override stays switchable — flipping it off removes that override.
- See `docs/adr/0006-delegate-subagents-to-pi-subagents.md`.


### Web password throttling
- `lib/auth-throttle.ts` is deliberately global, not per-IP: Next 16 route handlers have no socket address and `x-forwarded-for` is spoofable, while the server binds `127.0.0.1` for a single operator. Failures double the delay (1s → 60s cap) for everyone; a success or 5 idle minutes resets it. The reset window must stay longer than the max delay or waiting out one block restarts the burst.
- State lives on `globalThis` under `Symbol.for("pi-web:auth-throttle")` so it survives hot reload and is shared by every module instance. Tests reset it with `recordAuthSuccess()`.
- `POST /api/web-auth` and every `Authorization: Basic` header on `/api/*` share the counter; `proxy.ts` checks Basic before its `/api/web-auth` exemption, so `GET /api/web-auth` is not an unthrottled password oracle. A valid session cookie is checked first and is never blocked. While blocked, Basic gets `429` even with the right password (otherwise the answer leaks), and a Basic success does not reset the counter: Basic clients authenticate on every request, so a reset would restart an interleaved guesser at the base delay. The proxy and route handlers share the `globalThis` state under both `next dev` and `next start` (checked by failing one and observing `429` on the other).

### Auth and model config
- `ModelsConfig` combines models from `~/.pi/agent/models.json` with provider auth status from pi's `AuthStorage`/`ModelRegistry`.
- Provider listing is capability-driven, never id-driven: `lib/provider-listing.ts` decides membership from `auth.apiKey.login` / `auth.oauth` plus the stored credential type, so dual-auth providers (anthropic and github-copilot today — which providers declare both changes between SDK releases, so never assume it from an id) appear exactly once and never fall through both lists (#309). `lib/provider-listing-runtime.ts` adapts `ModelRuntime` to those pure helpers.
- auth.json holds **one** credential per provider and `ModelRuntime.logout()` deletes whichever it is. The delete routes therefore use `removeStoredCredentialIfType()` to compare and delete under the same file lock used by pi's auth storage. `ModelsConfig` also refreshes *both* provider lists after any auth change — refreshing one leaves a dual-auth provider rendered twice.
- OAuth/device-code/manual-code flows are streamed by `GET /api/auth/login/[provider]`; manual code responses POST back with a short-lived token stored in `globalThis.__piLoginCallbacks`.
- API-key routes store and remove keys through `AuthStorage`. Status endpoints must never return the raw key.
- The model test route is `app/api/models-config/test/route.ts`; `app/api/models/test/` is not a real route.

### Mobile software keyboard (`hooks/useViewportHeight.ts`)
- While an editor has focus and the visual viewport is more than `KEYBOARD_MIN_HEIGHT_PX` (60px) shorter than `innerHeight / scale`, the hook writes `visualViewport.height` to `--app-viewport-height`. Compare against the zoom-corrected height: iOS auto-zoom and pinch zoom shrink the visual viewport on their own, and skipping zoomed pages left the composer behind the keyboard. Smaller shrinks are Safari toolbars.
- WebKit settles the shrunken height only after the keyboard animation, often without another `resize` (bugs.webkit.org 265578), and an IME candidate bar resizes the keyboard with no viewport event at all. Every trigger therefore starts one non-restarting chain of re-reads (`SETTLE_DELAYS_MS`), and composition/input/keyup events on a focused editor count as triggers. Reading once per event kept the full-screen height; the page then scrolled to the caret and `scrollTo(0, 0)` fought the user's finger, which reads as a jittering composer.
- The same check sets `<html data-keyboard-open>`. Under `(max-width: 640px), (pointer: coarse) and (max-height: 500px)` CSS then hides `.chat-input-controls` and `.extension-status-shelf` and drops the bottom safe-area padding the keyboard already covers. Phone landscape is included because it has the least height; tablets keep their controls. `MobilePwaLayout.test.mjs` asserts each targeted class exists on its component, so a rename cannot leave a rule silently dead.

### Old Safari (iOS 16.2)
- `/` renders entirely on the client, so one script chunk the browser cannot *parse* is a blank page, not a broken feature (#753). Next 16 compiles for Safari 16.4+ by default; the `browserslist` in `package.json` lowers Safari and iOS to 16.2 so SWC turns class `static {}` blocks into private static fields. That reaches Next's own client runtime, but other node_modules keep the syntax they ship unless they are in `transpilePackages`; mermaid and `@mermaid-js/parser` are listed there because their lazy diagram chunks are full of static blocks. Keep the other browserslist entries at Next's defaults.
- SWC cannot downlevel a RegExp **lookbehind** (`(?<=`, `(?<!`), which Safari parses only from 16.4. Do not write one in client code: `lib/markdown.ts` emulates its leading lookbehinds with `replaceNotPrecededBy()`. A lookbehind built at runtime (`new RegExp("(?<=…)")` inside `try`) only fails when it runs, which is how `lib/gfm-autolink-email-loader.cjs` fixes the email regex in `mdast-util-gfm-autolink-literal`; the loader is registered for both webpack and Turbopack in `next.config.ts` and fails the build if that regex changes upstream.

## Pi Session File Format

Location: `~/.pi/agent/sessions/<encoded-cwd>/<timestamp>_<uuid>.jsonl`

```jsonl
{"type":"session","version":3,"id":"<uuid>","timestamp":"...","cwd":"/path","parentSession":"/abs/path/to/parent.jsonl"}
{"type":"model_change","id":"<8hex>","parentId":null,"provider":"zenmux","modelId":"claude-sonnet-4-6","timestamp":"..."}
{"type":"message","id":"<8hex>","parentId":"<8hex>","message":{"role":"user","content":"..."}}
{"type":"message","id":"<8hex>","parentId":"<8hex>","message":{"role":"assistant","content":[...],...}}
{"type":"message","id":"<8hex>","parentId":"<8hex>","message":{"role":"toolResult","toolCallId":"...","content":[...]}}
{"type":"compaction","id":"<8hex>","parentId":"<8hex>","summary":"...","firstKeptEntryId":"<8hex>","tokensBefore":N}
{"type":"session_info","id":"...","parentId":"...","name":"user-defined name"}
```

`entryIds[]` in `SessionContext` is a parallel array to `messages[]` — maps each displayed message back to its `.jsonl` entry id, used for fork and navigate_tree calls.
